# feasibility-review 技能使用说明

第四阶段「初步可行性分析与风险识别」技能的使用文档。技能本体在 [feasibility-review](./feasibility-review/) 文件夹中。

## 一、这个技能做什么

在需求已经明确的基础上，从项目整体角度判断：

- 这个软件项目是否值得做？
- 是否具备基本实施条件？
- 有没有明显障碍？
- 有哪些风险需要在后续阶段重点关注？

它回答的是**"项目能不能合理地进入后续设计阶段"**，不是"具体怎么实现"。技术调研、技术选型和 PoC 属于第六阶段，本技能不会涉及。

**最终产物**：一份 `FEASIBILITY_REVIEW.md`（初步可行性分析与风险评估报告），放在项目工作目录 `docs/04-初步可行性分析/` 下。

## 二、技能文件结构

```
step4初步可行性分析与风险识别/
├── 第四阶段说明.txt          ← 阶段设计理念与需求来源
├── 使用说明.md               ← 本文档
└── feasibility-review/       ← 技能本体
    ├── SKILL.md              ← 流程与规则（AI 执行时读取的主文件）
    ├── TEMPLATE.md           ← FEASIBILITY_REVIEW.md 的文档模板
    └── CHECKLIST.md          ← 阶段完成检查清单
```

## 三、使用前提

### 1. 前序文档（推荐已具备）

技能启动后会自动读取以下文档，不需要你重复描述项目：

| 文档 | 用途 |
| --- | --- |
| INITIAL_REQUIREMENTS.md | 项目最初的想法与背景（辅助参考） |
| DEVELOPMENT_APPROACH.md | 已确定的 AI 开发方式与约束 |
| REQUIREMENTS.md | **核心事实来源**：需求、MVP、非功能需求、约束 |
| REQUIREMENT_REVIEW.md | 此前发现的需求问题与处理结果 |
| PRODUCT_BACKLOG.md | 首版功能范围与优先级 |

文档缺失时技能会**优雅降级**：辅助文档缺失可以继续；核心文档（REQUIREMENTS.md、PRODUCT_BACKLOG.md）缺失时会提示风险，你确认后仍可继续，缺口会如实记录。

### 2. 你需要准备回答的问题

技能会像访谈一样**逐轮提问**（每轮 2–4 个），只问文档里没有的关键信息，主要围绕六个方面：

| 方面 | 典型问题 |
| --- | --- |
| 开发资源与个人能力 | 独立开发还是有协助？每周能投入多少时间？ |
| 时间与预算约束 | 有没有交付期限？能否接受每月持续费用？ |
| 目标平台与外部环境 | 软件跑在什么平台？要不要上架审核？ |
| 数据与外部资源 | 数据谁提供？涉及版权或许可吗？ |
| 隐私、安全与合规 | 是否处理个人信息？是否涉及未成年人？ |
| 运营与后续维护 | 给谁用？需要长期在线吗？出故障谁处理？ |

**不确定的问题直接回答"未知"即可**，会被记为待确认事项，不会阻塞流程。

## 四、如何触发

### 方式一：直接对话（推荐说法）

在完成第三阶段的项目对话中，对 AI 说：

- 「进入第四阶段，做初步可行性分析与风险识别」
- 「用 feasibility-review 分析这个项目能不能做」
- 「帮我做可行性分析，识别项目风险」

### 方式二：显式调用技能

```
使用 feasibility-review 技能，基于当前项目的需求文档做第四阶段可行性分析
```

## 五、技能的工作流程

```
读取前序文档 → 识别信息缺口 → 逐轮向你提问 → 六维度可行性分析
     → 风险识别与评估 → 风险关系分析 → 可行性结论 → 你审查确认 → 生成文档并交接
```

各阶段你会经历什么：

1. **读取阶段**：AI 静默读取前序文档，不会要求你重复描述需求。
2. **提问阶段**：AI 每轮问 2–4 个关键问题，每个问题都说明"为什么问"；已能从文档得知的信息不会重复问。
3. **分析阶段**：AI 从产品范围、人力能力、预算成本、平台环境、数据资源、运营合规六个维度评估，识别风险（RISK-001 格式登记）并分析组合风险。
4. **结论阶段**：AI 给出四档结论之一——**可行 / 有条件可行 / 暂不可行 / 信息不足**，并列出阻塞问题与进入下一阶段的条件。
5. **验收阶段**：你审查结论、风险和待确认事项，确认后 AI 才生成正式文档。
6. **交接阶段**：文档第 06 节写明移交第五阶段的设计约束、移交第六阶段的技术验证清单。

## 六、作为用户，你需要关注的三个关键机制

### 1. 信息可信度分离

报告中四类信息严格区分，请审查时留意：

| 标记 | 含义 |
| --- | --- |
| `confirmed` | 你明确确认过的事实 |
| `assumption` | AI 的初步估算（未经你确认） |
| `pending` | 待你补充或待核实的信息 |
| `deferred` | 移交给第五、六、七、八阶段的事项 |

AI 的推测永远不会被写成你已确认的事实。

### 2. 需求变更走反馈循环

如果分析发现首版范围过大等问题，AI 只会**提出建议**（如"建议缩小 MVP"）。是否调整由你决定；确认调整后应**返回第三阶段**更新 REQUIREMENTS.md 和 PRODUCT_BACKLOG.md，然后本阶段重新检查。AI 不会擅自修改需求文档。

### 3. 越界保护

技能内置边界检查：不会测试技术、不会选型、不会设计架构或页面。如果发现报告里出现了具体技术方案，属于越界，应要求 AI 删除并移交给对应阶段。

## 七、什么时候算完成

阶段退出条件（缺一不可）：

- [x] 六个可行性维度均已评估
- [x] 重大风险已记录，组合风险已分析
- [x] 已确认信息与 AI 估算、待确认事项已区分
- [x] 需要第六阶段验证的技术问题已登记（但未展开验证）
- [x] 可行性结论明确，你已审查确认
- [x] 第 06 节交接信息完整
- [x] CHECKLIST 全部通过
- [x] 你明确确认"可以进入第五阶段"

完成后即可进入**第五阶段：产品设计与交互原型**。

## 八、常见问题

**Q：跳过前三个阶段直接用这个技能可以吗？**
可以，但分析可靠性会下降。核心需求文档全缺时，技能会基于你的口述推进并在文档中标注输入缺口。

**Q：结论是"信息不足"算失败吗？**
不算。这正是设计意图之一：关键条件没明确时，不强行得出"可行"，而是告诉你缺什么信息、需要你做什么决定。

**Q：报告中的风险等级是"待评估"是什么意思？**
表示该风险的发生可能性依赖后续信息（如技术验证结果），本阶段不强行打分，会在指定阶段复核。

**Q：分析完发现项目"暂不可行"怎么办？**
说明存在已确认的项目级阻塞问题（如必要资源无法获得）。此时应调整项目条件或放弃，而不是带着阻塞问题强行进入第五阶段。
