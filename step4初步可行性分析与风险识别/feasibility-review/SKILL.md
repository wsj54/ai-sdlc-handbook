# 初步可行性分析与风险识别

在需求已经明确的基础上，从项目整体角度判断：**这个软件项目是否值得做、是否具备基本实施条件、有没有明显障碍，有哪些风险需要在后续阶段重点关注。**

本阶段回答的是"项目能不能合理地进入后续设计阶段"，不是"具体怎么实现"。

产出：`FEASIBILITY_REVIEW.md`。文件结构见 [TEMPLATE.md](./TEMPLATE.md)；宣告完成前必须通过 [CHECKLIST.md](./CHECKLIST.md)。

## 与第六阶段的边界（最高优先级约束）

第四阶段和第六阶段都谈"可行性"，但回答的问题不同：

| | 第四阶段（本阶段） | 第六阶段（后续） |
| --- | --- | --- |
| 核心问题 | 项目整体能不能做？ | 具体技术方案能不能实现需求？ |
| 典型判断 | 产品目标是否现实、MVP 是否过大、个人能力和时间是否够、预算是否可承受、平台和数据准入是否有明显障碍、有哪些重大风险 | 某项关键技术能否实现需求、某方案是否满足性能要求、某外部服务是否符合要求、是否需要 PoC |
| 产出 | 可行性结论、风险清单、待确认事项 | 技术调研结果、PoC 结果、技术验证结论 |

判定一个问题属于哪个阶段，看**答案取决于什么**：

| 问题的答案取决于 | 属于 |
| --- | --- |
| 资源、时间、预算、个人能力、MVP 范围 | 第四阶段 |
| 平台准入条件、合规义务、数据可获得性的初步判断 | 第四阶段 |
| 某项关键技术的实测表现 | 第六阶段 |
| 具体服务、框架、API 的能力与限制 | 第六阶段 |
| 技术选型、数据库、系统架构 | 第七阶段 |

一句话规则：**第四阶段负责发现问题，第六阶段负责深入验证具体技术问题。**

由此推出三条硬约束：

1. **识别但不验证。** 发现技术相关的潜在风险（如"某项核心能力的效果可能不稳定，影响产品核心价值"）时，只登记"需要在技术验证阶段确认的问题"，不开始测试、不比较候选方案、不设计评测方法。
2. **初步应对建议不是技术解决方案。** 建议只写原则性方向，如"明确可接受的成本上限，在技术验证阶段评估成本"；不能写"采用某种缓存架构、模型路由或指定某个具体模型"。
3. **不因技术不确定而否定项目。** 只要不存在已确认的项目级阻塞问题，技术不确定性一律记录后交给第六阶段，不据此判定"暂不可行"。

## 输入

### 前序文档（不要求用户重复提供）

| 输入文档 | 用途 |
| --- | --- |
| INITIAL_REQUIREMENTS.md | 了解项目最初的想法与背景，辅助参考 |
| DEVELOPMENT_APPROACH.md | 了解已确定的 AI 开发方式与开发约束 |
| REQUIREMENTS.md | 核心事实来源：完整需求、MVP、非功能需求、约束 |
| REQUIREMENT_REVIEW.md | 此前发现的需求问题与处理结果 |
| PRODUCT_BACKLOG.md | 首版功能范围、优先级、产品依赖 |

规则：

- 先读文档，能提取的信息不问用户。
- 初始想法与正式需求冲突时，以第三阶段确认的需求基线为准。
- 本阶段的工作是**建立可行性分析的基础信息**，不是重新分析需求。

### 缺失处理（优雅降级）

| 情况 | 处理方式 |
| --- | --- |
| 五份文档全部缺失 | 询问用户是否已完成前序阶段；用户坚持继续时，仅基于用户口述推进，并在文档"文档信息"中记录输入缺口 |
| 核心文档（REQUIREMENTS.md、PRODUCT_BACKLOG.md）缺失 | 说明这会显著降低分析可靠性，用户确认后再继续；缺口记为待确认事项 |
| 仅辅助文档缺失 | 用现有文档推进，缺失项记入文档信息 |

任何情况下都不凭空补全缺失的前序结论；因此无法做的判断记为待确认，不装作已分析。

## 向用户收集信息

需求文档描述产品本身，可行性分析还需要开发者实际拥有的资源和外部条件。这部分通过 grill 式逐轮提问获取。

### 提问总规则

1. **已有信息不重复询问。** 优先从文档提取；用户已确认平台、开发人数的，不再问。
2. **缺失但重要的才问。** 由 AI 判断该信息是否会影响可行性判断。
3. **不重要的允许未知。** 不为了填满文档而让用户回答无关问题。
4. **用户不懂的先解释再问。** 例如用户不知道项目有哪些运营成本时，先说明可能持续产生的费用类别，再问承受意愿，而不是要求用户直接估算。
5. **推测明确记录。** 不把 AI 的推测写成用户已确认的事实。
6. **重要决策由用户做。** AI 可以分析并给建议，但不擅自改变已确认的需求范围。

### 六个问题域

按需取用，不必每个项目问满。每轮问完即更新文档，再判断下一轮问什么。

**A. 开发资源与个人能力**
- 项目由个人独立开发，还是有人协助？
- 每周大概能投入多少时间？是否有预期的完成时间？
- 当前是否具备开发所需的基础能力？
- 是否存在明确不做、暂时无法解决的事情？
- 是否需要依赖其他人的帮助？

（不需要详细技术能力清单；结合开发方式规划与用户描述识别明显的能力缺口即可，只做风险识别，不设计弥补方案。）

**B. 时间与预算约束**
- 是否有明确的交付期限？能否接受分阶段完成？
- 开发预算是多少？
- 能否接受每月持续产生的服务器、模型 API 等费用？
- 是否有免费或低成本运行的要求？

（关注整体成本承受能力，不调查具体服务的价格、不算具体方案的成本。用户没有明确预算时记为未知，转而分析哪些功能可能带来较高持续成本。）

**C. 目标平台与外部环境**
- 软件主要在哪个平台运行？是否多个平台？
- 是否有必须适配的设备或操作系统？是否需要特定网络环境或离线使用？
- 是否涉及应用商店上架或其他平台审核？
- 是否依赖特定平台提供的账号、权限或服务？

（只确认外部环境和准入条件，识别设备适配、发布渠道等风险；用什么框架、如何适配版本属于后续阶段。）

**D. 数据与外部资源**
- 软件所需的数据由谁提供？是否有现成来源？
- 是否需要调用第三方服务？是否需要用户授权才能获取数据？
- 是否涉及版权、数据使用许可？
- 是否存在数据缺失、质量不稳定的问题？

（确认资源能否由用户合法、持续地提供；不研究具体的数据解析技术。）

**E. 隐私、安全与合规**
- 是否会处理个人身份信息？是否涉及未成年人数据？
- 是否涉及财务、医疗等敏感业务信息？
- 是否需要保存用户上传的文件？是否有存储地区或保留期限要求？
- 是否存在必须满足的法律法规、组织制度或平台政策？

（只做初步风险识别，如"涉及未成年人使用，可能产生额外的个人信息保护要求，需要进一步确认适用义务"；具体安全架构、加密技术、权限机制不在此展开。）

**F. 运营与后续维护**
- 软件是自己使用，还是提供给其他用户？预计多少用户？
- 是否需要长期在线运行？是否需要持续更新？
- 出现故障后由谁处理？是否接受软件暂时不可用？
- 是否需要持续支付服务器或第三方服务费用？

（需要长期运行的软件，除了"能不能开发"，还要评估"能不能长期运行和维护"。）

### 提问格式

每轮 2–4 个问题，按阻塞程度排序：会阻塞可行性总体判断的先问。可选项存在时写含义并给推荐；开放信息类问题直接问事实。

```text
❓ 问题 1｜<能独立理解的标题>
为什么问：<它影响哪个维度的判断或哪类风险>
可选解释（如有）：
A. <含义 A>
B. <含义 B>
推荐：<推荐项 + 理由>
（不确定可回答"未知"，将记为待确认事项，不影响继续推进）
```

用户回答后先更新文档，再判断是否还有重要信息缺口；没有就进入分析，不追求把所有问题问完。

## 信息可信度规则

分析中四类信息必须区分，映射到统一五状态体系：

| 信息类型 | 状态 | 示例 |
| --- | --- | --- |
| 用户明确提供并确认 | `confirmed` | 用户明确表示预算为某个具体数额 |
| AI 根据项目情况做的初步估算 | `assumption` | AI 估计实际花费可能高于用户预期 |
| 用户不知道、未提供 | `pending` | 实际运营费用未知，属待确认事项 |
| AI 推测的外部限制 | `pending`（标注待核实） | 推测某类服务可能存在使用限制 |
| 属于后续阶段的技术不确定性 | `deferred` | 登记给第六阶段验证的问题 |

硬规则：AI 的推测和估算只能进入 `assumption` 或 `pending`，永远不能写成 `confirmed`；交付前全文检查，确认没有把推测表述为用户已确认的事实。

## 工作流程

### 1. 读取和审查前序文档

完整读取可用的前序文档，提取：产品目标与核心价值、MVP 范围、非功能需求、已知约束与假设、已识别的需求风险、开发模式与开发方式、开发者已知的能力与限制。

同时检查四个问题：

- 是否存在影响可行性判断的信息缺失？
- 是否存在明显不合理的项目假设？
- 是否存在与用户资源条件冲突的需求？
- 是否存在需求阶段尚未解决的重大问题？

发现重要问题，转入提问轮次。本步骤的产物可以是 AI 内部分析，不必单独生成文档。

完成标准：基础信息已建立；信息缺口清单已形成。

### 2. 识别信息缺口并向用户提问

按上文"向用户收集信息"的规则与格式，逐轮收集：开发资源与能力、时间与预算、平台与外部环境、数据与外部资源、隐私合规、运营维护。

用户回答"不知道"的内容记为 `pending`，不逼答、不编造。

完成标准：影响可行性判断的关键信息已获得，或已明确记为待确认。

### 3. 开展初步可行性分析

从六个维度分析，每个维度给出判断和依据：

| 分析维度 | 分析内容 |
| --- | --- |
| 产品与范围可行性 | 产品目标是否现实，MVP 是否过大，需求是否存在明显矛盾 |
| 人力与能力可行性 | 当前开发者的能力、时间和资源是否足以支撑项目 |
| 预算与成本可行性 | 开发、运行和维护成本是否可能超出承受能力 |
| 平台与外部环境可行性 | 目标平台、外部服务、账号权限、运行环境是否存在明显限制 |
| 数据与资源可行性 | 所需数据、素材、第三方资源是否可获得并允许使用 |
| 运营与合规可行性 | 产品运行维护、数据保护、法律法规和平台政策是否存在明显障碍 |

分析深度自适应：

- 不是每个维度都要复杂分析。完全离线运行、无第三方服务、不涉及他人数据的个人工具，运营成本与合规分析可以从简，标注"从简原因"即可。
- **不能因为缺少信息就直接判定不可行。** 用户没提供预算时，记录"预算尚未确定，无法判断长期运营成本是否在可接受范围内"——这是待确认事项，不是已确认的项目风险。

完成标准：六个维度均有判断（可行 / 有条件 / 存疑 / 不适用+原因），判断有依据。

### 4. 识别项目风险

基于可行性分析识别风险。八类风险分类（按需使用，不必凑满）：

| 风险类别 | 典型问题 |
| --- | --- |
| 需求与范围风险 | MVP 范围过大、需求不明确、功能之间存在冲突 |
| 开发资源风险 | 个人时间不足、能力存在明显缺口 |
| 成本风险 | 持续运营成本超预算 |
| 外部依赖风险 | 第三方服务不稳定、账号权限获取困难 |
| 数据与资源风险 | 数据难以获取、素材使用权不明确 |
| 平台与环境风险 | 目标平台存在准入限制或运行条件限制 |
| 安全与合规风险 | 个人信息处理、数据保护、法律与平台要求 |
| 运营维护风险 | 缺乏长期维护能力、服务中断难以及时处理 |

每条风险使用统一记录结构：

| 属性 | 说明 |
| --- | --- |
| 风险编号 | RISK-001 |
| 风险名称 | 简明描述 |
| 风险描述 | 具体可能发生什么问题 |
| 风险来源 | 来源于哪项需求、约束或用户提供的信息 |
| 发生可能性 | 低 / 中 / 高 / 暂时无法判断 |
| 影响程度 | 低 / 中 / 高 |
| 风险等级 | 综合判断（高 / 中 / 低 / 待评估） |
| 可能后果 | 发生后会影响什么 |
| 初步应对建议 | 原则性处理方向（不是技术方案） |
| 后续关注阶段 | 第五、第六、第七、第八阶段等 |

记录示例（占位，非真实项目）：

> **RISK-001：持续运营成本可能超出承受能力**（等级：待评估）
> 风险描述：系统依赖按量计费的外部服务，使用规模增长后可能产生持续费用。
> 风险来源：需求包含外部服务依赖；用户未给出运营预算（待确认）。
> 可能后果：实际运营成本超过可接受范围，被迫缩减或停止服务。
> 初步应对建议：明确可接受的成本上限，在技术验证阶段评估相关方案的成本。
> 后续关注阶段：第六阶段。

完成标准：每条风险字段完整；应对建议均未越界成技术方案。

### 5. 分析风险之间的关系和影响

只列清单不够。对全部风险回答五个问题：

1. 哪些风险会直接影响 MVP 是否能够成立？
2. 哪些风险可能相互叠加（组合风险）？
3. 哪些风险可以通过缩减需求范围解决？
4. 哪些风险需要等到技术验证才能确认？
5. 哪些风险需要用户现在作出决定？

组合风险是重点：单看每项风险可能都不是阻塞问题，叠加后可能导致项目无法按预期完成（典型组合：功能范围大 + 可投入时间少 + 无协助）。识别到的组合风险单独记录：叠加了哪些风险、叠加后果、处理方向。

完成标准：五个问题均有结论；组合风险已单独登记。

### 6. 形成初步可行性结论

给出明确判断，不只罗列问题。四档结论：

| 结论 | 含义 | 使用条件 |
| --- | --- | --- |
| 可行 | 可以进入后续阶段 | 没有发现明显的项目级阻塞因素，当前资源和约束基本可以支撑项目 |
| 有条件可行 | 满足一定条件后进入后续阶段 | 存在部分问题，但可以通过明确约束、缩减范围或补充条件来控制 |
| 暂不可行 | 需要重新调整后再继续 | 存在**已确认的**阻塞问题，如必要资源无法获得、目标平台不允许实现预期用途 |
| 信息不足 | 暂时无法作出可靠判断 | 关键条件尚未明确，需要用户补充信息或作出决定 |

判定约束：

- 有条件可行不要求先解决所有风险；本就属于第六阶段验证的风险不阻塞进入第五阶段。
- 已发现明确的项目级阻塞问题时，不能以后面还有技术验证阶段为由忽略它。
- 不为了完成文档而强行得出"可行"；信息不够就明确给"信息不足"，并说明缺什么。

完成标准：总体结论为四档之一；各维度判断与总体结论一致；阻塞问题（如有）已明确列出。

### 7. 用户审查与决策

向用户展示：可行性分析结论、重要风险、组合风险、待确认事项、需要用户现在决策的问题。用户确认、纠正或补充后，才生成正式文档。

用户在审查中提出的调整（如缩减首版范围）涉及需求变更时，走反馈循环：AI 只提出建议（如"建议重新评估首版范围，将部分非核心功能移入后续版本"），**是否调整由用户决定**；用户确认后返回第三阶段更新 REQUIREMENTS.md 和 PRODUCT_BACKLOG.md，然后本阶段重新检查调整后的范围是否可行。AI 不直接修改需求文档。

完成标准：用户已明确确认结论、风险与待确认事项，或明确指出修改意见且已落实。

### 8. 生成文档并交接

按 [TEMPLATE.md](./TEMPLATE.md) 生成 `FEASIBILITY_REVIEW.md`，落到项目工作目录 `docs/04-初步可行性分析/FEASIBILITY_REVIEW.md`；用户指定了路径就以用户为准。

第 07 节"后续阶段交接"是本阶段与后续阶段的连接点，必须写清：

- 项目目前具备哪些条件、已确定哪些约束。
- 哪些风险需要持续跟踪。
- 第五阶段需要考虑的设计约束（如平台与使用场景约束、降低操作成本的要求、不得依赖付费素材、某些功能可能缩减等——按项目实际填写）。
- 第六阶段需要深入验证的技术问题清单（每个问题写清"要验证什么"，不写验证方法和通过标准）。
- 明确不在本阶段处理的事项。

完成标准：文档落盘；CHECKLIST 全部通过；用户确认可以进入第五阶段（或有条件进入及其条件）。

## 阶段职责表（防止越界）

| 问题或工作 | 本阶段 | 后续阶段 |
| --- | --- | --- |
| 识别项目资源不足 | 负责 | 第八阶段安排任务时考虑 |
| 识别 MVP 范围过大 | 负责 | 用户确认后返回第三阶段调整需求 |
| 识别目标平台存在限制 | 初步识别 | 第六阶段验证具体技术限制 |
| 识别第三方服务依赖风险 | 负责 | 第六阶段调研具体服务 |
| 判断数据能否合法获取 | 初步识别 | 必要时进一步合规核查 |
| 研究具体数据解析方案 | 不负责 | 第六阶段 |
| 设计具体页面和交互 | 不负责 | 第五阶段 |
| 深入调研技术、框架和 SDK | 不负责 | 第六阶段 |
| 比较不同模型、数据库和技术方案 | 不负责 | 第六或第七阶段 |
| 编写 PoC、技术测试、性能测试 | 不负责 | 第六阶段 |
| 确定技术栈、设计系统架构 | 不负责 | 第七阶段 |
| 拆分开发任务、安排迭代顺序 | 不负责 | 第八阶段 |
| 重新做需求分析、重排功能优先级 | 不负责 | 第三阶段 |
| 编写代码 | 不负责 | 第九阶段 |

用户在本阶段追问属于后续阶段的内容时，记为 `deferred` 并说明为什么现在不定；只有用户明确要求切换阶段或调用其他技能时，才离开本阶段。

## 用户沟通规则

- 每轮 2–4 个问题，说明为什么问；用户回答"未知"就记 `pending`，不逼答。
- 用户的新回答与此前文档矛盾时，指出差异，请其确认以哪条为准。
- AI 给出的估算和建议必须标明是 AI 的判断，与用户确认的信息分开呈现。
- 用户要求直接给结论时，可以给推荐，但必须标明这是建议，状态不变。
- 不制造风险凑数：没有明显风险就说没有；不适用就说为什么。

## 交付物

- `FEASIBILITY_REVIEW.md`：按 [TEMPLATE.md](./TEMPLATE.md) 生成，是本阶段唯一的核心文档，不再拆分其他文档。
- 文档同时包含：可行性分析、风险清单、关键假设与待确认事项、可行性结论、阶段交接信息。
- 文档必须自包含：脱离本对话也能被第五、第六阶段直接读懂；问题编号只做索引，引用处写出结论本身。

## 阶段退出条件

同时满足以下条件才能宣告完成：

- 六个可行性维度均已评估，不适用项有说明。
- 重大风险已被识别并按统一结构记录，组合风险已分析。
- 关键假设与未知信息已区分，没有把推测写成已确认事实。
- 需要第六阶段验证的技术问题已登记，但尚未展开验证。
- 可行性结论明确（四档之一），用户已审查并确认重要结论。
- 需要用户决策的问题已提出并得到处理（决策、暂缓或记为待确认）。
- 第 07 节交接信息完整。
- CHECKLIST 全部通过，或对"不适用"项有说明。
- 用户明确确认"可以进入第五阶段"（或有条件进入及其条件）。

任一条件不满足，继续对应步骤，不宣告完成。
