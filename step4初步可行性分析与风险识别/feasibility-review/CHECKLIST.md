# 初步可行性分析阶段完成清单（CHECKLIST）

> 逐项检查 `FEASIBILITY_REVIEW.md` 与本阶段工作过程。全部通过（或对"不适用"项有说明）且用户确认后，才能宣告阶段完成。
> 检查方式：对照文档逐条核对，不凭印象打勾。

## 1. 输入与基础信息

- [ ] 可用的前序文档已完整读取；缺失文档已在"文档信息"中标注"缺失"
- [ ] 核心文档（REQUIREMENTS.md、PRODUCT_BACKLOG.md）缺失时，已提示用户并获确认后才继续
- [ ] 没有凭空补全缺失的前序结论；因缺文档无法做的判断已记为待确认
- [ ] 第 01 节摘要信息每条都有来源和状态；与需求基线冲突的初始想法已按需求基线处理

## 2. 信息收集过程

- [ ] 已从文档提取的信息没有重复询问用户
- [ ] 每个提问都说明了"为什么问"；用户回答"未知"的内容记为 `pending`，未被逼答、未被编造
- [ ] 用户不懂的概念（如持续运营费用）先解释类别再问承受意愿
- [ ] 需要用户决策的问题已摆出可选方向和 AI 建议，最终由用户决定

## 3. 可行性分析质量

- [ ] 六个维度均有结论（可行 / 有条件可行 / 存疑 / 不适用+原因），判断有依据
- [ ] 分析深度与项目特点匹配；从简的维度已注明从简原因
- [ ] 没有因为缺少信息而直接判定"不可行"；缺信息记为待确认事项
- [ ] 第 05.2 节各维度判断与第 02 节正文一致

## 4. 风险识别质量

- [ ] 每条风险 11 个字段齐全（编号、名称、类别、描述、来源、可能性、影响、等级、后果、应对建议、后续关注阶段）
- [ ] 风险来源可追溯到具体需求、约束或用户提供的信息
- [ ] 发生可能性无法判断的风险标为"暂时无法判断"，未强行打分
- [ ] 风险关系五个问题均有结论；组合风险已单独登记（或写明未识别到）
- [ ] 没有制造风险凑数；无明显风险的方面如实写"无"

## 5. 边界检查（越界扫描）

> 逐条扫描全文，出现下列内容即为越界，必须删除并改为"移交第 X 阶段"的登记。

- [ ] 没有测试、比较或评测任何具体技术、模型、服务、框架
- [ ] 没有确定技术栈、数据库、系统架构或模块划分
- [ ] 没有设计页面、交互或原型
- [ ] 没有 PoC 方案、性能测试方案或评测数据设计
- [ ] 没有"初步应对建议"写成技术解决方案（如具体缓存架构、模型路由、指定某个具体产品）
- [ ] 没有直接修改 REQUIREMENTS.md 或 PRODUCT_BACKLOG.md；范围调整只以建议形式提出，走第三阶段反馈循环
- [ ] 没有重新做需求分析或重排功能优先级

## 6. 信息可信度

- [ ] `confirmed` 条目均有用户原话或明确回答支撑
- [ ] AI 的估算全部标 `assumption` 并写明估算依据
- [ ] AI 推测的外部限制标 `pending`（待核实），未写成事实
- [ ] 全文检索无"用户已确认"+AI 推测内容混写的情况

## 7. 结论与交接

- [ ] 总体结论为四档之一（可行 / 有条件可行 / 暂不可行 / 信息不足），且有明确理由
- [ ] 判"暂不可行"的依据是已确认的项目级阻塞问题，而非缺信息或技术不确定
- [ ] 判"信息不足"时已写明缺少什么信息
- [ ] 有条件可行时已列出进入下一阶段的具体条件
- [ ] 第 06.2 节登记了移交第六阶段验证的技术问题，且只写"验证什么"，未写方法和标准
- [ ] 第 06 节交接信息完整：条件与约束、第五阶段设计约束、第六阶段验证清单、持续跟踪风险、明确不处理事项

## 8. 文档与验收

- [ ] 文档已落盘为 `FEASIBILITY_REVIEW.md`，结构符合 TEMPLATE.md
- [ ] 记录自包含：无 `Q1=A` 式引用；编号只做索引，引用处写出结论本身
- [ ] 没有相关内容的章节写"不适用"并说明了原因
- [ ] 用户已审查并明确确认：可行性结论、重要风险、待确认事项
- [ ] 用户已明确确认"可以进入第五阶段"（或有条件进入及其条件）
