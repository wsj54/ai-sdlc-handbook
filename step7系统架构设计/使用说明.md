# 第七阶段：系统架构设计 —— 使用说明

## 这个阶段是做什么的

在需求基线、产品设计和技术验证已经确认的基础上，与 AI 共同讨论、共同决策，确定**整个系统应该如何组织、如何实现、各部分如何协作**：架构风格、技术栈、模块划分、数据架构、接口设计、AI 架构、安全与部署。

一句话定位：**第六阶段负责验证关键技术能不能实现，第七阶段负责设计整个系统最终怎么构建，第八阶段负责把架构拆成开发计划。**

## 什么时候用

- 第六阶段已完成（或确认采用跳过模式），准备进入第八阶段之前。
- 用户说"做架构设计""确定技术栈""设计系统架构""做模块划分""进入第七阶段"。

## 怎么用

让 AI 调用 `architecture-design` 技能一次即可，AI 会按 phases/01→08 自动推进，只在需要用户回答提问、在方案之间做决定或验收确认时暂停。

与 AI 讨论时用户不需要提前准备技术方案——技术栈、模块划分、数据库选型本身就是讨论后确定的设计结果。用户只需要提供：

1. **前置文档**（在 `docs/` 目录下即可）：REQUIREMENTS.md、PRODUCT_DESIGN.md、FEASIBILITY_REVIEW.md、DEVELOPMENT_APPROACH.md、TECHNICAL_VALIDATION.md（第六阶段跳过时无此文件，AI 会直接用 FEASIBILITY_REVIEW.md）。
2. **自己的想法**：倾向的技术、运行方式要求（自己用还是给别人用、单机还是多端）、取舍偏好（快速交付还是长期维护）、对 AI 能力的期望（AI 要能做什么，不需要指定用什么框架）。
3. **参与决策**：AI 每个主题会给出候选方案和专业建议，用户确认、修改或提出自己的方案。可以挑战 AI 的推荐，AI 会重新分析而不是固执己见。

## 三级设计深度

| 级别 | 适用 | 产出 |
| --- | --- | --- |
| 精简 | 单用户 / 本地运行 / 技术成熟 / 无复杂 AI 工作流 | 只保留总体架构、模块、核心数据、核心接口的精简文档 |
| 标准（默认） | 个人或小团队 Web 应用，含常规 AI 调用 | 主体章节齐全，AI 章节按实际复杂度裁剪 |
| 完整 | 多用户 / 多端 / 公网服务 / 复杂 Agent 工作流 / RAG | 全部章节，ADR 增多 |

级别由 AI 读取前置文档评估后推荐、**用户确认**，不由 AI 默自决定。

## 产出

| 产物 | 位置 |
| --- | --- |
| `ARCHITECTURE.md`（唯一核心文档，含内嵌 Mermaid 架构图） | 项目 `docs/07-架构设计/` |
| 独立 ADR（仅重大决策：整体架构、技术选型、模块边界、数据设计） | 项目 `docs/07-架构设计/adr/ADR-xxx-*.md` |

ARCHITECTURE.md 不只是设计报告，更是第九阶段编码的**约束依据**：模块边界、依赖规则、被否决方案都写在文档里，防止编码阶段 AI 重复造模块、擅自换技术栈、把单体拆成微服务。

## 与其他阶段的区别（常见误区）

| 误区 | 正确做法 |
| --- | --- |
| "架构设计就是列技术栈清单" | 技术栈只是其中一章；还要回答模块怎么分、数据怎么存、接口怎么定、AI 怎么协作 |
| "顺便把代码结构、类图也画了" | 设计到"模块职责 + 数据实体 + 接口契约"粒度即可，类代码、Prompt、迁移脚本属于第九阶段 |
| "为将来可能的 1000 个用户上分布式" | 架构服务于 MVP；只保留低成本扩展点，不提前引入组件 |
| "AI 功能就得用 LangGraph / 多 Agent" | 只有简单调用就不引入框架；是否需要由 AI 功能复杂度判断，理由记录在案 |
| "第六阶段跳过了，先补做技术验证" | 直接以 FEASIBILITY_REVIEW.md 为技术依据；未验证的选型标"待验证"，不强制补第六阶段 |
| "AI 推荐什么就用什么" | 推荐是建议不是决定；用户可以挑战，最终决策权在用户 |
