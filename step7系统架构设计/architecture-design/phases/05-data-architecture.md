# 阶段 05：数据架构

本阶段目标：设计核心数据实体、字段、实体关系、数据流转和管理策略。数据结构必须能支撑业务流程，且存在业务含义的设计问题必须交给用户确认。

## 1. 核心实体设计

根据需求和模块职责列出核心实体（ENT-xxx），每个实体写主要字段和用途。字段到"业务含义明确"的粒度即可，不设计索引、不生成迁移脚本：

```text
Task（任务）
├── id
├── title
├── description
├── status
├── priority
├── due_date
└── created_at
```

实体来源检查：每个实体必须追溯到 FR-xxx（需求提到该类数据）、PG-xxx（页面要展示/操作该数据）或用户本轮确认。不为"可能的未来功能"预留实体。

## 2. 实体关系确认

关系设计是业务决策，**不要直接把关系当成既定事实**。存在业务含义的问题必须向用户确认，例如：

- 一个计划是否可以包含多个任务？一个任务是否可以属于多个计划？（一对多还是多对多）
- 一段对话是否可以关联多个任务？
- AI 修改任务后是否需要保存操作记录？
- 任务是否需要软删除（删除后可恢复）？是否需要保留历史版本？

每个确认的关系登记 REL-xxx；涉及数据保存策略的决策登记 DEC-xxx。

## 3. 数据存储归属

- 每类数据存储在哪里（本地数据库 / 文件 / 外部服务）。
- 由哪个模块创建和修改（对应 MOD-xxx，检查与模块职责一致）。
- 模块之间传递什么数据（为 phases 06 提供输入）。

## 4. 数据管理策略

按设计深度级别裁剪：

- 软删除 / 历史版本：业务需要时设计。
- 数据备份：本地项目至少约定文件级备份方式；多用户服务设计定期备份。
- 数据量与增长：预估规模，确认选定的数据库能支撑（联动第 4 章选型）。
- 敏感数据处理：涉及隐私数据的存储约束（联动第 9 章）。

## 5. 落盘

- 第 6 章"数据架构设计"：核心数据实体（ENT 清单与字段）、数据库表结构要点（表名、主键、主要字段、关系字段）、实体关系（REL 清单 + ER 图 Mermaid）、数据流转说明、数据管理策略。
- 精简级别：ER 图为建议项，实体清单和关系说明必需；本章可与第 7 章合并执行（见 SKILL.md 合并规则）。

## 完成标准

- 核心实体覆盖全部业务数据需求，每个实体可追溯到需求、页面或用户确认。
- 实体关系（一对多 / 多对多）中存在业务含义的已向用户确认，登记 REL-xxx / DEC-xxx。
- 每类数据的存储位置和归属模块明确，与第 5 章模块职责一致。
- 软删除、备份等管理策略按级别覆盖，结论已记录。
- 第 6 章与 ER 图一致。
