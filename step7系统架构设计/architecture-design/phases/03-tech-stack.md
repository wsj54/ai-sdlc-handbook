# 阶段 03：技术栈与基础设施选型

本阶段目标：在整体架构方向确定后，逐项确定各设计领域的技术方案。**不能只列技术名称清单**——每个关键选型都要有推荐理由、备选方案和取舍分析。

## 1. 选型范围

按项目实际需要选取讨论领域，不问满：

| 设计领域 | 讨论内容 | 来源约束 |
| --- | --- | --- |
| 前端 | 框架、UI 组件库 | 架构方向、用户偏好 |
| 后端 | 语言与框架 | 架构方向、用户熟悉度 |
| 数据库 | SQLite / PostgreSQL / MySQL 等 | 并发、数据规模、部署方式 |
| 缓存 | 是否需要 Redis | 是否真有缓存场景 |
| 文件存储 | 本地 / 对象存储 | 文件类型与规模 |
| AI 接入 | 模型 SDK、统一模型调用层 | 第六阶段已验证结论 |
| Agent 框架 | 直接工具调用 / 工作流框架 / Agent 框架 | AI 功能复杂度，phases 07 细化 |
| 部署 | 直接运行 / Docker / 云平台 | 运行环境与运维成本 |

## 2. 逐项选型规则

每个关键选型按以下结构讨论（多项可合并为一轮提问）：

1. **推荐方案 + 选择理由**：理由必须结合本项目条件（用户规模、部署方式、第六阶段验证结论），不是"它最流行"。
2. **备选方案 + 主要优缺点**。
3. **对开发和维护的影响**：额外依赖、部署组件、学习成本。
4. **与已确定技术的兼容性**：与架构方向、已确认选型是否冲突。

**以第六阶段结论为依据**：已标记"通过 / 有条件通过"的技术结论（TV-xxx）直接作为选型依据；"有条件通过"的把条件写入架构约束；"尚未验证"的标注"待验证"，不得当成已确定事实。

**不过度选型检查**：SQLite 已足够时不因为 PostgreSQL 更适合大型系统而推荐它；没有缓存场景就不引入 Redis；简单模型调用就不引入 Agent 框架（该项与 phases 07 联动，这里只做初步判断）。

## 3. 典型讨论示例（数据库）

结合用户实际情况提问：是否只有一个用户？是否多设备访问？是否存在并发写入？是否需要复杂查询？是否考虑未来多人使用？——如果 SQLite 已经足够，就推荐 SQLite，并把"未来转向多人服务时需重新评估"记入 ADR 的后续影响。

## 4. 讨论并确认

- 按主题分轮提问，每轮聚焦 1–3 个选型决策。
- 用户提出自己熟悉的技术时，评估其与需求和约束的匹配度；合理就采纳，有风险就说明。
- 用户授权 AI 决定的低风险选型（如某工具库），记为 `assumption` 并注明"经用户授权确定"。

## 5. 落盘

- 第 4 章"技术栈设计"：逐领域填写选定技术、版本（已知时）、选择理由、备选方案（登记相应 DEC-xxx）。
- 重大选型（数据库、后端框架、AI 接入方式、部署方式）按 SKILL.md ADR 规则判断是否生成独立 ADR 文件。
- 引入的架构约束（版本、依赖条件、成本上限）登记到第 2.4 核心技术约束。

## 完成标准

- 每个需要的选型领域都有确认结论，无空白选型。
- 每个选型有选择理由和备选方案记录，与第六阶段结论一致。
- "待验证"的选型已明确标注，未当成已确定事实。
- 重大选型 ADR 已按需生成。
- 选型结论已写入 ARCHITECTURE.md 第 4 章。
