# 阶段 01：上下文、架构准备与设计深度判定

本阶段目标：建立架构设计上下文，向用户展示准备摘要核对理解是否正确，收集 AI 无法获知的信息，判定设计深度级别（精简 / 标准 / 完整）。**这是整个 skill 的分流点。**

## 1. 读取输入文档

按 [SKILL.md「输入」](../SKILL.md) 的优先级顺序查找并读取前置文档，提取八类信息：

1. 产品核心目标和 MVP 功能范围。
2. 主要业务流程和用户操作路径。
3. 功能模块之间的业务关系（来自产品设计的信息架构和页面职责）。
4. 非功能需求和质量要求（性能、安全、可靠性、成本）。
5. 技术约束和运行环境（平台、部署、网络、预算）。
6. 已验证可行的技术方案（第六阶段技术结论、推荐技术方向）。
7. 必须遵守的架构约束（第六阶段 DC-xxx、第四阶段 RISK-xxx）。
8. 用户已有的技术偏好和设计约束（若前序文档中有记录）。

每份输入记录：路径、版本、它回答了什么。多份输入冲突时，以第三阶段确认的需求基线为准，冲突登记到待确认事项。

**第六阶段跳过模式的处理**：没有 TECHNICAL_VALIDATION.md 时，直接以 FEASIBILITY_REVIEW.md 的技术结论和风险清单作为技术依据；FEASIBILITY_REVIEW.md 中移交第六阶段但未验证的问题，在架构文档中标注"待验证"，不得当成已验证事实。不为了架构设计强制补做第六阶段。

前置文档全部缺失时不拒绝启动：询问用户是否已完成前序阶段；用户坚持继续时仅基于口述推进，并在文档"文档基本信息"中记录输入缺口。不凭空补全前序结论。

## 2. 生成架构设计准备摘要

基于八类信息生成摘要，向用户展示并请其核对——**摘要只是为后续讨论做准备，不是正式架构设计**：

```text
📋 架构设计准备摘要（请核对我的理解是否正确）

项目定位：<一段话>
核心功能：<MVP 功能清单>
主要业务流程：<核心流程>
已确定约束：<运行方式、资源、平台限制>
已验证技术：<第六阶段通过/有条件通过的技术结论，引用 TV-xxx>
必须遵守的架构约束：<引用 DC-xxx / RISK-xxx>
尚未确定：<架构讨论中需要决定的问题，如前后端是否分离、是否需要 Agent 框架、AI 对话历史如何存储>
需要重点讨论：<主题级问题清单，对应 phases 02–07>
```

用户指出理解偏差时先修正再继续；摘要本身不写入 ARCHITECTURE.md 正文（可作为讨论记录留存）。

## 3. 向用户收集信息

根据准备摘要识别信息缺口，按 [SKILL.md「向用户收集信息」](../SKILL.md) 的五个问题域（技术偏好 / 运行方式 / 取舍偏好 / AI 设计想法 / 未来预期）和提问格式逐轮收集。

- 用户已有技术方案的，先完整理解再讨论，不立即否定，也不直接照单写入文档。
- 用户只说明 AI 希望具备的能力，是否需要 Agent 框架、Function Calling 由后续 phases 07 讨论。
- 事实自己查：前置文档中已有的信息不重复问；用户规模、部署方式等 AI 无法获知的才问。
- 用户回答后立即更新文档骨架，再判断下一轮问什么；没有实质缺口就停止提问。

**顺序硬规则：提问轮次只用于收集信息缺口。禁止在准备摘要完成前把"选精简/标准/完整"抛给用户——用户没有被给过评估依据，无法回答。**

## 4. 设计深度判定（分流点）

**触发前提（必须全部满足才能进入本节）：**

1. 前置文档已读取，八类信息已提取。
2. 架构设计准备摘要已生成并经用户核对。
3. 影响级别判定的信息缺口（用户规模、运行方式、AI 复杂度）已收集，或已记为 `pending`。

满足前提后，按 [SKILL.md「三级设计深度」](../SKILL.md) 判定：

1. **AI 先完成评估**：对照用户规模与运行方式、AI 功能复杂度、外部集成与部署复杂度三个核心变量逐一判断。
2. **AI 给出级别推荐 + 推荐理由**，理由必须引用具体证据（用户数、运行环境、AI 功能清单、非功能要求），不能只说"项目比较简单"。
3. **向用户呈现评估结论并请求确认**。固定格式：

```text
📋 设计深度评估结论（先给评估，再请确认）
用户规模与运行方式：<单用户本地 / 多端同步 / 多用户服务等，引用来源>
AI 功能复杂度：<简单模型调用 / 工具调用 / Agent 工作流 / RAG，引用 FR-xxx>
外部集成与部署复杂度：<外部服务、部署方式>
➡️ 推荐级别：<精简 / 标准 / 完整>
推荐理由：<引用具体需求与约束>
影响：<选不同级别分别意味着哪些章节保留/裁剪、讨论轮次多少>
（用户确认后登记为 DEC-001；用户有异议时按用户意见调整并记录）
```

4. **由用户确认**级别。级别决定文档章节取舍和后续讨论深度，必须用户拍板，但拍板的前提是 AI 已给出完整评估。

## 落盘要求

- 创建 `docs/07-架构设计/ARCHITECTURE.md` 骨架（见 [TEMPLATE.md](../TEMPLATE.md)），填写：文档基本信息（含设计深度字段）、架构设计概述（项目简介、设计目标、设计原则、核心技术约束——从需求与第六阶段约束提取）。
- 创建 `docs/07-架构设计/adr/` 目录说明（按需，见 SKILL.md ADR 规则）。
- 级别确认后登记 DEC-001。

## 完成标准

- 前置文档已读取，八类信息已提取，输入缺口已记录。
- 架构设计准备摘要已经用户核对。
- 五类用户信息已收集或记为 `pending`，不存在把设计结果当问题冷抛给用户的情况。
- 设计深度已判定并由用户确认，登记为 DEC-001。
- 文档骨架已落盘。
