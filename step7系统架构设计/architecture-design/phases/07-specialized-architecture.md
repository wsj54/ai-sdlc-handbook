# 阶段 07：AI 专项架构与安全、部署、可靠性设计

本阶段目标：AI 架构单独讨论（不是把模型 API 往架构图里一放了事），并按设计深度级别覆盖安全、部署、可靠性设计。

## A. AI 系统架构（项目含 AI 功能时）

### 1. 从能力需求出发，不从框架出发

用户在 phases/01 说明的是 AI 希望具备的能力。逐项判断需要什么组件，**不要默认每个 AI 项目都需要 Agent 框架、多 Agent、向量数据库和 RAG**：

| AI 设计领域 | 判断问题 | 结论处理 |
| --- | --- | --- |
| 模型调用层 | 如何统一调用？是否支持切换模型？ | 直接 SDK 或统一调用层（联动第 4 章选型） |
| Prompt 管理 | Prompt 如何组织、维护？ | 集中文件管理即可起步；不提前写每个 Prompt |
| 工具调用 | AI 可调用哪些业务工具？如何限制权限？ | 工具清单 + 权限边界，联动 MOD-xxx |
| Agent 工作流 | 是否有多步骤任务执行、状态管理？ | 只是简单模型调用 + 工具调用时，不引入框架 |
| 多 Agent | 是否真的需要多个 Agent？ | 默认不需要；有真实分工需求才设计 |
| RAG | 是否需要知识检索？知识如何更新？ | 检索需求简单时用关键词 / 全文检索，不默认上向量库 |
| 记忆机制 | 是否保存长期记忆和对话上下文？ | 上下文窗口策略 + 持久化范围 |
| 人工介入 | 哪些 AI 操作必须由用户确认？ | 只读操作可自动执行；写操作按风险分级（用户确认项登记 DEC-xxx） |
| 异常处理 | 模型超时、工具失败、输出格式错误怎么办？ | 重试 / 降级 / 向用户展示错误的规则 |
| AI 评估 | 如何判断输出和工具执行是否正确？ | 简单项目约定人工检查点即可 |

判断一个项目只需要简单模型调用服务还是需要工作流框架的核心问题：是否存在多步骤规划、状态管理、人工审批的复杂任务链。没有就不引入框架。

### 2. AI 异常与执行记录

- 模型调用失败（超时、限流、格式错误）的处理方式。
- AI 执行过程的记录方式（对话记录、操作日志），需要追溯的登记数据实体。

### 3. 落盘

- 第 8 章"AI 系统架构"：总体结构、模型调用设计、Prompt 管理方式、工具调用设计、Agent / 工作流（如需要）、RAG / 记忆（如需要）、异常处理、评估机制。
- AI 工作流复杂时绘制 AI 工作流图（Mermaid）。
- "是否引入 Agent 框架"这类决策登记 DEC-xxx，写清判断依据；被否决的框架方案保留记录。

## B. 安全与权限设计

按级别裁剪——没有用户账号体系的本地单用户项目不需要复杂权限架构：

- 身份认证：是否需要登录、用什么方式（多用户 / 公网服务必需；单用户本地可约定简单访问控制或明确"无认证 + 理由"）。
- 权限控制：角色与数据隔离范围（多用户必需）。
- 数据安全：敏感数据存储、密钥管理（模型 API Key 不硬编码）。
- 外部接口安全：公网暴露面、输入校验。

## C. 部署架构

- 运行环境：操作系统、运行方式（直接运行 / Docker）、是否公网。
- 部署组件清单：实际需要部署的组件（应用、数据库、反向代理……只列真实存在的）。
- 配置与环境变量：配置项清单和注入方式（如 .env）。
- 精简级别：只写运行环境和启动方式；完整级别：部署架构图必需。

## D. 异常处理与可靠性

- 系统异常处理：统一异常捕获与用户提示策略。
- 外部服务异常：模型 / 第三方 API 失败时的降级和提示。
- 日志：记录什么、写到哪里、AI 编码时如何使用日志排查问题。
- 数据备份与恢复：联动第 6 章数据管理策略。

## E. 扩展性设计

只考虑 phases/01 收集到的已明确近期规划（E 类信息）和低成本扩展点：

- 已知扩展需求：逐条列出（如未来多端、开放 API）及其对当前设计的影响。
- 可扩展设计：为已明确需求保留的扩展点（如模型调用层支持多服务商）。
- 暂不实现的能力：明确列出并说明为什么不提前做——防止第九阶段 AI 自行"顺手实现"。

## 完成标准

- AI 功能逐项有设计结论，未引入不必要的框架 / 多 Agent / RAG / 向量库；判断依据已记录。
- AI 写操作的人工确认边界已经用户确认。
- 安全、部署、异常处理按级别覆盖，"不适用"项有理由。
- 扩展性设计只覆盖已明确的近期规划，"暂不实现"清单已明确。
- 各节与第 4、5、6、7 章的选型、数据、接口一致。
