# 阶段 02：整体架构方向

本阶段目标：确定系统整体架构风格。这是第一个正式设计讨论环节，后续所有模块划分和技术选型都建立在它之上。

## 1. 说明已知条件

从准备摘要中提取影响架构方向的条件：

- 运行方式：Web / 桌面 / 移动 / 多端；本地 / 公网。
- 用户规模：单用户 / 少数用户 / 多用户服务。
- 是否需要跨设备同步、实时协作。
- 第六阶段已验证的技术方向（引用 TV-xxx）和架构约束（引用 DC-xxx）。
- 用户在 phases/01 表达的架构偏好。

## 2. 提出候选架构方向

根据项目特点提出一到几个合理的架构方向，**数量由项目实际决定，不固定三选一**。常见候选及适用性：

| 方向 | 特点 | 适用 | 代价 |
| --- | --- | --- | --- |
| 前后端一体化 | 前后端由一个应用统一组织，部署维护简单 | 规模小、功能明确、追求快速交付 | 前后端职责需要额外规范 |
| 前后端分离的单体 | 前端负责页面交互，后端统一负责业务、数据和 AI，API 通信 | 需要 API 复用（多端）、前后端独立演进 | 需要定义接口契约 |
| 多服务拆分 | 系统拆为多个独立部署的服务 | 多团队、独立扩展需求真实存在 | 开发部署维护成本高，个人项目通常过于复杂 |

每个候选方案必须说明：为什么适合或不适合当前项目、开发和部署复杂度、对后续功能扩展的影响、明显缺点、是否存在更简单的实现方式。

**反模式检查**：只有一个人使用的本地软件，不要为了"未来可能的 1000 个用户"推荐分布式；反过来，确实需要多端同步或公网多用户的项目，也不要为了省事推荐无法支撑需求的结构。

## 3. 讨论并确认

按 [SKILL.md「讨论模式」](../SKILL.md) 推进：说明已知条件 → 设计问题（整体采用什么架构风格）→ 候选方案 → AI 专业建议 → 邀请用户讨论。

- 用户表达自己的想法时，先理解再分析；用户方案更合理就采纳，存在明显问题就说明风险并给替代，最终用户拍板。
- 用户有强烈偏好但与需求存在张力的（如坚持单体但需要多端同步），如实说明影响后由用户决定，不替用户否决。

## 4. 落盘

- 第 3 章"架构风格"：确认的架构方向、选择理由、被否决方案及理由（登记 DEC-002）。
- 系统上下文图（Mermaid）：系统与外部用户、外部服务的关系。
- 待确认事项同步更新。
