# 开发模型选择与开发流程规划

把用户的原始需求，转化成一份**可执行的开发方式约定**：这个项目应该采用什么开发模型，后续分哪些阶段，每个阶段怎么和 AI 协作、交付什么、满足什么条件才能进入下一阶段。

本阶段回答的是：

- 这个项目属于什么类型，规模、风险和质量要求如何？
- 根据这些特征，主开发模型是什么？需要哪些辅助模型或工程实践？
- 哪些传统阶段必须完整执行，哪些可以合并、简化或省略？
- 后续开发分成哪些阶段？每个阶段的输入、工作内容、交付物、门禁和回流条件是什么？
- AI 和人分别负责什么？任务拆到多大？一次开发循环怎么走？
- 怎样验证成果，怎样管理上下文、版本和风险？

本阶段不回答：

- 产品具体有哪些功能、功能规则是什么；
- MVP 范围、功能优先级、版本排期；
- 技术栈、框架、数据库、部署平台等选型；
- 具体的界面设计和接口设计。

这些内容即使被提到，也只记录为 `deferred`，移交后续阶段。

## 输入

优先读取以下输入，按顺序查找：

1. 用户明确指定的需求文档或路径；
2. `docs/01-原始需求/INITIAL_REQUIREMENTS.md`；
3. `docs/01-原始需求/RAW_REQUIREMENTS_BRIEF.md`；
4. 项目根目录下的需求、说明、笔记类 Markdown；
5. 用户在对话中直接给出的需求描述。

同时读取项目现状，用于减少提问：

- `README.md`、`AGENTS.md`、`CLAUDE.md` 等项目说明；
- 依赖清单（`package.json`、`pyproject.toml`、`requirements.txt`、`go.mod` 等）；
- 目录结构、已有源码、测试目录、CI 配置、部署配置；
- Git 历史（如果可用）。

找不到 `INITIAL_REQUIREMENTS.md` 时，不拒绝启动。先用对话补齐最小信息：想解决什么问题、给谁用、第一版大概做什么、已知限制。缺少的内容标 `assumption` 或 `deferred`，不虚构。

## 输出

默认输出：`docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md`。

用户指定了其他路径时以用户为准。文档结构见 [TEMPLATE.md](./TEMPLATE.md)，宣告完成前必须通过 [CHECKLIST.md](./CHECKLIST.md)。

## 唯一入口与自动推进

用户只需要调用本技能一次。读到本文件后，按下面的顺序自动加载并执行阶段文件：

1. [phases/01-diagnosis.md](./phases/01-diagnosis.md)
2. [phases/02-interview.md](./phases/02-interview.md)
3. [phases/03-model-selection.md](./phases/03-model-selection.md)
4. [phases/04-process-design.md](./phases/04-process-design.md)
5. [phases/05-document-review.md](./phases/05-document-review.md)

规则：

- 每个阶段完成后，直接进入下一个阶段，**不要要求用户再次调用技能**。
- 只在三种情况下暂停：需要用户回答提问轮次、需要用户在方案之间做决定、阶段验收或修订确认。
- 上一阶段的产物就是下一阶段的输入；阶段之间通过 `DEVELOPMENT_APPROACH.md` 和对话中的决策记录衔接，不靠用户复述。
- 如果某个阶段判断为“不适用”（例如没有高风险项，不需要 PoC），在文档中写明原因并跳过，不要空转。

## 五个阶段

| 阶段 | 目标 | 主要动作 | 主要产物 | 何时暂停 |
| --- | --- | --- | --- | --- |
| 01 诊断 | 建立项目画像和信息缺口 | 读输入、查项目、八维诊断、列缺口 | 诊断快照、缺口清单、文档骨架 | 读完后进入 02 |
| 02 访谈 | 补齐影响模型与流程的信息 | 分轮提问、确认 AI 环境、记录决策 | 决策记录、约束确认 | 每轮提问后等待回答 |
| 03 选型 | 选定主模型、辅助实践和裁剪方式 | 对比候选、判定、说明理由、定切换条件 | 第 04 节 | 需要用户选择时暂停 |
| 04 流程 | 设计项目专属阶段路线 | 阶段裁剪、门禁、分工、并行、回流 | 第 05–07 节 | 需要用户确认关键取舍时暂停 |
| 05 审查 | 生成并验收文档 | 填模板、跑检查清单、提交审核、处理修订 | 完整 `DEVELOPMENT_APPROACH.md` | 用户验收时暂停 |

## 全流程必须遵守的规则

### 事实自己查，决策问用户

- 能从文件、目录、依赖、Git、配置中确认的事实，自己查，不问用户。
- 需要用户判断的内容（目标、约束、偏好、可投入资源、风险承受度）必须问用户，不能替用户决定。
- 查不到又必须知道的事实，明确说“这一点我无法从项目中确认”，再问。

### 分轮访谈，不机械问完所有维度

- 先建立“当前最阻塞的问题”清单，每轮只问 2–4 个。
- 一个问题只处理一个决策点，不把多个问题揉在一起。
- 每个问题都要说明为什么问、有哪些可选答案、推荐哪一个、不同回答会改变什么。
- 问完一轮就停，等待回答；不要连续抛出多轮问题。
- 访谈维度只是扫描表，不是必答清单。项目不涉及的维度写“不适用”并说明原因。

### 信息状态

文档中的信息只使用五种状态：

| 状态 | 含义 |
| --- | --- |
| `confirmed` | 用户明确确认，或文件/配置中有明确证据 |
| `pending` | 存在歧义，需要用户回答 |
| `conflict` | 与已确认信息矛盾，尚未解决 |
| `assumption` | 用户暂不回答，但为推进规划暂时采用 |
| `deferred` | 当前阶段不需要确定，移交后续阶段 |

规则：

- AI 的推荐只能进入 `assumption`，不能写成 `confirmed`。
- 用户只回“按推荐”时，把推荐内容本身写进结论，不能只写“按推荐”。
- 用户回答与之前的结论矛盾时，先指出差异，请其确认以哪条为准。
- 一个条目只保留一个状态；冲突和歧义同时存在时，先记 `conflict`。

### 记录自包含

- 文档要能被另一个对话或另一个人直接读懂。
- 代号只做索引，不承载含义。写“用户选择：主模型采用增量迭代，因为需求会在试用后变化”，不要写“Q3=B”。
- 每个决策记录都要有：完整问题、可选答案及含义、用户选择、结论、影响章节。
- 不把“按推荐”“都同意”“其余照旧”当成结论。

### 不过度设计

- 流程复杂度必须匹配项目规模、风险和用户能力。
- 个人自用的小工具，不建立重型项目管理体系，不为每个小功能写完整设计文档。
- 只有当风险、团队规模或质量要求真正需要时，才引入原型、PoC、螺旋验证、V 模型追踪、CI/CD、代码审查等实践。
- 每个额外流程都要能回答：“不加它会出什么问题？”

### 阶段边界

| 本阶段做 | 本阶段不做 |
| --- | --- |
| 判断项目类型、规模、风险和质量要求 | 定义产品功能和功能规则 |
| 选择开发模型和辅助实践 | 决定 MVP 和功能优先级 |
| 裁剪开发阶段，定义门禁和交付物 | 制定具体版本排期 |
| 设计 AI 与人的协作方式 | 选择技术栈、框架、数据库 |
| 定义质量保障和验证方式 | 编写详细设计文档 |
| 识别启动前必须补齐的信息 | 直接开始编码 |

用户在本阶段追问功能、优先级或技术选型时，记录为 `deferred`，说明为什么现在不定，并指出应由哪个后续阶段处理。

## 文档落盘与更新节奏

1. 阶段 01 结束时，创建 `DEVELOPMENT_APPROACH.md` 骨架，填写文档信息、输入来源和诊断快照。
2. 阶段 02 每轮回答后，立即更新第 03 节决策记录、第 02 节诊断和相关假设。
3. 阶段 03、04 每确定一个模型或阶段安排，就更新对应章节，不攒到最后一次性写。
4. 阶段 05 补齐所有章节，运行检查清单，处理自检失败项。

文档中的状态、结论和正文必须一致。改了结论，要同步改受影响的诊断、假设、风险和路线图。

## 修订模式

用户读完后提出修改时，不重新生成整份文档，按下面流程处理：

1. 读取最新版 `DEVELOPMENT_APPROACH.md`。
2. 把每个修改点登记为 `CH-001`、`CH-002`……
3. 评估修改是否与诊断、模型理由、阶段门禁、项目约束一致；是否属于过度设计或越界到功能/技术选型。
4. 每轮挑 2–4 个最需要决定的修改点，说明影响和可选处理方式，由用户确认。
5. 只改受影响章节，同步状态、假设、风险和 mermaid 路线图。
6. 在文末追加修订记录，保留原描述，不覆盖历史。
7. 重新运行 [CHECKLIST.md](./CHECKLIST.md)，给用户一份变动摘要。

修订时同样遵守“不照单执行、不替用户否决、不静默改结论”。

## 完成条件

同时满足以下条件才能宣告本阶段完成：

- 项目诊断的每个维度都有证据或明确的未知项。
- 影响模型选择和流程设计的信息缺口已解决，或明确标为 `assumption` / `deferred`。
- 主开发模型、辅助实践、流程裁剪、质量保障和切换条件都已写明理由。
- 开发路线包含阶段顺序、每阶段交付物、门禁、AI/人分工、并行关系和回流条件。
- mermaid 路线图能正确渲染，且与阶段表一致。
- AI 协作契约包含任务粒度、单次循环、人工确认点、上下文/版本管理、测试与失败处理。
- 文档中没有越界到功能规则、MVP、优先级、技术选型或排期。
- [CHECKLIST.md](./CHECKLIST.md) 全部通过，或对“不适用”项有说明。
- 用户明确确认这份开发流程规划。

任一条件不满足，继续对应阶段，不宣告完成。
