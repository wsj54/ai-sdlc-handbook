# 开发模型与开发流程规划检查清单

在宣告「开发模型选择与开发流程规划」阶段完成前逐项检查。

判定规则：

- **通过**：有明确证据，能指向 `DEVELOPMENT_APPROACH.md` 的具体章节或条目。
- **不适用**：本项目确实没有该项内容，并在文档中写明原因。
- **失败**：任一项既没有证据，也没有说明不适用。

出现失败项时，回到对应阶段修正，不宣告阶段完成。

## 1. 输入与诊断

- [ ] 已读取用户指定的需求文档，或已找到 `INITIAL_REQUIREMENTS.md` / `RAW_REQUIREMENTS_BRIEF.md`。
- [ ] 如果找不到需求文档，已通过对话补齐最小信息，没有因此拒绝启动。
- [ ] 输入清单完整，关键结论能追溯到具体来源。
- [ ] 多份输入冲突时已登记，没有静默选择其中一份。
- [ ] 项目现状（代码、依赖、测试、Git、CI、部署）已读取，用于减少提问。
- [ ] 八个诊断维度都有判断、证据或明确的未知项。
- [ ] 诊断没有越界到功能规则、MVP、优先级或技术选型。
- [ ] AI 开发环境的能力和限制已确认，并写明对流程的影响。

## 2. 访谈与信息状态

- [ ] 只问了影响模型或流程的问题，没有机械问完所有维度。
- [ ] 每轮 2–4 个问题，问完一轮就停，没有连续抛问。
- [ ] 每个问题都有“为什么问、可选答案及含义、推荐、影响”。
- [ ] 能通过文件确认的事实没有拿去问用户。
- [ ] 阻塞模型选择的信息缺口已解决，或明确标为 `assumption` / `deferred`。
- [ ] 阻塞流程设计的信息缺口已解决，或明确标为 `assumption` / `deferred`。
- [ ] 用户只回“按推荐”时，文档写的是推荐内容本身，不是“按推荐”。
- [ ] 用户只回字母选项时，文档先还原了选项含义，再写结论。
- [ ] 用户回答前后矛盾时，已指出差异并请其确认，未静默采用后一条。
- [ ] 只使用五种状态，且每条只有一个状态。
- [ ] AI 的推荐或推测没有被写成 `confirmed`。

## 3. 开发模型选择

- [ ] 比较了至少两个候选模型，而不是直接给出一个结论。
- [ ] 主开发模型明确，并说明它决定什么、不决定什么。
- [ ] 主模型至少给出两条与项目诊断对应的适合理由。
- [ ] 写明了主模型的代价和维护成本。
- [ ] 写明了主模型的具体形态（迭代节奏、交付内容、评审方式、需求变化如何进入下一轮）。
- [ ] 辅助模型/实践按需选择，没有为了完整而堆砌。
- [ ] 不适用的辅助实践写明了原因。
- [ ] 流程裁剪具体到阶段，没有“视情况而定”的空话。
- [ ] 质量保障包含验证层次、测试策略、评审和发布门禁。
- [ ] 写明了不采用的方案及原因。
- [ ] 写明了模型切换条件和决策人。
- [ ] 没有出现“只建议敏捷开发，但不说明接下来怎么做”的空泛结论。

## 4. 开发流程设计

- [ ] 阶段顺序清楚，与主开发模型一致。
- [ ] 每个保留的阶段都有目标、输入、工作内容、AI/人分工、交付物、门禁、并行和回流条件。
- [ ] 每个阶段的门禁都是可观察的条件，不是“感觉可以了”。
- [ ] 阶段表、mermaid 路线图和阶段明细三者一致。
- [ ] mermaid 图能正确渲染，节点名称与阶段表一致。
- [ ] 裁剪掉的阶段在图中已移除或标注“按需”，没有留下空节点。
- [ ] 写清楚了哪些工作可以并行，前提是什么；哪些必须串行。
- [ ] 写清楚了反馈与回流：出现什么情况回到哪个阶段。
- [ ] 阶段数量与项目规模匹配，没有对个人小工具套用重型流程。
- [ ] 没有把功能清单、MVP 或版本排期写进阶段路线。

## 5. AI 协作契约

- [ ] 任务粒度有明确规则，能判断一个任务是否过大。
- [ ] 任务拆分方式与项目形态匹配（垂直切片 / 按可见行为 / 其他）。
- [ ] 单次开发循环包含：读取上下文、计划、实现、验证、汇报证据、人工验收、提交。
- [ ] 写清楚了哪些节点必须由人确认。
- [ ] 写清楚了上下文载体（项目指令、需求、架构、任务、决策记录）。
- [ ] 写清楚了 Git 使用方式、提交粒度和回滚准备。
- [ ] 写清楚了自动化测试范围、人工验证范围和回归时机。
- [ ] 写清楚了如何确认 AI 生成的测试真的验证了需求。
- [ ] 写清楚了连续失败、测试失败、需求不清、设计不成立、发布失败时的处理方式。
- [ ] 完成定义（DoD）可观察、可验收。

## 6. 质量、风险与假设

- [ ] 验证矩阵覆盖技术验证、需求验证和真实使用验证。
- [ ] 质量目标有衡量方式，不是“保证高质量”。
- [ ] 需要 V 模型追踪时，写明了追踪粒度和维护方式；不需要时说明了理由。
- [ ] 评审与发布门禁写清楚了谁负责、何时触发、通过标准。
- [ ] 涉及敏感数据、权限、密钥、外部服务时，已写明流程要求。
- [ ] 风险有触发条件、影响和当前处理。
- [ ] 暂定假设有采用原因、影响和确认时间。
- [ ] 暂缓事项写明了原因和移交阶段。
- [ ] 没有把未验证的猜测写成确定结论。

## 7. 阶段边界

- [ ] 文档没有定义产品功能或功能规则。
- [ ] 文档没有决定 MVP 范围或功能优先级。
- [ ] 文档没有选择技术栈、框架、数据库或部署平台。
- [ ] 文档没有制定具体版本排期。
- [ ] 文档没有编写详细界面设计或接口设计。
- [ ] 用户追问上述内容时，已记录为 `deferred` 并说明移交阶段。
- [ ] 文档没有开始编码或替后续阶段做实现决策。

## 8. 文档自包含与一致性

- [ ] 全文搜索 `Q\d`：没有 `Q1=A`、`Q2=B` 这类无法自解释的引用。
- [ ] 每条决策记录都有完整问题、选项含义、用户选择和结论。
- [ ] 没有把“按推荐”“都同意”“其余照旧”当成结论。
- [ ] 文档信息、日期、版本、阶段状态已填写。
- [ ] 状态、结论和正文一致；改了结论，相关章节已同步。
- [ ] 阶段表、mermaid、阶段明细和 AI 协作契约没有互相矛盾。
- [ ] 把文档单独交给另一个对话，也能理解每个决定和后续做法。
- [ ] 不适用章节都写明了原因。

## 9. 交付与验收

- [ ] `DEVELOPMENT_APPROACH.md` 已按模板生成，并放在约定路径。
- [ ] 已向用户提交项目画像、推荐模型、流程裁剪、阶段路线、AI 协作方式、质量保障、假设与风险。
- [ ] 已明确告诉用户：启动前需要准备或决定什么。
- [ ] 已说明下一步从哪个阶段开始，以及本文件不替代需求分析和技术设计。
- [ ] 用户已明确确认当前版本。
- [ ] 如有修订，修订记录已追加，受影响章节已同步。
- [ ] 阶段完成后没有擅自开始编码。

## 退出判定

- 全部通过，或所有不适用项都有说明：阶段完成，可以交接。
- 任一项失败：回到对应阶段修正，不得宣告完成。
