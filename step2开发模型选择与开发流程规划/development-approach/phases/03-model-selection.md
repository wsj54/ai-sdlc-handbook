# 阶段 03：开发模型选择

## 目标

根据项目诊断和访谈结论，选出**主开发模型**、**辅助模型或工程实践**、**流程裁剪方式**和**质量保障方式**，并写清楚为什么适合、不采用什么、什么情况下应该换。

本阶段的产物必须能直接指导阶段 04 的流程设计，不能只停留在“建议采用敏捷开发”。

## 候选模型

按需比较下列模型，不必全部使用，也不必强行给每个模型写一段评价。

| 模型/实践 | 核心特征 | 更适合 | 不太适合 |
| --- | --- | --- | --- |
| 瀑布 / 阶段式 | 阶段顺序推进，前一阶段完成才进入下一阶段；变更走正式流程 | 需求稳定、范围固定、验收标准明确、外部约束强 | 需求变化快、需要早期反馈 |
| 增量迭代 | 按可运行的功能增量分批交付，每个增量都经过验证 | 需求中等明确、可以分期交付、希望尽早使用 | 完全无法拆分、必须一次性交付 |
| 敏捷 / Scrum | 固定周期、待办列表、评审与回顾、持续调整范围 | 需求变化快、有团队协作、需要频繁反馈 | 单人小工具、需求非常稳定且无需频繁评审 |
| 看板 / 持续流动 | 限制在制品、按优先级持续交付，不设固定迭代 | 维护型项目、持续小改动、响应式工作 | 需要明确里程碑和阶段验收的项目 |
| 原型模型 | 先做可丢弃或可演进的原型，验证需求、交互或可行性 | 界面/交互不确定、需求说不清、需要让用户先看到 | 需求已明确、直接实现更便宜 |
| 螺旋模型 | 风险驱动，每一圈都包含目标、风险分析、工程实现和评审 | 高技术风险、关键决策需要反复验证 | 低风险、小规模、流程承受不了反复评审 |
| V 模型（验证思想） | 需求、设计、实现、测试逐层对应，强调验证与确认 | 质量/安全/合规要求高、需要可追溯 | 探索型项目、需求频繁变化 |
| AI 原生迭代开发 | 以规范为上下文，AI 实现，人决策与验收；小步垂直切片，闭环验证 | 个人或小团队、AI 可读写项目、需要快速迭代 | 完全无法运行 AI 工具、强合规且必须人工逐行实现 |
| DevOps / 持续交付 | 自动化构建、测试、部署、监控和回滚 | 需要频繁发布、线上运行、长期维护 | 一次性脚本、本地自用且无部署需求 |
| PoC / Spike | 限时技术验证，不进入产品代码，目的是回答一个关键问题 | 关键技术点没验证过、方案存在重大不确定性 | 风险已明确、直接实现成本更低 |

## 判定规则

先看项目特征，再看组合。下面是倾向，不是公式。

| 项目特征 | 倾向 |
| --- | --- |
| 需求稳定、范围固定、验收明确、变更少 | 瀑布/阶段式为主；用 V 模型思想建立需求-测试对应关系 |
| 需求中等明确、可以分期交付 | 增量迭代为主；按垂直切片交付 |
| 需求变化快、需要真实反馈 | 迭代/敏捷为主；短周期评审，范围可调整 |
| 界面、交互或使用方式不确定 | 原型模型作为辅助，先验证体验，再进入实现 |
| 关键技术点没验证过（Agent、算法、模型质量、第三方 API、性能、安全） | 螺旋/PoC 作为辅助，先做限时验证，再决定是否进入正式开发 |
| 质量、安全、合规、可追溯要求高 | V 模型思想 + 独立验证 + 严格门禁；必要时阶段式 |
| 个人开发，AI 能读写项目并运行测试 | AI 原生增量迭代 + 垂直切片 + 轻量门禁 |
| 多人并行，模块之间有接口 | 增量迭代 + 接口契约 + 代码审查 + CI；必要时看板 |
| 维护型、持续小改 | 看板/持续流动 + DevOps 实践 |
| 一次性脚本或本地自用工具 | 简化流程，保留版本管理和基本验证即可 |

组合原则：

- **一个主模型**：决定阶段顺序和交付节奏。
- **零到两个辅助模型/实践**：只在确实需要时加入，例如原型、PoC、V 模型追踪、DevOps。
- **质量保障是独立一层**：不要用“敏捷”代替测试、审查和验收。
- **流程裁剪必须具体**：写清楚哪些阶段完整执行、哪些合并、哪些简化、哪些省略。

## 选择时要做出的判断

### 1. 主开发模型

回答：

- 主模型是什么？
- 它决定什么：阶段顺序、交付节奏、变更方式、评审方式？
- 它不决定什么：哪些内容仍由辅助实践或质量保障负责？
- 为什么它适合这个项目？至少给出两条与诊断结果对应的理由。
- 它的代价是什么？例如需要更多评审、需要维护待办列表、需要用户频繁参与。

不要只写“建议采用敏捷开发”。要写清楚：迭代多长、每个迭代交付什么、谁评审、需求变化怎么进入下一轮。

### 2. 辅助模型与工程实践

逐项判断是否需要：

| 辅助实践 | 什么时候需要 | 在本项目中的具体用法 |
| --- | --- | --- |
| 原型 | 界面、交互、需求表达不清 | [做什么原型、验证什么问题、何时丢弃/演进] |
| PoC / Spike | 关键技术点未验证、失败会导致方案改变 | [验证什么问题、时间盒、通过/失败标准] |
| 螺旋验证 | 高风险且需要多轮风险分析 | [每一圈验证什么、谁评审] |
| V 模型追踪 | 质量/合规要求高、需要需求-测试对应 | [追踪到什么粒度、谁维护] |
| DevOps / CI/CD | 需要频繁发布、线上运行、回滚 | [自动化到哪一步、是否值得] |
| 看板 | 维护型、持续小改、并行任务多 | [看板列、在制品限制] |
| 代码审查 | 多人协作、质量要求高、AI 生成代码需要把关 | [谁审、审什么、什么变更必须审] |

不需要的实践写“不适用”，并说明为什么不需要。例如：“个人自用工具，没有线上部署，暂不引入 CI/CD；保留本地测试和 Git 即可。”

### 3. 流程裁剪

用下表说明每个阶段怎么处理：

| 阶段 | 完整执行 / 合并 / 简化 / 省略 | 理由 |
| --- | --- | --- |
| 需求基线确认 | [处理方式] | [为什么] |
| 风险验证（原型/PoC） | [处理方式] | [为什么] |
| 项目初始化 | [处理方式] | [为什么] |
| 任务分解 | [处理方式] | [为什么] |
| 迭代开发 | [处理方式] | [为什么] |
| 验证与发布 | [处理方式] | [为什么] |
| 运营与迭代 | [处理方式] | [为什么] |

裁剪规则：

- 个人自用小工具：可以合并需求基线和风险验证，简化项目初始化和发布，但不能省略版本管理和基本验证。
- 高风险项目：风险验证不能省略，必须设门禁；不能为了赶进度跳过 PoC。
- 高质量/合规项目：需求-测试追踪、独立验证、发布回滚不能省略。
- 团队项目：接口契约、代码审查、集成节奏不能省略。
- 任何项目：都不能省略“可运行的验证”和“用户验收”。

### 4. 质量保障方式

写清楚：

- 验证层次：技术验证（能运行、测试通过）、需求验证（符合需求）、真实使用验证（能完成真实任务）。
- 测试策略：自动化测试覆盖什么，哪些靠人工验收，哪些必须做回归。
- 评审方式：代码审查、设计评审、需求评审，分别由谁做、什么频率。
- 需求-测试追踪：是否需要，追踪到什么粒度。
- 发布门禁：什么条件下可以发布，什么条件下必须回滚。
- 安全与数据：是否涉及敏感数据、权限、密钥、备份，流程上如何保证。

质量保障要写成可执行的动作，不要写“保证高质量”。

### 5. 不采用的方案及原因

列出被排除的模型或实践，说明为什么不适合。例如：

- 不采用完整 Scrum：个人开发，没有团队角色和固定评审成本。
- 不采用瀑布：需求会在试用后变化，无法一次锁定范围。
- 不采用微服务/多 Agent 编排：当前规模和风险不需要，增加协调和调试成本。

这一节用于防止后续反复讨论，也帮助未来的人理解决策背景。

### 6. 模型切换条件

写清楚什么信号出现时，应该重新评估模型：

- 需求变化频率明显高于预期；
- 关键技术风险迟迟无法验证；
- 质量事故增多，现有验证不足；
- 团队规模扩大，协作成本上升；
- 交付周期失控，现有节奏无法维持；
- 模型调用成本或维护成本超出承受范围。

每个条件写“观察到什么 → 切换到哪里 → 谁来决定”。

## 写出结论

把结果写入 `DEVELOPMENT_APPROACH.md` 第 04 节：

- 4.1 候选模型对比；
- 4.2 主开发模型；
- 4.3 辅助模型与工程实践；
- 4.4 流程裁剪；
- 4.5 质量保障方式；
- 4.6 不采用的方案及原因；
- 4.7 模型切换条件。

每个结论都要能回答：“为什么是这个项目，而不是通用最佳实践？”

## 常见错误

- 只给模型名称，不给阶段安排、交付节奏和评审方式。
- 把“敏捷”当成不写文档、不做计划的理由。
- 对所有项目都加原型、PoC、V 模型、CI/CD，导致流程过重。
- 为了显得专业，堆砌模型名称，但不说明各自负责什么。
- 把技术选型写进模型选择，例如“采用敏捷 + React + PostgreSQL”。
- 把功能优先级或 MVP 范围写进本阶段。

## 完成标准

- 主模型明确，并说明它决定什么、不决定什么。
- 辅助实践按需选择，不适用的写明了原因。
- 流程裁剪具体到阶段，没有“视情况而定”的空话。
- 质量保障包含验证层次、测试策略、评审和发布门禁。
- 写明了不采用的方案及原因。
- 写明了模型切换条件。
- 结论能直接支撑阶段 04 的阶段设计。

完成后直接进入 [04-process-design.md](./04-process-design.md)。
