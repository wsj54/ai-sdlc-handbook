# 阶段 05：文档生成、自检与验收

## 目标

把前四个阶段的结论整理成一份完整、可执行、可交接的 `DEVELOPMENT_APPROACH.md`，运行检查清单，向用户说明方案和仍未确定的事项，取得明确确认。

本阶段不开始编码，也不替后续阶段做需求分析或技术设计。

## 步骤

### 1. 补齐文档

按 [TEMPLATE.md](../TEMPLATE.md) 补齐所有章节。填写时遵守：

- 每个结论都来自诊断、访谈或用户的明确确认。
- AI 的建议如果还没有被用户确认，保持 `assumption`。
- 不适用章节写“不适用”，并说明原因；不要为了填满模板编造内容。
- 阶段表、mermaid 路线图、阶段明细三者保持一致。
- 决策记录自包含：写完整问题和结论，不写 `Q1=A`。
- 功能规则、MVP、优先级、技术选型和排期不进入正文；如被提到，放入 `deferred`。

### 2. 自检

逐项运行 [CHECKLIST.md](../CHECKLIST.md)。判定规则：

- **通过**：有明确证据，能指向文档的具体章节或条目。
- **不适用**：本项目确实没有该项内容，并在文档中写明原因。
- **失败**：既没有证据，也没有说明不适用。

出现失败项时，回到对应阶段修正，不要带着失败项宣告完成。

### 3. 向用户提交摘要

提交时至少包含：

1. **项目画像**：项目类型、规模、需求成熟度、主要风险、开发资源。
2. **推荐模型**：主模型是什么，为什么适合；用了哪些辅助实践。
3. **流程裁剪**：哪些阶段完整执行，哪些合并/简化/省略。
4. **阶段路线**：按顺序列出阶段、每个阶段的门禁和主要交付物。
5. **AI 协作方式**：任务粒度、单次循环、人工确认点。
6. **质量保障**：测试、审查、验收和发布门禁。
7. **关键假设与风险**：哪些是暂定假设，哪些还需要验证。
8. **启动前需要用户准备或决定的事**。
9. **检查清单结果**：通过项、不适用项、失败项（如果有）。

然后问一个明确问题：

> 这份开发流程规划是否可以确认？确认后，后续开发按第 05 节的阶段路线执行；如果需要修改，请指出具体章节或条目。

### 4. 处理用户反馈

| 用户反应 | 处理方式 |
| --- | --- |
| 明确确认 | 记录确认日期，阶段完成 |
| 指出某处不对 | 进入修订模式，登记修改点，先评估再讨论 |
| 补充新信息 | 判断是否推翻诊断或模型结论；更新文档并重新自检 |
| 要求直接改 | 可以改，但要先说明影响；不能静默改动关联章节 |
| 暂时不确认 | 保留 `pending`，说明还差什么，不宣告完成 |

用户只回“可以”“没问题”时，记录为“用户确认当前版本”，不要扩展成对未确认内容的认可。

### 5. 修订模式

用户提出修改时，不重新生成整份文档。按下面流程：

1. 读取最新版 `DEVELOPMENT_APPROACH.md`。
2. 登记修改点为 `CH-001`、`CH-002`……
3. 评估每个修改点：
   - 是否与项目诊断一致？
   - 是否与主模型的选择理由冲突？
   - 是否破坏阶段门禁或交付链？
   - 是否属于过度设计或过度简化？
   - 是否越界到功能、优先级或技术选型？
4. 每轮挑 2–4 个最需要决定的修改点，说明影响和可选处理方式，由用户确认。
5. 只改受影响章节，同步更新：
   - 诊断表中的相关判断；
   - 决策记录和状态；
   - 假设、风险和暂缓事项；
   - 阶段表、mermaid 路线图和阶段明细。
6. 在文末追加修订记录，保留原描述，不覆盖历史。
7. 重新运行检查清单，给用户一份变动摘要。

修订原则：

- 不照单执行：明显不合理的修改先指出，给替代方案。
- 不替用户否决：最终改不改、怎么改，由用户决定。
- 不静默改结论：改了模型或阶段，要说明影响了哪些章节和假设。
- 不把修订变成重新规划：只处理被指出的问题和必要的一致性联动。

### 6. 交接

阶段完成后，说明：

- 这份文档约束的是“怎么开发”，不替代需求分析、体验设计和技术设计。
- 下一步按第 05 节的第一个阶段启动；如果需求还不成熟，先回到需求阶段。
- 后续开发中的变更，如果影响开发模型、阶段门禁或协作方式，回到本技能修订；如果只是功能或技术细节，交给对应阶段处理。
- 文档应放在项目仓库中，作为 AI 的长期上下文，而不是只留在聊天里。

## 提交前的最后检查

- 文档没有把 AI 的推荐写成用户确认。
- 文档没有 `Q1=A`、`Q2=B` 这类无法自解释的引用。
- 主模型、辅助实践、流程裁剪、质量保障都有理由。
- 阶段路线有门禁、回流和 AI/人分工。
- mermaid 能渲染，且与阶段表一致。
- 没有功能规则、MVP、优先级、技术选型或排期。
- 用户已经看到方案摘要和未决事项。

## 完成标准

- `DEVELOPMENT_APPROACH.md` 已按模板补齐。
- 检查清单全部通过，或所有不适用项都有说明。
- 用户明确确认当前版本。
- 如有修订，修订记录已追加，受影响章节已同步。
- 没有开始编码或进入后续阶段。

完成后向用户交付文档路径和摘要，结束本次技能调用。
