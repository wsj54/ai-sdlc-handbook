# 阶段 02：信息缺口访谈

## 目标

用尽可能少的轮次，补齐影响开发模型和流程设计的信息；把每个回答转成自包含的决策记录；确认 AI 开发环境的真实能力，以及哪些节点必须由人确认。

本阶段不追求把七个维度全部问完，只问“现在不定就无法继续”的问题。

## 设计树与 frontier

把待确认信息组织成一棵设计树：

```text
开发模型与开发流程
├── 项目约束
│   ├── 人员：个人 / 团队 / 是否有人协助
│   ├── 时间：周期 / 每天可投入时间 / 截止日期
│   ├── 预算：模型调用 / 服务 / 部署成本
│   └── 维护：谁来维护 / 维护多久
├── 需求稳定性
│   ├── 核心需求是否明确
│   ├── 第一版范围是否稳定
│   └── 后续变化由谁决定、变化频率
├── 技术风险
│   ├── 是否涉及 Agent / 算法 / 模型质量
│   ├── 第三方 API、数据、合规、成本
│   └── 是否有关键技术点没验证过
├── 质量与交付
│   ├── 个人自用 / 内部工具 / 正式产品
│   ├── 可用性、安全、数据、长期维护要求
│   └── 验收方式和发布频率
├── AI 开发环境
│   ├── 工具形态：IDE / CLI / 纯对话
│   ├── 项目访问、命令执行、测试运行、日志分析
│   ├── Git、浏览器、数据库、MCP、子 Agent
│   └── 成本、上下文限制、人工审核要求
└── 流程偏好
    ├── 愿意写多少文档
    ├── 迭代节奏和反馈方式
    └── 对返工、重构、发布的态度
```

**frontier（边界）**：所有前置条件已经确定、现在就能问的问题。问题的答案如果依赖本轮另一个还没回答的问题，它属于下一轮，不属于本轮。

每轮只问 frontier 上最阻塞的 2–4 个问题。用户回答后，重新计算 frontier，再问下一轮。

## 提问格式

使用下面的格式，问完一轮就停，等待回答：

```text
❓ Q1｜<能独立理解的标题>
为什么问：<它影响哪个模型判断、阶段安排或门禁>
可选答案：
A. <含义>
B. <含义>
C. <含义>
➡️ 推荐：<推荐项 + 理由>
影响：<选 A/B/C 分别会改变什么>

---

❓ Q2｜<能独立理解的标题>
为什么问：...
可选答案：
A. ...
B. ...
➡️ 推荐：...
影响：...
```

规则：

- 每个问题只处理一个决策点。
- 选项写含义，不只有字母。
- 推荐是建议，不是替用户决定。
- “影响”要具体，例如“选 A 会把发布门禁从人工验收改为自动化回归”，不要写“影响流程”。
- 问题标题要能脱离上下文独立理解。
- 不要问能通过读文件确认的事实。

## 访谈维度与问题库

下面是扫描表，不是必答清单。只问与当前项目相关、且会影响模型或流程的维度。

### 1. 开发人员情况

- 个人开发还是团队开发？是否有人协助？
- 是否有其他人会读代码、跑测试、做验收？
- 是否需要多人并行？并行的是同一模块还是不同模块？
- 如果只有一个人，是否接受“开发、测试、验收都由自己完成”？

影响：个人开发倾向更小的任务粒度和更轻的项目管理；多人并行需要接口契约、代码审查、CI 和协调机制。

### 2. 时间与资源

- 预期开发周期大概多长？是否有硬截止日期？
- 每天或每周可投入多少时间？
- 预算范围：模型调用、服务器、第三方服务、部署？
- 是一次性项目，还是需要长期维护？

影响：时间紧且范围固定，倾向阶段式/固定范围；时间弹性、需求会变，倾向增量迭代；预算紧需要控制模型调用和验证成本。

### 3. 技术能力

- 编程基础如何？主要熟悉什么语言和方向？
- 对计划使用的技术栈熟悉程度如何？
- 是否有 AI Coding 使用经验？是否看得懂 AI 生成的代码？
- 遇到问题时，更愿意自己调试，还是让 AI 自行分析修复？

影响：技术能力强、能审查代码，可以放宽 AI 自主范围；技术经验少，需要更小的任务、更明确的验收和更多人工确认点。

### 4. 需求成熟度与变化预期

- 核心需求是否明确？第一版范围是否已经确定？
- 后续需求变化的频率和来源是什么？谁决定加功能？
- 是否接受“先做一个小版本，再根据使用反馈调整”？
- 有没有“必须一次做完、不能分批”的外部约束？

影响：需求稳定、范围固定，倾向瀑布/阶段式；需求会变、需要真实反馈，倾向增量/迭代/原型。

### 5. 技术与业务风险

- 是否涉及 Agent、复杂算法、模型质量、自动决策？
- 是否依赖第三方 API、外部数据、付费服务？
- 是否处理敏感数据、权限、支付、合规？
- 有没有“如果这个技术点不成立，整个方案就要改”的风险？
- 失败时的后果是什么：只是不好用，还是会丢数据、泄露信息、产生费用？

影响：高风险点需要 PoC、原型或螺旋式验证；高风险且不可逆，需要更严格的门禁和人工确认。

### 6. 交付与质量要求

- 个人自用、内部工具，还是正式对外产品？
- 是否要求高可用、数据安全、长期维护、可追溯？
- 出问题时，用户能否接受“先手动绕过去”？
- 验收由谁做？验收标准是否明确？
- 发布频率：每天、每周、每个版本，还是一次性交付？

影响：质量要求越高，越需要 V 模型式的需求-测试追踪、独立验证、发布门禁和回滚方案。

### 7. AI 编程工具和开发环境

- 使用什么 AI Coding 工具？IDE 插件、CLI，还是纯对话？
- AI 能否直接读取和修改整个项目目录？
- 能否执行终端命令、启动服务、运行测试？
- 能否根据日志、报错和运行结果自行分析修复？
- 是否使用 Git？AI 能否查看代码变更和版本记录？
- 能否使用浏览器、数据库、MCP、子 Agent 等能力？
- 模型调用成本、上下文限制、工具权限有什么限制？
- 是否需要你手动审核每次代码变更？哪些变更必须审核？

影响见下表。

### AI 能力对流程的影响

| AI 环境能力 | 对开发流程的影响 |
| --- | --- |
| 能读写全项目、执行命令、运行测试、分析日志 | 可以设计完整闭环：分析 → 计划 → 实现 → 测试 → 修复；任务可以是一个可验证的垂直切片 |
| 能读写项目，但不能执行命令/测试 | 计划与实现分开；人负责运行测试并回传结果；任务要更小，验收证据由人提供 |
| 只能通过聊天提供代码片段 | 任务拆得更细；增加人工粘贴、运行、验证环节；必须提供明确的文件路径和上下文 |
| 没有 Git | 先补版本管理，否则回滚、审查和变更追踪不可靠 |
| 没有自动化测试 | 增加人工验收清单、冒烟测试、关键路径手测；优先补最小测试能力 |
| 有浏览器/数据库/MCP | 可以做端到端验证、数据检查、真实环境回归；但仍需独立判断，不能只看 AI 报告 |
| 成本或上下文受限 | 控制单次任务范围；把决策写进文档，减少长对话依赖；分段会话 |
| 要求人工审核每次变更 | 把审核点写进单次循环；高风险变更单独设门禁 |

### 8. 流程偏好与协作方式

- 愿意维护多少文档？是否接受用文档作为 AI 的上下文？
- 喜欢短周期频繁反馈，还是集中一段时间做完再验收？
- 对返工和重构的态度：尽量一次做对，还是允许先跑通再重构？
- 是否希望 AI 自主完成整个任务，还是每一步都先给计划？
- 是否愿意在关键节点做人工验收？

影响：文档意愿低，流程要更轻，但关键决策仍要落盘；喜欢频繁反馈，适合小步迭代；希望 AI 自主，需要更清晰的边界和验收条件。

## 回答处理

每轮回答后，按下面的方式处理：

| 用户反应 | 处理方式 | 状态 |
| --- | --- | --- |
| 明确选择某个选项 | 把选项含义写成结论，更新诊断和决策记录 | `confirmed` |
| 回答仍模糊，或产生新歧义 | 保留问题，必要时拆成新问题 | `pending` |
| 回答与已有结论矛盾 | 指出差异，请用户确认以哪条为准 | `conflict` |
| 不回答但要求继续推进 | 写明假设内容、采用原因、影响和何时确认 | `assumption` |
| 属于后续阶段 | 写明暂缓原因和移交阶段 | `deferred` |
| 只回“按推荐” | 把推荐内容本身写成结论，不写“按推荐” | `confirmed` |
| 只回“Q1 选 A” | 先复述 A 的含义，再写结论 | `confirmed` |

补充规则：

- 用户说“不知道”“还没想好”时，不逼答；转成 `assumption` 或 `deferred`。
- 用户提出新信息时，先检查是否推翻已有诊断，再更新文档。
- 用户要求直接给结论时，可以给推荐，但必须标明这是建议，不能写成用户确认。
- 用户回答“都可以”时，追问“哪个更符合你的实际情况”，或按推荐记为 `assumption`。

## 每轮更新文档

每次收到回答后立即更新 `DEVELOPMENT_APPROACH.md`：

1. 在第 03.2 节追加决策记录：完整问题、可选答案及含义、用户选择、结论、影响章节、状态。
2. 更新第 02 节诊断表中受影响的维度。
3. 更新第 08 节的假设、暂缓和风险。
4. 检查是否引入新的信息缺口；如果有，加入下一轮 frontier。
5. 检查文档中的状态与正文是否一致。

不要攒到最后一次性写；也不要只把回答留在对话里。

## 停止条件

同时满足以下条件时，结束访谈，进入阶段 03：

- 影响主模型选择的信息缺口已经解决，或明确标为 `assumption` / `deferred`。
- 影响阶段顺序、门禁和分工的信息缺口已经解决，或明确标为 `assumption` / `deferred`。
- AI 开发环境的能力和限制已经确认，足以设计任务粒度和验证方式。
- 关键风险已经识别，并知道是否需要 PoC 或原型。
- 用户没有新的、会推翻已有结论的信息。

不要求把所有维度问完。功能细节、技术选型、排期等不属于本阶段的问题，标 `deferred` 后继续。

## 完成标准

- 每个影响模型或流程的 `pending` 问题都已处理。
- 所有决策记录自包含，不依赖对话中的字母编号。
- AI 环境能力已确认，并写清楚它对任务粒度和验证方式的影响。
- 文档第 02、03、08 节与回答一致。
- 没有把 AI 推荐或推测写成用户确认。

完成后直接进入 [03-model-selection.md](./03-model-selection.md)。
