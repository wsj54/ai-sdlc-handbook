# **第八阶段：开发计划与任务拆解（Development Planning & Task Breakdown）**

我认为你提出的方向非常值得采用，而且可以让第八阶段成为整套 AI 时代个人软件开发流程中非常有特色的一环。

传统开发计划主要是将系统架构转化为开发人员可以执行的任务，然后由开发人员逐项完成。

而你现在希望实现的是：

**AI 根据前面所有设计文档，自动将系统拆解成多个相对独立的开发板块，为不同板块设计专门的 Vibe Coding 子 Agent，让它们在具备条件时并行、异步开发，最后由主 Agent 负责整合和检查。**

我建议将这一阶段重新定位为：

**AI 驱动的开发规划与多 Agent 任务编排。**

它不只是生成开发计划，还要提前解决后面编码阶段的几个关键问题：

1. 整个项目应该分成哪些开发板块？
2. 每个板块包含哪些具体开发任务？
3. 哪些任务必须先完成，哪些可以同时进行？
4. 哪些任务适合交给独立的子 Agent？
5. 不同 Agent 如何共享架构约束、协作接口和开发规范？
6. 多个 Agent 完成开发后，如何集成、测试和验收？
7. 如果当前 Vibe Coding 工具不支持多 Agent，如何退化为顺序开发？

这里我特别建议你增加一个设计原则：

**不要单纯按照前端、后端、数据库等技术层次拆分开发任务，而是优先按照业务能力和可独立交付的功能板块进行拆分，再根据依赖关系决定并行方式。**

因为多 Agent 开发的最大问题不是 Agent 数量不够，而是任务之间存在大量依赖、文件冲突和接口不一致。

## **一、首先明确：这一阶段应该完成什么？**

第八阶段不负责实际编写产品代码，而是负责把架构设计转化成一套能够交给 AI 执行的开发计划。

我建议将它分成四个核心成果：

**1. 开发板块划分**

将系统架构拆分为若干独立的开发板块，明确每个板块的功能范围和交付结果。

**2. 具体开发任务**

将每个板块拆解为 AI 能够独立理解、执行、测试和验收的小任务。

**3. 多 Agent 协作规划**

设计主 Agent、开发子 Agent、测试子 Agent 等角色，明确分工、协作边界和异步执行顺序。

**4. 开发执行路线**

确定任务依赖关系、并行开发组、集成节点、测试节点和最终交付标准。

我认为这四项缺一不可。

如果只做第一项和第二项，得到的仍然只是传统开发任务清单；增加第三项和第四项，才真正体现出 AI Agent 开发时代的工作方式。

## **二、需要参考之前的哪些文档？**

这一阶段必须以之前的设计文档为依据，不能让 AI 根据自己的理解随意拆分任务。

我建议分成五份核心输入和若干辅助输入。

### **1. 必需的前置文档**

| 文档                        | AI 主要读取什么              | 用途                |
| :------------------------ | :--------------------- | :---------------- |
| `DEVELOPMENT_APPROACH.md` | 开发模型、迭代方式、质量门禁、AI 协作规则 | 决定采用什么开发节奏和任务执行方式 |
| `REQUIREMENTS.md`         | MVP、功能需求、优先级、验收标准      | 决定开发任务的范围和优先级     |
| `PRODUCT_DESIGN.md`       | 用户流程、页面结构、交互规则         | 确定各功能板块的实际交付内容    |
| `ARCHITECTURE.md`         | 系统模块、技术栈、数据结构、接口、模块依赖  | 确定任务拆分和技术边界       |
| `FEASIBILITY_REVIEW.md`   | 风险、资源限制、平台限制           | 避免开发计划违反现实约束      |

其中 `ARCHITECTURE.md` 是本阶段最直接的技术依据。

### **2. 条件适用的辅助文档**

| 文档                            | 用途                        |
| :---------------------------- | :------------------------ |
| `TECHNICAL_VALIDATION.md`     | 参考已经验证的技术方案和仍然存在的风险       |
| `PRODUCT_BACKLOG.md`          | 获取功能优先级和未来迭代需求            |
| `REQUIREMENT_TRACEABILITY.md` | 将需求与开发任务、测试验收关联起来         |
| `REQUIREMENT_REVIEW.md`       | 检查尚未解决的需求争议               |
| ADR 架构决策记录                    | 防止子 Agent 擅自改变已经确认的架构决策   |
| PoC 代码                        | 复用已经验证的技术实现，避免重复研究        |
| 现有代码仓库                        | 非全新项目时，判断当前开发进度、代码结构和已有实现 |

这里还有一个比较重要的地方：

**AI 必须检查所有文档之间是否存在矛盾。**

例如：

`REQUIREMENTS.md` 要求支持模型切换，但是 `ARCHITECTURE.md` 只设计了固定模型调用方式。

这种情况不应该直接进入任务拆解，而应该先报告问题，和用户确认是否需要修订架构。

### **3. 前置文档之间的作用关系**

**开发目标**

`REQUIREMENTS.md` + `PRODUCT_DESIGN.md`

决定需要开发哪些能力，以及这些能力应该如何表现。

**技术实现依据**

`ARCHITECTURE.md` + ADR

决定每个开发板块应该按照什么架构和技术约束实现。

**开发执行规则**

`DEVELOPMENT_APPROACH.md`

决定开发节奏、质量标准和 AI 协作方式。

**风险与限制**

`FEASIBILITY_REVIEW.md` + `TECHNICAL_VALIDATION.md`

决定哪些工作需要特别注意，哪些技术已经验证，哪些还有待解决。

## **三、用户需要向 AI 提供哪些信息？**

我认为用户在这一阶段不应该负责自己拆解任务，也不应该被要求提前设计所有子 Agent。

这些正是 AI 应该完成的工作。

用户主要需要补充的是 AI 无法从设计文档中直接获知的执行条件。

建议分成六类。

### **1. 开发时间与交付优先级**

AI 需要了解：

- 是否有期望的开发完成日期？
- 是否有明确的 MVP 发布日期？
- 每天或每周大概有多少开发时间？
- 是否是利用业余时间断续开发？
- 哪些功能必须优先完成？
- 是否允许部分功能延后到后续版本？

例如：

你可能周末有大量时间，但工作日只能抽出一小时。

AI 就不能把一个需要用户频繁确认的开发流程安排在工作日，也不能安排大量需要连续调试的任务。

如果用户没有明确时间要求，AI 可以按任务复杂度规划开发顺序，不必强行估算准确工期。

### **2. 开发环境与 Vibe Coding 工具能力**

这是你新增的多 Agent 需求中非常重要的一类信息。

AI 需要了解：

| 信息       | 需要明确的内容                                     |
| :------- | :------------------------------------------ |
| 使用工具     | Cursor、Codex、Claude Code 或其他 Vibe Coding 工具 |
| Agent 能力 | 是否支持子 Agent、Agent Teams 或任务委派               |
| 并行能力     | 是否允许多个 Agent 同时运行                           |
| 隔离能力     | 是否支持独立工作区、Git Worktree 或独立分支                |
| 文件共享     | 不同 Agent 是否能够访问相同项目文件                       |
| 任务协调     | 是否支持主 Agent 获取子 Agent 进度及执行结果               |
| 工具限制     | 是否存在并发数量、权限、上下文或模型限制                        |

需要注意：

**子 Agent 能力和并行代码开发能力不是一回事。**

有些工具允许主 Agent 创建子 Agent，但子 Agent 可能只能返回分析结果，不一定能够安全地在独立工作空间中同时修改代码。

这会直接影响后续的任务分配方式。

不过，我不建议要求用户手动提供一大堆工具参数。

AI 应该优先检查当前开发环境的可用能力。确实无法识别的，再向用户询问。

### **3. 用户希望参与多少开发过程**

例如：

- 希望 AI 自动完成大部分任务，自己只负责审查。
- 希望每个开发板块完成后都由自己确认。
- 希望关键架构或数据库变更必须经过批准。
- 希望 AI 在遇到问题时及时向自己反馈。
- 是否允许 Agent 自主安装依赖、运行测试、修改配置？
- 是否允许 Agent 自动创建分支和提交代码？

这会影响开发计划中的人工检查节点。

### **4. 现有代码仓库和项目初始状态**

如果是从零开始，需要确认：

- 是否已经创建项目目录？
- 是否已经初始化 Git？
- 是否已经创建基础工程？
- 是否已有脚手架或模板？
- 是否存在已有代码？

如果是已有项目，还需要让 AI 检查实际代码结构、当前实现情况和已有测试，避免把已经完成的功能重新安排一遍。

### **5. 外部资源与开发前置条件**

例如：

- 是否已经拥有 API Key？
- 是否已经准备好数据库？
- 是否已经拥有服务器？
- 是否有测试账号？
- 是否存在等待第三方审核的事项？
- 是否需要人工准备测试数据？

这些事项可能成为开发任务的阻塞条件。

### **6. 多 Agent 开发的授权与偏好**

最后需要确认：

- 是否希望优先使用多 Agent 并行开发？
- 是否接受增加模型调用成本，以换取并行开发效率？
- 是否接受 Agent 分别修改独立代码分支？
- 是否要求所有代码最终经过主 Agent 审查？
- 是否希望保留一份可直接复制给不同 Agent 的工作指令？

我建议把默认原则设为：

**能安全并行就并行，但不为了并行而强行拆分；如果串行更可靠，就使用串行。**

## **四、AI 在这一阶段应该怎么做？**

我建议将 AI 的工作划分为九个步骤。

### **第一步：读取文档，检查开发准备情况**

AI 首先读取前置文档，提取：

- MVP 功能及其优先级。
- 系统模块及其职责。
- 模块之间的依赖关系。
- 核心数据结构和接口。
- 技术栈和技术约束。
- 已确认的架构决策。
- 各项功能的验收标准。
- 已知风险和待解决问题。

接着检查：

1. 需求是否足够明确？
2. 架构是否足以指导编码？
3. 模块边界是否清晰？
4. 核心接口是否已经确定？
5. 是否存在尚未解决的技术阻塞？
6. 是否有必要的开发环境和外部资源？

如果发现架构文档缺失重要接口或模块定义，AI 应先提出补充建议，而不是直接让多个 Agent 各自发挥。

这里有一个特别重要的原则：

**多 Agent 开发之前，必须先让各 Agent 对要协作的部分拥有一致的架构认知。**

### **第二步：将系统拆分为开发板块**

这是本阶段最核心的任务之一。

AI 应该根据：

- `REQUIREMENTS.md` 中的业务功能。
- `PRODUCT_DESIGN.md` 中的用户操作流程。
- `ARCHITECTURE.md` 中的系统模块。
- `ARCHITECTURE.md` 中的模块依赖关系。

将整个项目拆分为几个相对独立的开发板块。

我建议优先按照以下逻辑拆分：

**先拆分独立业务能力，再考虑技术层次。**

例如，一个 AI 任务管理软件可以拆分成：

**开发板块 A：项目基础设施**

项目初始化、依赖管理、环境配置、数据库连接、统一异常处理、基础工程规范。

**开发板块 B：任务管理**

任务创建、修改、删除、状态管理、任务查询。

**开发板块 C：计划管理**

计划创建、任务关联、计划调整、进度查看。

**开发板块 D：AI 助手**

模型调用、意图识别、工具调用、AI 任务操作。

**开发板块 E：前端界面**

页面框架、任务界面、计划界面、AI 对话界面。

**开发板块 F：系统集成与质量验证**

模块集成、端到端流程验证、问题修复、回归测试。

以上是示例，不代表每个项目都必须拆成六个板块。实际拆分必须遵循架构文档。

为什么我建议采用这种方式？

因为 B、C、D 是相对独立的业务能力，可以在接口约定明确后分别开发；E 可以在约定接口和数据格式后使用 Mock 数据并行开发；A 则通常要先完成一部分基础工作，F 则需要等相关模块能够集成后再开展。

但要注意：

**开发板块不等于子 Agent。**

一个开发板块可能需要多个 Agent 完成，也可能一个 Agent 负责多个简单板块。

AI 应根据任务规模、代码边界和依赖关系决定，不应该机械地一块板块对应一个 Agent。

### **第三步：将开发板块拆解为具体任务**

板块划分只是第一层，接下来 AI 需要继续拆解。

例如，任务管理板块可以拆成：

```
开发板块：任务管理

├── TASK-001：定义任务数据模型
├── TASK-002：实现任务数据库操作
├── TASK-003：实现任务创建接口
├── TASK-004：实现任务查询接口
├── TASK-005：实现任务修改接口
├── TASK-006：实现任务删除接口
├── TASK-007：实现任务状态管理
├── TASK-008：实现任务管理页面
└── TASK-009：完成任务管理模块测试
```

不过，这里还需要进一步区分：

有些任务可以合并，有些任务应该拆得更细。

例如：

`TASK-001：实现整个任务管理系统`

这种任务太大，AI 不容易准确把握边界。

而：

`TASK-003：为任务标题字段增加一个非空校验`

如果它本身只是某个任务中的一个小修改，也没必要单独成为一个开发任务。

我建议采用一个判断标准：

**一个开发任务应该具备明确的目标、有限的修改范围、确定的输入和输出，以及可以独立验证的完成标准。**

每项任务至少包含以下内容：

| 字段    | 说明               |
| :---- | :--------------- |
| 任务 ID | 唯一标识，例如 TASK-001 |
| 任务名称  | 简短描述要实现什么        |
| 所属板块  | 归属于哪个开发板块        |
| 关联需求  | 对应哪些需求 ID        |
| 任务目标  | 具体要完成什么          |
| 任务范围  | 需要实现和不需要实现的内容    |
| 前置依赖  | 必须先完成哪些任务        |
| 输入资料  | 需要读取哪些文档和文件      |
| 修改范围  | 允许修改哪些模块或文件      |
| 接口约束  | 必须遵循哪些已有契约       |
| 交付内容  | 需要生成或修改什么        |
| 验收标准  | 怎样才算完成           |
| 测试要求  | 需要执行哪些测试         |
| 优先级   | P0、P1、P2 等       |
| 执行状态  | 待开始、进行中、待验收、已完成等 |

我尤其建议将验收标准写得足够具体。

例如：

```
## TASK-003：实现任务创建接口

### 任务目标
实现创建任务的后端 API。

### 输入
- ARCHITECTURE.md
- 任务数据模型设计
- 接口契约

### 修改范围
- backend/modules/tasks/
- backend/api/tasks.py

### 验收标准
1. 能够正常创建任务。
2. 必填字段不能为空。
3. 非法日期能够被拒绝。
4. 创建成功后能够从数据库查询到记录。
5. 返回结构符合既定 API 契约。
6. 相应自动化测试全部通过。

### 依赖任务
- TASK-001：定义任务数据模型
- TASK-002：实现任务数据库操作

### 交付内容
- API 实现
- 对应测试代码
- 简要实现说明
```

这样子 Agent 不需要每次重新理解整个项目的所有历史对话，就可以根据任务卡片开展工作。

### **第四步：分析任务依赖关系，制定开发顺序**

这是多 Agent 能否成功协作的关键。

AI 需要为所有任务建立依赖关系，而不是只生成一份按顺序排列的任务清单。

例如：

```
TASK-001：项目初始化
        │
        ▼
TASK-002：数据库基础配置
        │
        ▼
TASK-003：核心数据模型
        │
        ├──────────────┐
        ▼              ▼
TASK-004：任务接口   TASK-005：计划接口
        │              │
        └──────┬───────┘
               ▼
        TASK-006：AI 工具调用
               │
               ▼
        TASK-007：系统集成
               │
               ▼
        TASK-008：端到端测试
```

这里可以采用 DAG（有向无环图）表达任务依赖关系。

AI 需要识别：

- 哪些任务是前置任务？
- 哪些任务可以同时开展？
- 哪些任务必须等待其他任务完成？
- 哪些任务处于关键路径？
- 哪些任务会因为接口变化而受到影响？

特别是多个 Agent 协作时，需要把共享接口和共享数据结构提前确定下来。

例如，任务管理模块和 AI 助手都需要操作 `Task` 数据模型。

如果两个 Agent 分别设计自己的任务数据结构，最终集成时就会出现问题。

因此，数据模型和关键服务接口必须优先明确。

### **第五步：判断哪些任务可以并行开发**

这一点我建议专门建立一套判断规则。

不是所有依赖关系明确的任务都能直接并行。

例如：

| 情况                   | 是否适合并行                |
| :------------------- | :-------------------- |
| 不同模块，修改不同文件，接口已确定    | 适合                    |
| 不同页面，使用已确定的 API 契约   | 通常适合                  |
| 前端和后端，已确定接口和数据结构     | 通常适合                  |
| 两个 Agent 同时修改同一个核心文件 | 不适合                   |
| 两个 Agent 同时修改数据库公共结构 | 通常不适合                 |
| 后一个任务依赖前一个任务的实现结果    | 应等待，或通过 Mock / 接口契约解耦 |
| 独立的代码审查和测试设计         | 适合并行                  |
| 高度耦合的核心业务流程          | 倾向由同一个 Agent 连续完成     |

这里还有一个重要区别：

**能够并行，不代表值得并行。**

例如，一个简单的项目只有三个开发任务，即使可以拆成三个 Agent，也可能因为任务协调、上下文传递和最终整合而增加额外成本。

AI 应综合考虑：

- 任务是否足够独立。
- 任务工作量是否值得委派。
- 多 Agent 是否会重复消耗上下文和模型调用。
- 最终集成是否会增加大量工作。
- 用户是否有能力审查多个 Agent 的结果。

OpenAI 的多 Agent 开发指南也强调，独立、边界明确的工作适合委派，而高度依赖前序结果或共享可变资源的工作更适合由单一 Agent 连续完成；并行 Agent 还会增加额外的模型调用成本。

### **第六步：设计子 Agent 及其职责**

这是你特别提出的内容，我建议作为第八阶段的一个独立子流程。

AI 根据已经划分的开发板块和任务依赖，设计合理的子 Agent 团队。

但不要提前固定所有项目都要使用哪些 Agent。

应该让 AI 根据项目特点动态生成。

#### **1. 主 Agent：项目开发协调者**

主 Agent 由当前负责整个项目的 AI 担任。

主要职责：

- 掌握完整架构和需求。
- 维护整体开发计划。
- 分配开发任务。
- 启动和协调子 Agent。
- 跟踪开发进度。
- 解决模块之间的冲突。
- 负责代码集成。
- 检查最终交付结果。

我建议主 Agent 不要在所有子 Agent 已经开始工作后，又自行修改它们正在维护的代码。

主 Agent 应尽量承担协调、审查和集成职责，必要时负责无法安全委派的核心任务。

#### **2. 开发型子 Agent**

根据项目板块来设计，例如：

**Backend Agent**

示例角色

负责后端业务模块、API、数据库访问、服务逻辑和后端测试。

**Frontend Agent**

示例角色

负责前端页面、组件、交互和前后端接口接入。

**AI Agent Developer**

条件适用

负责模型接入、Prompt、工具调用、Agent 工作流及 AI 相关测试。

**Database Agent**

条件适用

负责数据库模型、迁移、数据关系和相关存储逻辑。对于小项目，可以由 Backend Agent 负责。

**QA / Code Reviewer Agent**

建议保留的职责

独立检查代码、测试结果、接口一致性、架构约束和潜在缺陷。

以上只是可供 AI 选择的角色类型，不意味着每个项目都需要五个子 Agent。

例如，一个很小的任务管理应用可能只需要：

- 主 Agent：统筹及集成。
- Backend Agent：后端。
- Frontend Agent：前端。
- QA Agent：独立审查和测试。

如果 AI 功能比较复杂，再增加独立的 AI Agent Developer。

#### **3. 每个子 Agent 必须有明确的工作契约**

仅仅告诉子 Agent“负责开发后端”是不够的。

建议 AI 为每个 Agent 生成一份配置说明，至少包括：

| 配置项      | 内容               |
| :------- | :--------------- |
| Agent 名称 | Backend Agent 等  |
| 角色定位     | 负责的专业领域          |
| 核心目标     | 需要交付什么           |
| 负责板块     | 哪些开发板块归它负责       |
| 分配任务     | 具体 TASK ID       |
| 输入文档     | 必须阅读的文档          |
| 可修改范围    | 允许编辑的目录、文件       |
| 禁止事项     | 不得修改的模块和架构约束     |
| 接口契约     | 与其他 Agent 如何交互   |
| 验收标准     | 每项任务的通过条件        |
| 测试要求     | 必须执行的测试          |
| 交付报告     | 完成后向主 Agent 汇报什么 |

我认为这里最重要的两个字段是：

**可修改范围和禁止事项。**

多 Agent 并行开发时，不同 Agent 如果同时修改同一个公共文件，很容易出现代码覆盖、合并冲突和架构不一致。

因此，尽可能为每个 Agent 划定独立的代码所有权。

### **第七步：制定异步执行与集成策略**

这一步不能只是告诉 AI 哪些 Agent 可以同时工作，还需要决定它们具体如何工作。

建议采用以下策略：

**A. 前置准备阶段**

主 Agent 先完成或安排基础设施任务：

- 初始化项目。
- 创建基础目录。
- 确认依赖管理方式。
- 建立公共配置。
- 明确公共数据模型。
- 明确核心 API 契约。
- 配置必要的代码格式、测试和质量检查。

**B. 并行开发阶段**

前置条件完成后，主 Agent 同时分配互不冲突的任务。

例如：

**并行开发波次 1**

**Backend Agent**

任务管理模块

**Frontend Agent**

页面骨架和 Mock 接口

**并行开发波次 2**

**AI Agent Developer**

AI 工具调用

**Backend Agent**

计划管理模块

**集成阶段**

**Main Agent + QA Agent**

接口集成、功能联调、测试、代码审查。

这是一个示意安排。实际波次必须由任务依赖决定，不能机械地按照 Agent 角色排列。

**C. 集成阶段**

所有独立模块开发完成后，由主 Agent 负责：

- 检查代码差异。
- 合并不同 Agent 的修改。
- 解决文件和接口冲突。
- 运行统一测试。
- 检查是否违反架构约束。
- 修复模块集成问题。

我建议尽可能采用 Git 分支或 Git Worktree 隔离不同 Agent 的工作区。

例如：

```
main
│
├── feature/backend-task
│
├── feature/frontend-ui
│
└── feature/ai-agent
```

每个 Agent 在自己的分支或 Worktree 中工作，完成后再由主 Agent 审查和整合。

Git Worktree 可以让多个任务使用同一 Git 仓库的独立工作目录，减少同时修改代码时的工作区冲突。OpenAI 的 Codex 文档也将 Worktree 作为并行代码任务的隔离方式。

### **第八步：制定每个开发任务的交付和验收机制**

这是经常被忽略，但对 AI 编码特别重要的一步。

不能因为 Agent 声称“开发完成”，就认为任务已经完成。

每个任务都应该规定：

1. 必须交付哪些代码或文件。
2. 必须执行什么测试。
3. 是否需要更新相关文档。
4. 是否需要通过代码检查。
5. 是否需要与其他模块集成。
6. 如何向主 Agent 汇报结果。

- 是否修改公共接口：

- 待处理问题：

- 实现是否符合需求。
- 是否遵守架构设计。
- 是否存在明显逻辑错误。

## **六、建议增加一个非常重要的机制：并行开发之前的接口冻结**

这是我认为你提出多 Agent 开发时，最应该额外增加的设计。

假设 Backend Agent 和 AI Agent Developer 同时工作。

Backend Agent 设计：

```
create_task(title, due_date)
```

而 AI Agent Developer 认为应该设计：

```
create_task(task_data: dict)
```

两边单独开发可能都没有问题，但集成时就会出现不兼容。

所以，在并行开发之前，必须先明确：

1. 共享数据结构。
2. 模块公开接口。
3. API 请求和响应格式。
4. 公共配置。
5. 文件和目录所有权。
6. 允许修改的范围。

我把这件事称为：

**并行开发接口冻结（Interface Freeze）。**

并不意味着这些接口永远不能修改，而是并行开发期间，Agent 不能随意变更公共契约。

确实需要修改时，必须通知主 Agent，由主 Agent 评估影响，并同步更新相关任务和其他 Agent 的工作说明。

这会大大降低并行开发的协调成本。

## **七、关于多 Agent 异步开发，我还有四个重要建议**

我想单独强调这部分，因为它决定这套流程最终能不能真正落地。

### **1. 不要把子 Agent 简单理解为多个聊天窗口**

你需要区分三种协作模式：

| 模式          | 工作方式                                 | 适用场景                  |
| :---------- | :----------------------------------- | :-------------------- |
| 单会话内子 Agent | 主 Agent 委派任务，子 Agent 使用独立上下文，完成后返回结果 | 独立分析、小型编码、测试审查        |
| 多会话并行开发     | 多个独立 Agent 分别处理不同开发任务                | 多个功能板块同时开发            |
| 独立工作区并行开发   | 每个 Agent 在独立 Git Worktree 或分支中修改代码   | 多 Agent 同时修改同一项目的不同部分 |

需要注意：

**独立上下文不一定意味着独立代码工作区。**

例如，一个子 Agent 即使拥有独立对话上下文，如果多个 Agent 实际修改同一个项目目录，仍然可能产生文件冲突。

因此，是否支持代码工作区隔离，是多 Agent 并行开发能力判断中的重要条件。

不同开发工具对这几种模式的支持程度不同。

Claude Academy+2

<br />

### **2. Agent 数量由可独立工作的任务决定**

不要规定每个项目固定使用三个或五个 Agent。

我的建议是：

- 小项目：主 Agent + 1～2 个子 Agent，甚至单 Agent。
- 中等项目：主 Agent + 2～4 个开发 Agent，再根据需要加入 QA。
- 大型项目：根据独立开发板块增加 Agent，但必须确保主 Agent 有足够能力完成协调和审查。

这些只是规划参考，不是固定上限。

尤其要避免 Agent 数量超过用户能够有效审查的范围。

可以参考一个比较实际的策略：先使用少量并行工作流，确认分工、隔离和集成机制有效后再增加。Anthropic 的相关开发实践也将两到三个独立工作流作为较合理的起步方式，并强调开发任务需要拥有不重叠的修改范围。

### **3. 子 Agent 必须采用统一的项目上下文**

这是 Vibe Coding 非常容易出现的问题。

主 Agent 可能已经和用户讨论了很多架构细节，但新创建的子 Agent 未必能够看到这些历史对话。

因此，不能只给子 Agent 一句：

> 请负责开发任务管理模块。

它至少需要获得：

```
项目公共上下文：
- REQUIREMENTS.md
- PRODUCT_DESIGN.md
- ARCHITECTURE.md
- DEVELOPMENT_APPROACH.md

必要的专项上下文：
- 对应的 ADR
- 对应的接口契约
- 对应的开发任务

执行约束：
- 只负责指定任务
- 不随意修改架构
- 遵循既定代码规范
- 不得擅自修改其他 Agent 的文件
- 必须进行规定的测试
- 完成后提交交付报告
```

这样即使 Agent 异步运行，仍然能够遵循统一的架构和开发规则。

### **4. 主 Agent 必须拥有最终集成权**

不能让几个 Agent 自己开发、自己决定如何集成，最后直接宣布项目完成。

建议明确：

- 子 Agent 负责自己的开发任务和局部测试。
- 主 Agent 负责任务协调、跨模块集成和最终代码检查。
- QA Agent 负责独立审查和验证。
- 用户保留重大架构变更、敏感权限操作和关键交付的最终决策权。

尤其要规定：任何 Agent 都不能未经授权擅自改变 `ARCHITECTURE.md` 中的已确认设计。

## **八、这一阶段的最终执行流程**

综合前面的内容，我建议将第八阶段的 Skill 执行流程确定为以下结构：

1. **前置文档读取与开发准备检查**

   读取需求、产品设计、架构和开发模型等文档，检查是否具备开发条件。
2. **开发条件收集**

   询问时间安排、开发环境、工具能力、人工参与程度和其他外部约束。
3. **开发板块划分**

   根据业务能力、架构模块和 MVP 范围，划分独立开发板块。
4. **任务拆解**

   将开发板块拆成具有明确目标、输入、输出和验收标准的开发任务。
5. **任务依赖分析**

   建立任务依赖图，确定前置任务、并行任务、关键路径和集成节点。
6. **并行开发可行性判断**

   判断当前工具是否支持子 Agent、独立工作区、异步执行和并行代码修改。
7. **子 Agent 团队设计**

   根据开发板块和任务分工，设计主 Agent、开发 Agent、测试 Agent 等角色及其工作契约。
8. **执行策略与集成规划**

   制定并行波次、文件所有权、接口冻结、代码合并、测试和顺序执行备用方案。
9. **开发计划审查与确认**

   检查需求覆盖、任务粒度、依赖、协作和验收机制，与用户确认。
10. **正式文档生成**

    生成 `ROADMAP.md`、`DEVELOPMENT_TASKS.md`，需要多 Agent 时额外生成 `AGENT_EXECUTION_PLAN.md`。

## **十、我建议你对原来的十二阶段流程再增加一个重要认识**

从第八阶段开始，你的开发流程实际上发生了一次转变。

前面第一至第七阶段主要是在确定：

**要开发什么软件，以及这个软件应该如何设计。**

第八阶段则是把这些设计转化为：

**AI 可以按照什么计划、由哪些 Agent、通过什么协作方式去完成开发。**

而第九阶段才真正开始执行开发。

所以，我认为第八阶段不应该只被称为传统的「开发计划与任务拆解」，更准确的定位是：

**AI 开发任务规划与 Agent 编排（AI Development Planning & Agent Orchestration）。**

### **最后，我认为有五条规则应该写入这个 Skill 的最高优先级约束**

1. **任务拆分必须以可交付、可验证为目标。** 不要只按代码文件或技术层次机械拆分。

2. **并行开发必须建立在任务相互独立、接口明确的基础上。** 不允许为了多 Agent 而强行并行。

3. **Agent 的职责和文件修改范围必须明确。** 尽可能避免多个 Agent 同时修改同一份代码。

4. **开发计划必须独立于具体 Vibe Coding 工具。** 支持多 Agent 就并行执行，不支持就按照依赖关系顺序执行，不需要重新规划。

5. **主 Agent 必须负责整合与最终审查。** 子 Agent 完成任务不等于整个项目完成。

另外，我建议把两个动作分开：

- 第八阶段：设计 Agent 团队、任务分工、协作规则，生成平台无关的 `AGENT_EXECUTION_PLAN.md`。
- 第九阶段：根据实际使用的 Vibe Coding 工具，将规划转化为可执行的子 Agent 配置或任务委派指令，并正式启动开发。

这样既不会让第八阶段过早陷入某个工具的配置细节，也能保证第九阶段拿到计划后就可以开始执行。

**我最推荐的最终设计是：第八阶段由 AI 自动完成开发任务拆解、依赖分析和 Agent 团队规划，用户负责审核开发策略和关键分工；第九阶段由主 Agent 按照计划调度多个子 Agent，或者在不支持多 Agent 时顺序执行。**

这会让你的整套流程从传统的 AI 辅助编码，真正过渡到 AI Agent 协同软件开发。
