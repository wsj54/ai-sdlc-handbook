# **第三阶段：需求分析与范围管理——AI skill方案设计**

第一阶段已经整理了原始需求，第二阶段选择了开发模型

现在第三阶段真正要做的事情是：

**将用户最初的模糊想法，转化为结构清晰、范围明确、优先级合理、可以设计和开发、并且可以验证的软件需求。**

建议不要把这个阶段设计成一次简单的「让 AI 生成 PRD 文档」。

而是将它设计成一个完整的 AI 需求工程协作过程：AI 负责需求分析、主动提问、需求细化、冲突检查、范围规划和质量审查；用户负责提供真实需求、回答问题、确认取舍和最终验收。

下面将从工作目标、执行流程、AI 的具体任务、向用户提问的内容、最终文档以及阶段验收六个方面来设计。

# **一、首先明确第三阶段的定位和边界**

先明确第三阶段需要解决什么问题。

## **第三阶段：需求分析与范围管理**

**输入：**

- `INITIAL_REQUIREMENTS.md`：第一阶段原始需求整理文档。
- `DEVELOPMENT_APPROACH.md`：第二阶段开发模型规划。
- 其他已有的项目背景和约束信息。

**核心目标：**

将初始需求系统化、结构化，明确第一版软件应该做什么、不应该做什么，以及每项需求应该如何验收。

**输出：**

- `REQUIREMENTS.md`：正式需求规范。
- `PRODUCT_BACKLOG.md`：可选，适用于敏捷、增量迭代项目。
- 需求疑问、假设、风险和决策记录。

这里有一个非常重要的边界：

| 工作内容             | 属于哪个阶段         |
| ---------------- | -------------- |
| 确定软件解决什么问题       | 第一阶段，必要时在本阶段修正 |
| 选择瀑布、敏捷、增量等开发模型  | 第二阶段           |
| 明确软件具体有什么功能      | 第三阶段           |
| 明确功能的输入、输出、行为和规则 | 第三阶段           |
| 确定 MVP 和功能优先级    | 第三阶段           |
| 设计详细页面和交互原型      | 第四阶段           |
| 确定数据库、API、技术架构   | 后续技术设计阶段       |
| 拆分具体编码任务         | 开发计划阶段         |

特别需要注意：需求分析不是技术架构设计。

例如，用户的 AI 试卷生成系统需要支持试题生成、试题核验、主观题判分，这是需求。

至于采用什么 Agent 框架、数据库、向量数据库、模型调用方式，这是后续技术设计需要讨论的事情。

**第三阶段要明确软件需要实现什么行为，但不应该过早决定软件内部如何实现。**

# **二、第三阶段应该采用什么样的 AI 协作模式？**

建议把整个阶段划分为八个连续的工作步骤。

## **需求分析与范围管理：八步工作流**

1. **项目上下文读取与流程适配**

   读取原始需求、开发模型、项目执行流程，明确本阶段的工作方式。
2. **原始需求诊断与需求补充**

   分析需求缺口、歧义、重复、冲突，制定访谈和澄清计划。
3. **需求获取与深入分析**

   通过持续对话明确用户、场景、功能行为、业务规则和异常情况。
4. **需求分类与结构化**

   整理功能需求、非功能需求、业务规则、约束条件和外部依赖。
5. **需求范围与优先级管理**

   确定 MVP、首版功能、后续版本、不做事项和功能依赖。
6. **需求细化与验收标准制定**

   为核心需求补充输入、输出、前置条件、正常行为、异常行为和验收标准。
7. **需求完整性与一致性审查**

   检查遗漏、歧义、冲突、可行性、需求膨胀和验收不可操作问题。
8. **需求基线确认与阶段交接**

   生成正式文档，由用户审查确认，形成后续设计阶段的输入。

这八步是建议的通用结构，具体执行顺序、哪些工作可以合并或重复，要服从第二阶段形成的项目流程。

例如，用户选择的是增量开发，那么本阶段应该优先明确第一个可交付增量的详细需求，而不是强行把未来所有版本的功能全部定义完毕。

下面详细解释每一步。

# **三、八个步骤应该如何执行？**

## **Step 3.1：项目上下文读取与开发流程适配**

准备工作

**目的：让 AI 先理解当前项目的情况，避免不了解项目就直接分析需求。**

### **AI 应该做什么？**

首先读取：

1. 第一阶段的原始需求文档。
2. 第二阶段的开发模型选择文档。
3. 已有的其他约束和项目信息。

然后完成以下分析：

| AI 的任务  | 具体内容               |
| ------- | ------------------ |
| 理解项目目标  | 确认软件的核心目的和目标用户     |
| 理解开发模型  | 确认采用增量、敏捷、瀑布还是混合模型 |
| 理解本阶段位置 | 判断当前需求分析应该完成到什么程度  |
| 了解阶段门禁  | 确认本阶段必须满足哪些条件      |
| 分析原始材料  | 识别已经明确、缺失和存在疑问的内容  |
| 制定访谈计划  | 确定需要向用户补充询问的内容     |

这里尤其需要注意开发模型的影响。

例如：

| 开发模型 | 本阶段应该如何开展                   |
| ---- | --------------------------- |
| 瀑布   | 对约定范围内的需求进行较完整的分析，形成需求基线    |
| 敏捷   | 建立产品目标、MVP 和产品待办列表，近期需求细化优先 |
| 增量   | 明确各个增量的目标和边界，优先细化首个增量       |
| V 模型 | 在需求定义时同步规划验证方法和验收条件         |
| 螺旋   | 优先明确重大风险相关的需求和验证目标          |
| 原型模型 | 标记需要通过原型反馈继续明确的需求           |

### **用户需要提供什么？**

一般不需要再次提供第一阶段已经确认的信息。

只有当 AI 发现初始需求文档中存在缺失或矛盾时，才向用户询问。

### **本步骤产物**

`REQUIREMENT_ANALYSIS_PLAN.md`，即本阶段需求分析执行计划。

它可以包括：

- 本阶段工作目标。
- 开发模型适配规则。
- 当前已有信息。
- 待补充信息。
- 需要讨论的问题。
- 后续八个步骤的执行安排。

**完成标准：** AI 已经理解项目，知道本阶段应该完成什么，也知道哪些信息还需要向用户获取。

## **Step 3.2：原始需求诊断与需求补充**

需求获取的准备阶段

**目的：不要立即把原始想法改写成 PRD，而是先诊断需求本身。**

用户在第一阶段可能只是告诉 AI：

> 我想开发一个 AI 试卷生成和批改系统，可以生成题目、让用户在线作答，然后自动判分，还希望能和 AI 讨论试题。

这还不是一份合格的需求。

AI 首先应该对原始想法进行拆解。

### **AI 应该做什么？**

**1. 提取原始需求**

将用户提出的想法逐一提取出来，避免遗漏。

**2. 识别需求类型**

区分：

- 已经明确的功能需求。
- 隐含的功能需求。
- 非功能需求。
- 业务规则。
- 技术约束。
- 尚未确认的想法。

**3. 识别需求问题**

例如：

- 同一个功能是否重复出现？
- 两项需求是否相互矛盾？
- 需求是否过于模糊？
- 是否缺少必要的操作步骤？
- 是否存在明显的需求依赖？
- 是否存在用户没有提到但实现核心功能不可缺少的需求？

**4. 建立需求问题清单**

不要急于补全，而是告诉用户目前还存在哪些问题。

### **AI 可以询问用户什么？**

例如：

| AI 提问                       | 提问目的        |
| --------------------------- | ----------- |
| 这个系统是只供用户自己使用，还是未来需要支持其他用户？ | 明确用户范围      |
| 生成的试卷需要保存下来反复使用吗？           | 确认数据生命周期    |
| 是否需要支持多个学科和不同题型？            | 明确核心功能范围    |
| 判分结果是否需要人工修改？               | 明确评分流程      |
| 是否希望 AI 根据错题进行讨论和解释？        | 区分核心功能和扩展功能 |

不过，并不是所有问题都必须一次询问完。

我建议默认每次提出一个最重要的问题；如果几个问题属于同一个场景，且回答它们比较方便，可以合并询问。

### **本步骤产物**

- 原始需求清单。
- 需求问题清单。
- 信息缺失清单。
- 需求冲突清单。
- 待确认事项。

**完成标准：** 原始需求都已经被识别和分类，AI 已经知道接下来需要重点澄清什么。

## **Step 3.3：需求获取与深入分析**

核心工作阶段

这是整个第三阶段最重要的环节。

建议将 AI 定义为一个**需求分析师 + 产品经理 + 需求访谈者**。

不要让它只是给用户写需求，而是让它主动与用户讨论，逐步把每个需求变得具体。

建议将这个环节拆成六个分析维度。

### **3.3.1 用户与使用场景分析**

AI 需要了解谁在使用软件，以及使用软件是为了做什么。

可以询问：

| 需要分析的内容 | 示例问题               |
| ------- | ------------------ |
| 用户类型    | 谁会使用这个软件？          |
| 使用目的    | 用户使用它主要是为了解决什么问题？  |
| 使用场景    | 用户一般在什么情况下打开软件？    |
| 使用频率    | 每天使用、偶尔使用还是特定场景使用？ |
| 使用环境    | PC、手机、平板，还是多个设备？   |
| 使用习惯    | 用户目前是怎样完成这些事情的？    |

这里有一个很重要的问题：

**AI 不仅要询问用户希望软件有什么功能，还应该询问用户现在是怎么解决这个问题的。**

例如，用户希望使用 AI 帮助安排任务。

AI 可以询问：

> 你现在是如何管理任务的？使用 Excel、备忘录，还是直接依靠记忆？

> 你通常在什么情况下需要调整任务安排？

这些问题可以帮助 AI 发现真正的需求，而不是盲目增加功能。

### **3.3.2 核心业务流程分析**

让 AI 将用户的主要操作过程拆解出来。

例如试卷生成系统：

选择学科和试卷参数

生成试题

审核和调整试题

发布试卷

用户在线作答

提交试卷

系统判分

人工修改或复核评分

查看报告与讨论

AI 应该分析每一步：

- 由谁发起？
- 需要什么前置信息？
- 用户输入什么？
- 系统应该做什么？
- 会产生什么结果？
- 下一步是什么？
- 是否可能中断或失败？

用户需要确认这些流程是否符合自己的实际想法。

尤其需要注意：不能只分析正常流程，还要分析中断、撤销、重试、超时等情况。

### **3.3.3 功能需求分析**

将软件的功能拆分为模块，再把模块拆分成独立需求。

例如：

| 模块    | 具体需求                  |
| ----- | --------------------- |
| 试卷管理  | 创建试卷、编辑试卷、删除试卷、查看历史试卷 |
| 试题管理  | 添加试题、编辑试题、删除试题、调整顺序   |
| AI 出题 | 按照参数生成试题、核验试题         |
| 在线作答  | 显示试题、保存答案、提交试卷        |
| 自动判分  | 客观题判分、主观题判分、总分计算      |
| 评分管理  | 修改评分、重新计算成绩           |
| AI 讨论 | 针对题目、答案和评分结果进行讨论      |

这里需要让 AI 进行进一步拆解，而不是停留在模块名称。

例如：

「在线作答」可以继续拆分：

- 查看试卷。
- 填写单选题。
- 填写多选题。
- 填写主观题。
- 自动保存作答草稿。
- 提交试卷。
- 超时自动交卷。
- 查看提交结果。

这些才是可以进一步设计和开发的需求。

### **3.3.4 业务规则和异常场景分析**

这是很多个人开发者容易遗漏的地方。

例如：

- 已经提交的试卷还能修改吗？
- 修改题目以后，历史成绩是否需要重新计算？
- 主观题判分不准确时怎么办？
- AI 生成了不符合题目规范的试题怎么办？
- 网络中断时，用户的答案是否保留？
- 用户重复点击提交按钮会怎样？

建议 AI 针对每个核心功能都检查：

| 维度   | 检查内容           |
| ---- | -------------- |
| 前置条件 | 什么情况下允许操作？     |
| 正常行为 | 正常情况下系统怎么处理？   |
| 边界情况 | 极端输入或特殊状态如何处理？ |
| 异常情况 | 发生错误时如何反馈？     |
| 状态变化 | 操作前后数据状态如何变化？  |
| 用户反馈 | 用户应该看到什么结果？    |

### **3.3.5 非功能需求分析**

非功能需求不仅仅是性能和安全，它还涉及软件整体质量。

AI 应主动分析：

| 类别   | 需要了解的内容           |
| ---- | ----------------- |
| 性能   | 页面响应、生成时间、并发需求    |
| 可靠性  | 失败处理、数据恢复、稳定性     |
| 安全性  | 身份认证、权限、敏感数据保护    |
| 易用性  | 学习成本、操作复杂度、交互体验   |
| 兼容性  | 浏览器、设备、操作系统       |
| 可维护性 | 后续功能扩展与代码维护       |
| 可用性  | 是否需要离线使用、是否需要持续在线 |
| 成本约束 | 模型调用成本、服务器预算和存储成本 |

注意，AI 不应该机械要求用户为所有项目设定所有指标。

例如，一个本地单用户工具，可能不需要定义复杂的并发性能指标。

但它仍然需要明确数据保存、备份和恢复等基本要求。

### **3.3.6 数据与外部依赖分析**

这一部分我建议独立出来，因为 AI 软件往往存在很多数据和外部服务约束。

AI 应主动询问：

- 需要保存哪些类型的数据？
- 用户是否需要导入已有数据？
- 是否需要导出数据？
- 数据保存多久？
- 是否包含个人或敏感信息？
- 是否需要调用外部 API？
- 外部服务失败时能否继续使用核心功能？
- 是否需要使用用户自己提供的模型 API Key？

具体技术实现留到架构阶段，但数据的业务需求和限制应该在这里明确。

### **本步骤的用户参与方式**

这一步不是简单地回答 AI 的问题。

建议形成以下对话循环：

**AI 提出一个需要澄清的问题**

解释为什么需要确认，提供可选答案

**用户回答、补充或提出新的想法**

**AI 分析回答并更新需求草稿**

必要时识别新的问题和关联影响

**AI 检查是否还存在重要歧义**

重复讨论，直到核心需求清楚

**建议：每讨论清楚一组需求，就立即更新草稿，不要等到全部问题问完之后才整理文档。**

## **Step 3.4：需求分类与结构化**

需求规范化

**目的：将前面讨论得到的零散需求，整理成规范、清晰、具有层次结构的需求体系。**

前面 Step 3.3 解决的是「通过讨论获得足够的信息」。

现在则要解决「如何将这些信息整理成规范的需求」。

### **AI 应该做什么？**

首先，AI 应该对需求进行分类。

我建议至少分成以下六类：

| 需求类别       | 具体内容             | 示例               |
| ---------- | ---------------- | ---------------- |
| 功能需求（FR）   | 软件需要提供哪些功能       | 用户可以生成试卷         |
| 非功能需求（NFR） | 软件需要达到什么质量要求     | 数据不能轻易丢失         |
| 业务规则（BR）   | 软件必须遵守什么业务逻辑     | 已提交试卷不能继续修改答案    |
| 数据需求（DR）   | 需要记录、管理和处理哪些业务数据 | 保存试卷、题目、答案和成绩    |
| 外部接口需求（IR） | 需要与哪些外部系统或服务交互   | 调用模型 API 生成试题    |
| 约束条件（CON）  | 软件开发和运行有什么限制     | 仅支持个人使用，数据优先本地保存 |

不同类别之间可能有关联，不需要为了分类而重复描述同一项需求。

其次，AI 应该对功能需求进行层次拆解。

例如：

**功能模块：试卷管理**

FR-001：创建试卷

FR-002：编辑试卷

FR-003：删除试卷

FR-004：查看历史试卷

每个功能需求还可以继续细化为用户场景、具体行为和验收标准。

第三，AI 应该为需求分配唯一编号。

例如：

- FR-001：创建试卷。
- FR-002：编辑试卷。
- BR-001：试卷提交规则。
- NFR-001：试卷数据持久化要求。

后面架构设计、开发任务拆分和测试都可以引用这些编号。

### **用户需要提供什么？**

主要是确认 AI 整理后的内容是否符合自己的真实意图。

例如：

- AI 有没有理解错某个功能？
- 两个功能是否应该合并？
- 某些功能是否属于一个独立模块？
- 某条业务规则是否符合自己的实际使用习惯？

### **特别需要增加：需求状态管理**

建议让 AI 为每项重要信息标记状态：

| 状态    | 含义                |
| ----- | ----------------- |
| 已确认   | 用户明确认可            |
| 建议待确认 | AI 提出了方案，但用户还没有批准 |
| 合理假设  | 为了推进工作暂时采用的假设     |
| 待讨论   | 存在歧义或缺少信息         |
| 暂不纳入  | 已明确不在当前范围内        |

这样可以避免 AI 把自己推测的内容变成正式需求。

**本步骤产物：** 结构化需求清单、需求分类、需求编号、需求状态表。

## **Step 3.5：需求范围与优先级管理**

核心工作阶段

这一步应该作为第三阶段的独立工作，而不是简单地在需求文档最后添加一个优先级字段。

因为很多个人软件开发项目失败，不是因为 AI 不会写代码，而是因为：

- 功能越想越多。
- 第一版迟迟不能完成。
- 很多功能其实并不重要。
- 需求之间依赖复杂。
- 开发过程中不断增加新需求。

所以必须让 AI 帮助用户进行严格的范围管理。

### **AI 应该做什么？**

**1. 判断哪些需求属于核心功能。**

例如，试卷生成与批改系统：

核心流程可能是：

出卷 → 作答 → 交卷 → 判分。

如果没有这条流程，软件就无法实现最主要的价值。

而复杂的成绩分析、学习报告、错题统计，可能都可以后续增加。

**2. 对需求进行优先级排序。**

建议个人开发先使用简单的 MoSCoW 方法：

| 优先级         | 含义                 |
| ----------- | ------------------ |
| Must Have   | 没有它，第一版就无法实现核心价值   |
| Should Have | 很重要，但可以通过暂时的简单方案替代 |
| Could Have  | 有价值，但不影响第一版核心使用    |
| Won't Have  | 当前明确不做，未来也可能考虑     |

AI 应该结合以下因素进行建议：

- 对核心问题的解决价值。
- 是否属于完整业务流程的必要部分。
- 开发复杂度。
- 对其他功能的依赖。
- 技术风险。
- 是否可以通过简单方式替代。

但 AI 对开发成本和技术风险的判断只能作为初步估计，后续技术可行性分析还需要进一步验证。

**3. 定义 MVP 和版本范围。**

建议针对增量开发模型，采用三个层次的范围管理：

第一层：MVP / 首个可用版本

**必须详细定义**

必须确定完整的核心流程、必要功能、业务规则和验收条件。

第二层：后续近期增量

**明确目标与主要需求**

可以明确功能模块、价值、优先级和依赖，但具体实现细节允许在进入对应迭代前继续细化。

第三层：未来扩展

**保留想法，不急于细化**

记录未来可能需要的功能，避免提前投入大量需求分析成本。

这点非常重要：

**增量开发不是要求一开始就将整个软件的全部需求确定下来，而是要让第一个增量的需求足够清楚，并对后续增量保留合理的规划。**

**4. 明确不做项（Out of Scope）。**

让 AI 不仅列出需要做什么，还列出当前明确不做什么。

例如：

- 第一版不支持多人协作。
- 暂不支持移动端专用客户端。
- 暂不支持复杂的学习数据分析。
- 暂不支持多个模型自由切换。

不做项可以避免 AI 在后续开发时擅自扩大需求。

### **用户需要回答什么问题？**

这一部分需要用户做出比较多的产品取舍。

AI 可以询问：

1. 如果第一版不包含某个功能，用户是否依然愿意使用这个软件？
2. 哪些功能是解决核心问题不可缺少的？
3. 哪些功能可以通过人工操作暂时替代？
4. 哪些功能只是用户觉得以后可能有用？
5. 有没有功能虽然重要，但是开发成本很高？
6. 第一版用户最希望尽快体验到什么？

我特别建议增加一个问题：

> 假设第一版只能实现 5 个功能，用户最希望保留哪 5 个？为什么？

它可以有效帮助用户识别真正重要的功能。

**本步骤产物：** MVP 范围、需求优先级、版本路线、明确不做项、功能依赖清单。

## **Step 3.6：需求细化与验收标准制定**

核心工作阶段

这一步要回答一个问题：

**目前整理出来的需求，是否已经具体到后续 AI 能够根据它进行设计和开发？**

例如：

原始需求：

> 支持用户在线答题。

这个需求仍然太模糊。

AI 应该进一步将它细化。

| 细化维度    | 应明确的内容              |
| ------- | ------------------- |
| 用户与前置条件 | 用户是否需要进入一份有效的试卷？    |
| 输入      | 用户如何填写答案？           |
| 正常行为    | 系统如何记录和展示作答内容？      |
| 数据规则    | 答案何时保存？如何区分未作答与空答案？ |
| 边界情况    | 用户切换题目、刷新页面怎么办？     |
| 异常行为    | 网络中断时怎么办？           |
| 结束行为    | 交卷后如何处理？            |
| 验收标准    | 怎样证明这个功能已经正确实现？     |

### **AI 应该做什么？**

建议 AI 对每项 Must Have 需求至少进行以下检查：

1. 是否明确功能目标？
2. 是否明确用户操作？
3. 是否明确系统响应？
4. 是否明确业务规则？
5. 是否明确正常场景？
6. 是否明确重要异常和边界场景？
7. 是否有可验证的验收标准？

然后为每项需求生成验收条件。

可以采用 Given-When-Then（前置条件—触发行为—预期结果）的格式。

例如：

**FR-005：提交试卷**

**场景：用户成功提交试卷**

- Given：用户已经进入一份有效试卷，并且有已保存的作答记录。
- When：用户点击提交试卷。
- Then：系统保存最终答案，将试卷作答状态变更为已提交，并且用户不能继续修改本次作答。

可验证的验收条件

如果用户暂时不确定某项业务规则，AI 应该向用户提问，而不是自己决定。

例如：

> 用户提交试卷后，是否允许重新打开并修改答案？

这是产品规则，需要用户确认。

### **非功能需求也需要验收标准**

例如：

- 试卷草稿需要在刷新页面后恢复。
- 网络异常时不能静默丢失已保存的答案。
- AI 生成的试题必须经过结构和业务规则核验。
- API Key 不得明文写入代码仓库。

某些性能和 AI 质量指标可能暂时无法确定具体数值，这种情况下可以先记录待验证指标，将数值确定安排到技术验证阶段。

**本步骤产物：** 详细需求说明、业务规则、异常场景、验收标准、需求与验证的关联表。

## **Step 3.7：需求完整性、一致性与合理性审查**

质量保障阶段

这一步我非常建议用户单独保留。

因为前面 AI 一直在帮用户完善文档，如果最后让它简单地总结一次，很可能只是重复之前自己的判断。

应该要求 AI 在这一轮改变角色，成为一个严格的需求审查者。

### **AI 应该做什么？**

建议从以下八个角度审查：

| 检查维度 | 重点检查内容             |
| ---- | ------------------ |
| 完整性  | 是否遗漏核心功能和必要场景？     |
| 准确性  | 是否真正符合用户表达的意图？     |
| 一致性  | 不同需求之间有没有相互矛盾？     |
| 清晰性  | 是否存在模糊、歧义的表达？      |
| 可验证性 | 是否能够通过测试确认功能完成？    |
| 可行性  | 是否存在明显无法实现或高风险的要求？ |
| 合理性  | 是否存在不必要的复杂功能？      |
| 可追溯性 | 是否能追溯到原始需求和目标？     |

这里还有一个很重要的工作：

**让 AI 检查需求之间的依赖关系。**

例如：

如果支持修改题目，那么就需要考虑修改后的试题是否影响已经生成的试卷；如果允许删除试卷，那么又需要考虑历史作答记录如何处理。

AI 应主动寻找这种关联，而不是只孤立地检查每个功能。

### **可以让 AI 扮演不同的审查角色**

不需要真的使用多个 Agent，只要在审查过程中切换视角即可：

- 产品经理：检查功能是否真正解决用户问题。
- 用户：检查操作是否符合真实使用习惯。
- 测试工程师：检查需求是否能够被测试。
- 软件架构师：检查是否存在明显的技术约束和依赖问题，但暂不替代后续架构设计。
- 安全审查者：检查数据隐私、权限和危险操作是否考虑充分。

### **用户需要做什么？**

用户需要处理 AI 提交的审查报告：

- 纠正 AI 对需求的误解。
- 确认建议删除或延后的功能。
- 决定是否接受某些简化方案。
- 对重大业务规则作出最终决定。

**本步骤产物：** 需求审查报告、修订后的需求文档、未解决问题清单。

## **Step 3.8：需求基线确认与阶段交接**

阶段完成与交付

前面的工作完成后，AI 不应该只是告诉用户「需求分析已完成」。

它需要形成正式的阶段交付。

### **AI 应该做什么？**

汇总最终需求，并进行一次交付前检查：

1. 核心需求是否都已经确认？
2. MVP 和当前增量范围是否明确？
3. 不做项是否明确？
4. 核心功能是否具有验收标准？
5. 是否还有阻塞性歧义？
6. 是否与 Step 2.5 的项目执行流程一致？
7. 是否满足本阶段的门禁条件？

随后生成完整的正式文档。

### **用户需要做什么？**

主要是最终审查与确认：

- 是否符合自己的真实想法？
- 是否遗漏了重要功能？
- 是否存在不合理的功能？
- 第一版范围是否可以接受？
- 是否同意进入产品设计阶段？

**本步骤产物：** 正式的 `REQUIREMENTS.md`，以及必要的产品待办列表和决策记录。

# **四、整个过程中，AI 究竟应该询问用户什么？**

上面分步骤介绍了提问内容。这里我再把所有应该考虑的用户信息整合成一张通用问题清单。

这张表非常适合以后放到用户的通用需求分析工作规范中，作为 AI 的提问参考库。

但注意：这不是要求 AI 每个项目都问完所有问题，而是让 AI 根据项目类型和已有信息判断哪些问题有必要提出。

| 信息类别  | AI 需要了解的内容      | 示例提问                     |
| ----- | --------------- | ------------------------ |
| 项目目标  | 核心问题和期望结果       | 做这个软件最主要想解决什么问题？         |
| 用户范围  | 用户类型、人数、角色      | 只有用户自己使用，还是多人使用？         |
| 使用场景  | 使用环境、频率、操作流程    | 用户通常在什么情况下使用？            |
| 当前痛点  | 目前的工作方式及其问题     | 现在是如何解决这个问题的？            |
| 功能需求  | 需要完成的业务操作       | 用户需要通过软件完成哪些事情？          |
| 交互行为  | 输入、输出、操作反馈      | 操作完成后希望看到什么结果？           |
| 业务规则  | 权限、状态、操作限制      | 什么情况下允许修改或删除？            |
| 数据需求  | 数据来源、存储、管理      | 哪些信息必须保存？是否需要导出？         |
| AI 行为 | AI 能力、工具操作和人工干预 | AI 可以自主操作到什么程度？哪些操作需要确认？ |
| 异常情况  | 失败、错误、恢复        | 网络中断或模型失败时怎么办？           |
| 非功能需求 | 性能、安全、可靠性等      | 是否有响应速度和数据安全要求？          |
| 平台环境  | 设备、系统、网络        | 只在电脑使用，还是需要手机访问？         |
| 外部依赖  | API、第三方服务、数据源   | 是否必须接入某个外部服务？            |
| 优先级   | 核心功能与次要功能       | 第一版最不能缺少的功能是什么？          |
| 范围边界  | 版本规划与不做项        | 哪些功能可以明确推迟？              |
| 验收标准  | 预期行为和成功条件       | 怎样才能证明这个功能符合用户的预期？       |
| 约束条件  | 预算、时间、隐私和其他限制   | 是否有成本、数据存储或部署方面的限制？      |

# **五、不同开发模型下，第三阶段应该如何变化？**

这一部分尤其重要，因为用户正在建立的是一套通用开发方案，而不是只针对敏捷开发。

AI 应根据第二阶段和 Step 2.5 的结果，调整第三阶段的工作重点和信息深度。

| 开发模型 | 需求分析的重点              | 需求文档应该达到的程度           |
| ---- | -------------------- | --------------------- |
| 瀑布模型 | 完整分析当前项目范围内的需求，明确边界  | 约定范围内尽可能完整、详细，建立需求基线  |
| 敏捷开发 | 建立产品目标、用户故事和产品待办列表   | MVP 和近期迭代详细，远期需求允许粗略  |
| 增量开发 | 明确每个增量的目标、范围、依赖和验收标准 | 首个增量详细，后续增量按计划逐步细化    |
| V 模型 | 将每项需求与验证方法建立对应关系     | 需求和验收条件具有明确追溯关系       |
| 螺旋模型 | 优先分析重大风险相关需求和约束      | 风险相关需求深入分析，未知内容标记为待验证 |
| 原型模型 | 识别需要通过原型反馈才能确定的需求    | 已确认的需求和待验证的体验假设分开管理   |

例如，用户选择增量开发。

AI 就不应该要求用户现在把未来所有功能都定义到非常详细。

它应该：

- 先完整定义第一版核心需求。
- 为后续增量明确功能目标和大致范围。
- 将未明确的功能保留为待办。
- 在进入下一轮增量前，再进行相应的需求细化。

这才是真正的开发模型适配。

# **六、第三阶段最终应该生成什么文档？**

我不建议把八个步骤的所有过程对话都放进最终需求文档。

用户需要将「分析过程记录」和「最终需求产物」分开。

我建议采用以下文档结构。

**第三阶段最终交付文件**

**REQUIREMENTS.md**

核心必需

正式需求规范，记录项目目标、功能需求、非功能需求、业务规则、范围、优先级、验收标准等。

**PRODUCT\_BACKLOG.md**

条件适用

适用于敏捷、增量开发，记录功能列表、优先级、迭代归属、依赖和后续待办。

**REQUIREMENT\_TRACEABILITY.md**

条件适用

关联原始需求、正式需求编号、验收标准和后续测试。小项目可以直接整合到 REQUIREMENTS.md。

**REQUIREMENT\_REVIEW\.md**

建议保留

记录需求完整性审查、阻塞问题、风险、假设和未决事项。

其中，`REQUIREMENTS.md` 是最重要的，其他文件根据项目规模和开发模型决定是否独立创建。

## **REQUIREMENTS.md 推荐目录**

```
REQUIREMENTS.md

1. 项目背景与目标
2. 目标用户与使用场景
3. 项目范围
   3.1 MVP 范围
   3.2 首版功能范围
   3.3 后续版本范围
   3.4 明确不做项

4. 功能需求
   4.1 功能模块
   4.2 具体功能
   4.3 用户故事 / 用例
   4.4 业务规则

5. 非功能需求
   5.1 性能
   5.2 安全
   5.3 可靠性
   5.4 易用性
   5.5 可维护性

6. 数据与外部接口需求

7. 需求优先级与版本规划

8. 功能验收标准

9. 需求依赖关系

10. 约束条件

11. 风险、假设与待确认事项

12. 需求追溯关系
```

这里不要求每个栏目都有大量内容。没有必要的栏目标记为不适用即可。

# **七、AI 与用户之间的提问机制，应该如何设计？**

我认为这部分应该写入用户的通用 AI 工作规范，因为它决定了整个阶段的协作效率。

不要只告诉 AI：

> 如果需求有不清楚的地方，请询问我。

这句话太简单了，AI 不知道什么情况应该问、什么时候应该停止问，也不知道应该如何提出问题。

我建议用户明确以下规则。

## **规则 1：AI 主动发现问题，而不是被动等待用户补充**

AI 需要自己分析：

- 哪些需求表述不清楚？
- 哪些操作缺乏业务规则？
- 哪些异常场景尚未定义？
- 哪些功能存在依赖？
- 哪些需求可能不合理？
- 哪些内容需要用户做出取舍？

不能把发现问题的工作全部交给用户。

## **规则 2：每次提问都需要提供上下文**

不建议 AI 只问：

> 是否支持多人使用？

建议它这样问：

**需要确认：系统是否需要支持多个用户？**

目前初始需求只体现了个人使用场景，但这个决定会影响未来的用户身份、数据隔离和权限设计。

A. 只供自己使用

B. 未来可能有多个用户，但暂不做协作

C. 第一版就支持多人和数据隔离

D. 目前不确定，希望先比较方案

提交回答

这是提问形式示例，实际项目中由 AI 根据项目情况生成。

这样的提问更容易让用户做决定。

## **规则 3：AI 应该提供合理的推荐方案**

用户不是每个领域都懂。

有些问题用户可能不知道应该怎么回答。

例如：

> 第一版需要支持完整的复杂权限体系吗？

AI 不应该只是等用户做选择。

它应该结合项目实际情况分析，告诉用户：

- 方案 A 的优缺点。
- 方案 B 的优缺点。
- 自己更推荐哪种方案。
- 为什么这么推荐。
- 如果暂时不决定，会影响后续什么工作。

但最终决定权仍然在用户手上。

## **规则 4：严格控制无效提问**

AI 不应该为了完整性，提出大量没有必要的问题。

例如：

一个完全本地运行的个人工具，如果没有多人协作需求，就不需要花费大量时间讨论复杂的角色权限体系。

它应该判断：

- 是否影响核心功能？
- 是否影响本阶段输出？
- 是否影响后续设计？
- 是否存在无法撤销的风险？

如果没有，就允许暂时采用合理假设或推迟讨论。

## **规则 5：讨论结果必须及时写入文档**

每次回答后，AI 都要更新：

- 已确认需求。
- 需求状态。
- 相关业务规则。
- 新增的待确认事项。
- 受影响的其他需求。

不能只把结果留在聊天记录里。

# **八、用户在这个阶段到底应该怎么参与？**

我认为用户应该重点扮演四种角色。

| 角色    | 用户需要做什么             |
| ----- | ------------------- |
| 需求提供者 | 描述真实想法、实际场景和期望效果    |
| 业务决策者 | 确认功能行为、业务规则及需求取舍    |
| 产品负责人 | 决定功能优先级、MVP 和不做项    |
| 最终验收者 | 判断整理后的需求是否符合自己的真实意图 |

用户不需要主动编写规范的需求文档，也不需要使用专业软件工程术语。

例如，用户只需要告诉 AI：

> 我希望在交卷后，如果发现某道题有问题，可以修改题目，然后重新计算成绩。

AI 就应该进一步问：

- 修改题目后，所有学生的成绩都要重新计算吗？
- 之前的作答记录是否保留？
- 是否需要保留修改前的题目版本？
- 重新判分后是否允许再次人工调整？

这些问题由 AI 发现和提出，用户只需要根据实际需要回答。

**用户负责提供真实业务知识，AI 负责把这些知识转化成工程上清晰的需求。**

另外，用户可以提供一些比文字描述更有效的材料：

- 当前使用的 Excel 表格。
- 现有软件的截图。
- 真实操作过程。
- 参考软件或网站。
- 典型输入和预期输出。
- 真实业务数据的脱敏示例。
- 用户认为不合理的使用体验。

AI 可以从这些材料中提取需求，减少反复口头描述。

# **九、第三阶段的最终门禁应该如何设定？**

我建议用户为第三阶段设置一套明确的完成条件。

## **第三阶段验收清单**

以下是建议的通用门禁。不是每个项目都必须使用所有条目，但必须说明不适用的原因。

**检查进度**

# **0/13**

已经明确软件的核心目标和用户范围

已分析核心使用场景和业务流程

原始需求均已识别、归类，没有无故遗漏

核心功能已拆分成清晰、可理解的需求

核心业务规则和重要异常场景已经明确

已明确 MVP、首版范围和不做项

需求优先级和重要依赖关系已经明确

核心需求具有可验证的验收标准

非功能需求、数据要求和项目约束已合理处理

未知事项、假设和风险均已标记

需求与原始需求及项目开发流程具有追溯关系

已完成独立审查，并解决所有阻塞性问题

用户已经审查并确认需求基线

勾选仅用于帮助用户检查，不代表系统已经自动审核文档。

真正的阶段通过条件应该是：

- MVP 和当前开发范围没有阻塞性歧义。
- 核心功能可以理解、可以设计、可以验证。
- 没有未处理的重大需求冲突。
- 重要假设和风险有明确处理方案。
- 用户已经确认正式需求基线。

对于增量开发，后续版本的需求不需要全部详细化。只要已经明确记录并不影响当前增量即可。

# **十、额外建议：需求分析不要和后续需求变更管理混为一谈**

这是最后一个很值得用户提前考虑的问题。

第三阶段完成，并不代表需求以后不能变化。

尤其是采用敏捷或增量开发模型，后续实际使用软件时，肯定还会出现新想法和需求调整。

因此，我建议在整个开发体系中区分两件事情：

**第三阶段：需求基线建立。**

负责将初始想法转化为合理的正式需求，并确认当前版本的范围。

**后续阶段：需求变更管理。**

当出现新想法、缺陷或需求变化时，让 AI 判断属于哪一种：

| 类型         | 处理方式          |
| ---------- | ------------- |
| 原有需求理解不正确  | 修正原需求         |
| 原有功能没有实现正确 | 作为缺陷处理        |
| 新增功能       | 进入产品待办列表      |
| 业务规则发生变化   | 评估影响并更新需求     |
| 优先级发生变化    | 调整后续开发计划      |
| 重大方向变化     | 重新评估整体需求及开发流程 |

不能因为每次想到一个新功能，就直接让 AI 修改代码。

AI 应该先判断它对现有需求、架构、开发计划和测试的影响。

# **十一、最终我建议确定的第三阶段设计**

浓缩结构：

| 序号  | 工作环节         | AI 核心职责        | 用户核心职责      |
| --- | ------------ | -------------- | ----------- |
| 3.1 | 项目上下文读取与流程适配 | 读取资料，确定执行方案    | 补充缺失背景      |
| 3.2 | 原始需求诊断       | 识别缺失、歧义、冲突     | 回答关键问题      |
| 3.3 | 需求获取与深入分析    | 主动访谈、分析场景和功能   | 提供业务知识和使用习惯 |
| 3.4 | 需求分类与结构化     | 分类、拆解、编号和记录状态  | 确认整理结果      |
| 3.5 | 范围与优先级管理     | 分析 MVP、版本和功能依赖 | 做出优先级及范围取舍  |
| 3.6 | 需求细化与验收标准制定  | 明确行为、规则和验收条件   | 确认预期结果      |
| 3.7 | 完整性与一致性审查    | 独立审查并提出修订建议    | 审查争议和修改方案   |
| 3.8 | 需求基线确认与交接    | 生成正式文档和交接记录    | 确认需求基线      |

**第三阶段最重要的设计原则有三个：**

1. **AI 不能只是文档生成器，而应该是主动的需求分析者。** 它要主动发现问题、提出问题、补充问题，而不是等用户把所有需求都讲清楚。
2. **需求分析不是追求文档越完整越好，而是追求当前开发范围内的信息足够明确。** 尤其是增量开发，不应该过早分析未来所有功能。
3. **最终需求文档必须能够成为后续 AI 产品设计、架构设计、任务拆分和测试的可靠依据。** 后续阶段应该能够追溯每项设计和开发任务来自哪条需求。

这样，第三阶段就不再是传统意义上简单的需求分析，而是一套真正适合 AI Vibe Coding 的、可以反复使用的需求工程工作流。
