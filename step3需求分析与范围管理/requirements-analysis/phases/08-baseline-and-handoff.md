# 阶段 08：需求基线确认与阶段交接

## 目标

形成正式、可交付、可追溯的需求基线，并由用户明确确认。

不能只告诉用户“需求分析已完成”。要说明完成了什么、还有什么没定、下一阶段依赖什么。

## 1. 交付前检查

逐项确认：

1. 核心需求是否都已经确认？
2. MVP 和当前增量范围是否明确？
3. 明确不做项是否具体、有原因？
4. 核心功能是否都有可验证的验收标准？
5. 是否还有阻塞性歧义或未解决冲突？
6. 是否与 `DEVELOPMENT_APPROACH.md` 中的项目流程和门禁一致？
7. 是否满足本阶段的门禁条件？

任一问题无法回答，回到对应阶段修正。

## 2. 生成正式文档

按项目规模和开发模型生成：

| 文件 | 何时生成 | 内容要求 |
| --- | --- | --- |
| `REQUIREMENTS.md` | 始终 | 正式需求规范，按 [TEMPLATE.md](../TEMPLATE.md) 生成 |
| `PRODUCT_BACKLOG.md` | 敏捷、增量项目 | 功能列表、优先级、迭代归属、依赖、后续待办 |
| `REQUIREMENT_TRACEABILITY.md` | 大型项目 | 原始需求、正式需求、验收条件、后续测试的追溯；小项目并入 `REQUIREMENTS.md` 第 12 节 |
| `REQUIREMENT_REVIEW.md` | 建议保留 | 审查问题、阻塞项、风险、假设、未决事项和处理结果 |

规则：

- 不要把完整访谈过程复制进需求文档。需求文档只保留结论、决策依据和必要的来源。
- 过程性讨论、被否决的方案和详细问答放在审查记录或决策记录中。
- 没有内容的章节写“不适用”并说明原因，不为了填满模板编造内容。
- 文档中的编号、状态、优先级和验收条件必须互相一致。

## 3. 提交用户验收

向用户提交以下内容：

- 已确认需求摘要；
- MVP 和首版范围；
- 明确不做项；
- 核心验收标准；
- 需求优先级和版本规划；
- 关键依赖；
- 待确认事项、暂定假设、暂缓事项和风险；
- 需要下一阶段重点关注的内容；
- 一个明确问题：是否可以进入下一阶段。

提交时用用户能理解的语言，不要求用户阅读全部文档或理解需求工程术语。

## 4. 基线确认

用户确认后：

- 把文档版本标记为基线版本；
- 记录确认日期和确认范围；
- 明确哪些内容仍允许在后续阶段继续细化；
- 明确哪些内容属于基线，变更需要走变更管理。

基线不是“以后永远不能改”，而是“改变需要有意识地评估影响”。

## 5. 需求变更的边界

本阶段完成后，需求仍可能变化。后续出现新想法、缺陷或调整时，先判断类型，不直接改代码或静默改需求：

| 类型 | 处理方式 |
| --- | --- |
| 原有需求理解不正确 | 修正原需求，并检查受影响的验收条件和设计 |
| 原有功能没有按需求实现 | 作为缺陷处理，不改需求定义 |
| 新增功能 | 进入产品待办列表，评估优先级和版本归属 |
| 业务规则变化 | 评估对需求、数据、验收和后续设计的影响 |
| 优先级变化 | 调整版本规划和开发顺序 |
| 重大方向变化 | 重新评估整体需求、范围和开发流程 |

变更管理不属于本技能的执行范围；本阶段只负责建立基线并说明边界。

## 6. 阶段交接

交接给下一阶段时，明确：

- 下一阶段可以依赖哪些已确认需求；
- 哪些需求还需要继续细化；
- 哪些假设和风险需要下一阶段验证；
- 哪些内容属于后续版本，不在当前设计范围内；
- 需求编号和追溯关系如何继续使用。

不替下一阶段做界面设计、技术选型或任务拆分。

## 完成标准

- 交付前七项检查全部通过，或有明确说明。
- `REQUIREMENTS.md` 已按模板生成并放在约定路径。
- 条件适用的 `PRODUCT_BACKLOG.md`、`REQUIREMENT_TRACEABILITY.md` 已生成或说明并入位置。
- `REQUIREMENT_REVIEW.md` 已记录审查问题和处理结果。
- 用户已收到需求摘要、范围、不做项、验收标准、依赖、假设和风险。
- 用户明确确认需求基线。
- 文档中没有未处理的阻塞性歧义或冲突。
- [CHECKLIST.md](../CHECKLIST.md) 全部通过，或对“不适用”项有说明。

完成后向用户说明：本阶段已结束，下一阶段应处理什么，以及哪些内容仍需保持关注。
