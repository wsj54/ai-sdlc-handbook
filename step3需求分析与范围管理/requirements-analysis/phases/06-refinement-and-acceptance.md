# 阶段 06：需求细化与验收标准制定

## 目标

回答一个问题：**当前整理出来的需求，是否已经具体到后续可以设计、可以开发、可以验收？**

模块名称、功能名称和一句描述通常不够。必须明确行为、规则、异常和可验证的结果。

## 1. 对每项 Must Have 需求做七项检查

| 检查项 | 要回答的问题 |
| --- | --- |
| 功能目标 | 这项需求为用户解决什么问题？ |
| 用户操作 | 谁在什么条件下做什么？ |
| 系统响应 | 系统接收什么、处理什么、返回或改变什么？ |
| 业务规则 | 有哪些权限、状态、条件和计算规则？ |
| 正常场景 | 最典型的一次使用如何完成？ |
| 异常与边界 | 失败、空数据、重复、超时、中断时怎么办？ |
| 验收标准 | 怎样证明这项需求已经正确实现？ |

七项中任一项缺失，需求就还没有细化到位。

Should Have 和 Could Have 可以按版本深度要求处理，不必在第一版全部细化到同一程度。

## 2. 细化维度

对每项核心需求，至少明确：

| 维度 | 应明确的内容 |
| --- | --- |
| 用户与前置条件 | 谁可以操作、开始前必须满足什么 |
| 输入 | 用户提供什么、从哪里来、是否必填、格式和范围 |
| 正常行为 | 系统按什么顺序做什么 |
| 数据规则 | 什么数据被创建、修改、删除、保存多久 |
| 边界情况 | 空值、重复、极端值、最大/最小、并发或重复操作 |
| 异常行为 | 失败、超时、权限不足、数据不存在时如何反馈和恢复 |
| 结束行为 | 操作完成后状态是什么、用户看到什么、下一步做什么 |
| 验收标准 | 可观察、可重复验证的结果 |

细化时不要滑向实现：

- 可以写“用户提交后数据必须保存并在刷新后恢复”；
- 不写“用 localStorage 保存”；
- 可以写“外部服务失败时核心功能仍可继续”；
- 不写“加一层降级适配器”。

## 3. 验收标准

核心需求使用 Given-When-Then 格式：

```text
场景：<能独立理解的场景名>
Given：<前置条件>
When：<触发动作>
Then：<可观察、可验证的结果>
```

规则：

- 一个场景只验证一个主要行为。
- `Then` 必须可观察，不写“系统正确处理”这类无法判断的结果。
- 正常、边界、异常分别写场景。
- 验收条件不写实现细节，不绑定具体技术。
- 一项需求可以有多条验收条件，编号为 `AC-xxx`。
- 验收条件要能交给另一个人或另一个 AI，在不看对话的情况下执行。

示例结构（不包含具体业务内容）：

```text
场景：<正常完成>
Given：<前置条件和已有数据>
When：<用户执行核心操作>
Then：<数据状态变化 + 用户可见结果 + 后续可执行的操作>

场景：<重复操作>
Given：<同一操作已经执行过>
When：<用户再次执行>
Then：<不会产生重复数据或重复副作用，并给出明确反馈>
```

## 4. 业务规则的处理

如果用户暂时不确定某项业务规则：

- 不要替用户决定；
- 把规则写成待确认问题，说明影响；
- 用户确认后再写入需求和验收条件；
- 未确认前，相关需求不能标为 `confirmed`，必要时标 `assumption` 并写明影响。

典型需要用户确认的规则：

- 已产生的数据能否修改或删除；
- 修改后历史数据是否重算；
- 哪些角色可以执行哪些操作；
- 重复操作是允许、拒绝还是合并；
- 失败后是否自动重试，重试次数和间隔；
- 是否需要保留操作历史或版本。

## 5. 非功能需求的验收标准

非功能需求同样需要验收方式，不能只写“要快”“要安全”。

| 类型 | 验收方式 |
| --- | --- |
| 可量化指标 | 写明指标、测量条件、测量方式 |
| 可观察行为 | 写明在什么情况下必须发生什么、不能发生什么 |
| 暂不能定数值 | 记录“待验证指标”，写明验证阶段和验证方法 |

常见可验收的非功能要求：

- 数据在刷新、重启或异常退出后不丢失；
- 失败时不能静默丢失已保存的数据；
- 权限隔离必须可观察地生效；
- 敏感信息不能出现在日志、代码仓库或导出文件中；
- 外部服务失败时，核心功能有明确的降级行为。

不要编造性能数字。用户没有要求且项目不需要时，写“不适用”并说明原因。

## 6. 需求与验证的关联

为核心需求建立映射：

| 需求编号 | 验收条件 | 验证方式 | 验证阶段 | 状态 |
| --- | --- | --- | --- | --- |
| FR-xxx | AC-xxx | 手工验收 / 自动化测试 / 演示 / 数据检查 | 开发后 / 发布前 / 后续技术验证 | `pending` |

说明：

- 验证方式是计划，不是测试用例设计。
- 性能、AI 质量等暂不能定的指标，验证阶段可以写后续技术验证。
- 每条 Must Have 需求至少有一条验收条件，否则不能进入基线。

## 7. 完成标准

- 每项 Must Have 需求通过七项检查。
- 每项核心需求都有输入、正常行为、规则、异常和结束行为。
- 每项核心需求至少有一条可执行的验收条件。
- 正常、边界、异常场景都有覆盖，或明确说明不适用。
- 非功能需求有验收方式，或明确标为待验证指标。
- 不确定的业务规则已交给用户确认，没有 AI 自行决定。
- 需求与验收条件、验证方式之间的映射已建立。

完成后直接进入 [07-review.md](./07-review.md)。
