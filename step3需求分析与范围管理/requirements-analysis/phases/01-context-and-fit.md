# 阶段 01：项目上下文读取与流程适配

## 目标

在分析需求之前，先确认三件事：

1. 这个项目是什么、为谁解决什么问题；
2. 本次需求分析应该做到什么程度；
3. 哪些信息已经有了，哪些还缺，哪些存在冲突。

不了解项目就直接分析需求，会把 AI 的想象写进用户的需求。

## 读取顺序

按下面的顺序读取，遇到不存在的内容就跳过，并记录“缺失”：

1. 用户明确指定的需求文档或路径；
2. `docs/01-原始需求/INITIAL_REQUIREMENTS.md`；
3. `docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md`；
4. 项目根目录的 README、AGENTS、CLAUDE、说明、笔记类 Markdown；
5. 依赖清单、目录结构、已有源码、测试目录、CI 和部署配置；
6. Git 历史（如果可用）。

每份输入记录：

| 项目 | 内容 |
| --- | --- |
| 路径 | [实际路径] |
| 日期或版本 | [文档中标注的日期 / Git 提交] |
| 回答了哪些问题 | [目标 / 用户 / 范围 / 约束 / 开发方式] |
| 局限性 | [未覆盖的内容、可能过期、只是草稿] |
| 与其他输入的关系 | [一致 / 冲突 / 补充] |

## 缺失输入的处理

找不到 `INITIAL_REQUIREMENTS.md` 或 `DEVELOPMENT_APPROACH.md` 时，不拒绝启动，也不虚构一份前置文档。用对话补齐最小信息：

- 想解决什么问题；
- 给谁用；
- 第一版大概做什么；
- 已知限制和不能接受的结果；
- 打算怎么开发（如果完全没有，按通用增量方式处理，并标 `assumption`）。

补齐的信息要写进文档的输入来源和待确认事项，不能假装它来自前置文档。

## 建立分析基线

在 `REQUIREMENTS.md` 开头先写清楚本次分析的基础：

| 维度 | 需要确认 | 来源 |
| --- | --- | --- |
| 项目名称 | 正式名称或暂定名称 | [来源] |
| 核心问题 | 软件要解决的主要问题 | [来源] |
| 项目目标 | 期望达到的结果，不是功能列表 | [来源] |
| 目标用户 | 谁使用、单用户还是多用户、是否有角色区分 | [来源] |
| 开发模型 | 瀑布 / 敏捷 / 增量 / V 模型 / 螺旋 / 原型 / 混合 | [DEVELOPMENT_APPROACH] |
| 本阶段位置 | 当前在第几个阶段、前面交付了什么 | [DEVELOPMENT_APPROACH] |
| 阶段门禁 | 本阶段必须满足哪些条件才能进入下一阶段 | [DEVELOPMENT_APPROACH] |
| 已有材料 | 哪些需求、约束、场景已经明确 | [输入清单] |
| 待补充信息 | 哪些内容缺失且会影响分析 | [缺口清单] |
| 待讨论问题 | 哪些内容需要用户做决定 | [问题清单] |

这一步只建立基线，不展开功能细节。发现输入之间冲突时，先登记，不静默选择其中一份。

## 开发模型适配

`DEVELOPMENT_APPROACH.md` 决定本阶段做到什么程度。默认规则如下，项目有专属流程时以其为准：

| 开发模型 | 本阶段重点 | 需求文档应达到的程度 |
| --- | --- | --- |
| 瀑布 | 完整分析约定范围内的需求，明确边界 | 范围内尽可能完整、详细，形成需求基线 |
| 敏捷 | 建立产品目标、用户故事和产品待办列表 | MVP 和近期迭代详细，远期需求允许粗略 |
| 增量 | 明确每个增量的目标、范围、依赖和验收标准 | 首个增量详细，后续增量按计划逐步细化 |
| V 模型 | 每项需求同步规划验证方法和验收条件 | 需求与验证条件有明确追溯关系 |
| 螺旋 | 优先分析与重大风险相关的需求和约束 | 风险相关需求深入分析，未知内容标为待验证 |
| 原型 | 识别必须通过原型反馈才能确定的需求 | 已确认需求与待验证体验假设分开管理 |
| 混合 | 按组件或阶段分别适配 | 不同部分允许不同深度，但要在文档中说明 |

补充规则：

- **增量开发不是一次性定义全部需求**。首个增量必须详细，后续增量写明目标、范围、依赖即可，进入对应迭代前再细化。
- 八步工作流可以合并、重复或跳过；跳过要在文档中写明原因。
- 不要求所有项目都产出同样厚度的文档。个人自用的小工具，不为每个小功能写完整用例。
- 开发模型缺失或不清楚时，按通用增量方式推进，并把这一点标为 `assumption`，在阶段 02 首轮提问中确认。

## 创建文档骨架

在约定路径创建 `REQUIREMENTS.md`，先填写：

- 文档信息（名称、版本、日期、当前阶段、输入来源、阶段状态）；
- 状态说明和编号约定；
- 项目背景与目标；
- 本阶段分析范围与开发模型适配；
- 输入清单和缺口清单。

未确认的内容不要提前填。骨架的作用是让后续每轮讨论都有落点，不是先写一份完整文档再让用户签字。

## 首轮问题

阶段 01 只问会阻塞分析计划的问题，例如：

- 两份输入文档对项目目标或范围的描述不一致，以哪份为准？
- 开发模型或项目流程缺失，是否按通用增量方式推进？
- 项目明显存在多个用户角色，但原始需求只描述了单一用户，是否需要在本阶段确认用户范围？
- 输入材料中有一项内容可能决定整个第一版的范围，是否先讨论？

不要在这一步展开功能细节、业务规则或界面问题；它们属于后续阶段。

## 完成标准

- 输入清单完整，每份输入都有路径、日期、覆盖范围和局限。
- 缺失输入已通过对话补齐最小信息，或明确标为 `assumption` / `deferred`。
- 分析基线表已填写，核心问题、目标、用户和开发模型都有来源。
- 开发模型适配规则已写明，本次分析深度有依据。
- `REQUIREMENTS.md` 骨架已创建，文档信息和输入来源已填写。
- 阻塞分析计划的问题已提出，或明确记录为下一轮处理。

完成后直接进入 [02-diagnosis.md](./02-diagnosis.md)。
