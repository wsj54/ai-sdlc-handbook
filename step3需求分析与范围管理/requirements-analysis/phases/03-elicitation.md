# 阶段 03：需求获取与深入分析

## 目标

把“用户想要一个东西”，逐步问成“谁在什么情况下、输入什么、系统做什么、产生什么结果、失败时怎么办”。

这是本阶段最重要的环节。AI 不是替用户写需求，而是持续提问、分析回答、更新草稿，直到核心需求清楚。

## 需求空间的设计树

把待确认内容组织成一棵设计树，按 frontier 逐轮推进：

```text
需求空间
├── 用户与场景
│   ├── 用户类型与角色
│   ├── 使用目的与频率
│   ├── 使用环境与设备
│   └── 现有做法与痛点
├── 业务流程
│   ├── 正常路径
│   ├── 中断、撤销、重试、超时
│   └── 结束、回访、后续处理
├── 功能
│   ├── 模块划分
│   ├── 单项行为
│   └── 输入、输出、反馈
├── 业务规则与异常
│   ├── 前置条件与权限
│   ├── 状态变化
│   ├── 边界情况
│   └── 错误与恢复
├── 非功能需求
│   ├── 性能、可靠性、安全
│   ├── 易用性、兼容性、可维护性
│   └── 可用性、成本
├── 数据与外部依赖
│   ├── 数据来源、保存、导出、生命周期
│   ├── 敏感信息与访问控制
│   └── 外部服务、失败降级、成本
└── AI 行为（产品包含 AI 能力时）
    ├── 自主范围与人工确认
    ├── 失败、超限、质量不合格
    └── 人工修改与接管
```

每轮只问 frontier 上最阻塞的 1–4 个问题（默认 2–3 个）。回答后重新计算 frontier，再问下一轮。

## 3.1 用户与使用场景

| 维度 | 需要明确 |
| --- | --- |
| 用户类型 | 谁使用、有几种角色、是否需要区分权限 |
| 使用目的 | 用户用它解决什么问题、期望得到什么结果 |
| 使用场景 | 什么情况下打开软件、要完成什么任务 |
| 使用频率 | 高频、低频、特定场景、一次连续使用多久 |
| 使用环境 | 设备、操作系统、网络条件、使用场所 |
| 现有做法 | 目前如何完成、用什么工具、哪里最费时或最容易出错 |
| 使用习惯 | 操作偏好、不能接受的交互、必须保留的旧习惯 |

提问方向：

- 谁会使用？只有自己，还是有其他人？其他人是否看到或修改同一份数据？
- 现在这件事是怎么完成的？用表格、纸笔、聊天工具，还是靠记忆？
- 当前做法最麻烦、最容易出错或最耗时的环节是什么？
- 通常在什么设备、什么网络环境下使用？
- 一次使用大概多久？是每天用，还是偶尔用？
- 有没有“绝对不能改变”的操作习惯？

重点：**不仅要问用户希望软件有什么功能，还要问用户现在是怎么解决问题的。** 现有做法往往比功能清单更能暴露真实需求。

## 3.2 核心业务流程

让用户描述主要操作过程，再逐步拆解。每个流程至少明确：

| 要素 | 需要明确 |
| --- | --- |
| 发起者 | 谁发起、在什么条件下发起 |
| 前置信息 | 开始前必须已经存在什么 |
| 输入 | 用户提供什么、从哪里来 |
| 系统行为 | 系统在每一步做什么 |
| 中间结果 | 每一步产生什么、保存在哪里 |
| 下一步 | 什么条件下进入下一步 |
| 中断 | 用户离开、刷新、关闭、断网会怎样 |
| 撤销与重试 | 能否撤销、能否重复执行、重复执行会怎样 |
| 超时 | 是否有时间限制、超时后如何处理 |
| 结束状态 | 流程结束后数据和状态变成什么 |

提问方向：

- 正常走完一次，大概有哪几步？
- 哪一步最容易失败或被打断？
- 用户中途离开、刷新页面或断网时，已经做的内容会怎样？
- 操作能否撤销？撤销后哪些数据会恢复，哪些不会？
- 同一个操作能否重复执行？重复执行会不会产生重复数据或重复副作用？
- 流程结束后，用户还需要做什么？是否需要回看、修改或再次发起？

不能只分析正常流程。中断、撤销、重试、超时和失败，是需求最容易遗漏的部分。

## 3.3 功能需求分析

将软件功能拆分为模块，再把模块拆分成独立需求。

拆分标准：

- 能独立理解：不看模块名也知道它做什么；
- 能独立设计：后续可以单独做界面和交互；
- 能独立验证：可以写出验收条件；
- 不按页面拆、不按数据库表拆、不按代码模块拆。

每个模块至少明确：

- 模块目标；
- 包含哪些独立需求；
- 哪些是核心功能、辅助功能、管理功能、扩展功能；
- 与其他模块的输入输出关系。

不要停留在“管理”“处理”“支持”这类无法验证的模块名上。继续问：用户具体做什么、系统具体显示或改变什么。

## 3.4 业务规则与异常场景

对每个核心功能，按六个维度检查：

| 维度 | 检查内容 |
| --- | --- |
| 前置条件 | 什么情况下允许操作，什么情况下禁止 |
| 正常行为 | 正常情况下系统如何处理 |
| 边界情况 | 空数据、极端输入、重复数据、最大/最小值如何处理 |
| 异常情况 | 失败、超时、权限不足、数据不存在时如何反馈 |
| 状态变化 | 操作前后哪些数据或状态发生变化 |
| 用户反馈 | 用户应该看到什么提示、结果或下一步 |

提问方向：

- 谁可以做这个操作，谁不可以？
- 什么条件下允许，什么条件下禁止？
- 空数据、重复数据、超长输入、极端值分别怎么处理？
- 操作失败时，用户看到什么？能否重试？重试会不会重复执行？
- 操作前后，哪些对象的状态会变化？变化后是否影响历史数据？
- 是否需要通知、记录、审计或人工复核？
- 是否允许修改或删除已经产生的数据？修改后历史记录怎么办？

业务规则是产品规则，必须由用户确认。AI 可以提出候选规则，但不能自己决定。

## 3.5 非功能需求分析

非功能需求不是只有性能和并发，还包括整体质量：

| 类别 | 需要了解 |
| --- | --- |
| 性能 | 响应速度、处理时间、并发量、数据规模 |
| 可靠性 | 失败处理、数据恢复、稳定性、重复执行安全 |
| 安全性 | 身份认证、权限、敏感数据保护、危险操作确认 |
| 易用性 | 学习成本、操作步骤、错误提示、可发现性 |
| 兼容性 | 浏览器、设备、操作系统、网络条件 |
| 可维护性 | 后续扩展、配置修改、数据迁移 |
| 可用性 | 是否需要离线、是否需要持续在线、可接受的中断时长 |
| 成本 | 外部服务调用成本、存储成本、运行成本 |

规则：

- 不机械要求所有项目定义所有指标。
- 本地单用户工具可能不需要复杂并发指标，但通常仍需明确数据保存、备份和恢复。
- 区分三类：必须达到的指标、期望但暂不确定的指标、明确不适用的类别。
- 暂不能定数值的指标，记录为“待验证指标”，写明在哪个后续阶段验证，不编造数字。

## 3.6 数据与外部依赖分析

这一部分独立检查，因为数据和外部服务往往决定需求边界。

提问方向：

- 需要保存哪些数据？数据由谁创建、修改、删除？
- 数据来自用户输入、导入、外部服务，还是系统生成？
- 是否需要导入已有数据？是否需要导出？导出给谁、用来做什么？
- 数据保存多久？是否需要备份、恢复、迁移或清理？
- 是否包含个人信息、敏感信息或商业机密？谁可以访问？
- 是否需要调用外部 API、服务、模型或数据源？
- 外部服务失败、超时、限流或收费变化时，核心功能能否继续？
- 是否需要用户自备账号、密钥或额度？成本由谁承担？

只写业务需要和约束，不写表结构、接口协议、调用方式。

## 3.7 AI 行为与人工干预

产品包含 AI 能力时，单独检查这一维度；不包含时写“不适用”。

| 维度 | 需要明确 |
| --- | --- |
| 自主范围 | AI 可以自主做什么，哪些操作必须人工确认 |
| 输入与输出 | AI 接收什么、产出什么、产出给谁看 |
| 失败处理 | 超时、失败、输出不合规、质量不达标时怎么办 |
| 人工修改 | 用户能否修改、撤销、重做 AI 的结果 |
| 质量判断 | 谁判断结果是否合格，不合格如何处理 |
| 成本与限额 | 是否有调用次数、费用、时长限制 |
| 可追溯性 | 是否需要记录 AI 的依据、来源或操作历史 |
| 人工接管 | 什么情况下必须由人接管 |

提问方向：

- AI 是给建议、替用户执行，还是自动完成整件事？
- 哪些操作必须用户确认后才能继续？
- AI 结果不符合要求时，用户能做什么？能否重试、修改、转人工？
- 是否需要保留 AI 的输入、输出和操作记录？
- 是否有成本或调用次数上限？超限时如何表现？

同样只写产品行为要求，不写模型、框架或调用方式。

## 3.8 提问循环

每一步都按下面的循环推进：

1. AI 提出一个或一组同场景问题；
2. 说明为什么需要确认、有哪些可选答案、推荐哪一个；
3. 用户回答、补充或提出新想法；
4. AI 分析回答，立即更新需求草稿和状态；
5. AI 检查回答是否引入新的歧义、冲突、依赖或范围变化；
6. 重复，直到核心需求清楚。

规则：

- 每讨论清楚一组需求，就立即更新草稿，不等到全部问完。
- 用户回答后出现新问题时，先登记，再决定是否进入下一轮。
- 用户说“不知道”“还没想好”时，不逼答；标 `assumption` 或 `deferred`。
- 用户回答与之前的结论矛盾时，先指出差异，请其确认以哪条为准。
- 用户提出新功能时，先判断它属于当前范围、后续版本还是不做，不直接写进 MVP。
- 不追求问完所有维度，只问到“核心需求足够清楚”。

## 3.9 术语与场景压力测试

需求的模糊往往来自词语的模糊。

- 一个词只表达一个概念；同一个概念只用一个词。
- 用户使用多义词时，提出候选规范术语，请用户选择。例如“用户”“账号”“客户”是否指同一类对象。
- 用具体边界场景测试概念：“如果这种情况，算不算你说的 X？”
- 术语一旦确认，立即写入第 13 节术语表，不攒到最后。
- 不在文档中混用同义词，除非术语表明确说明二者关系。

## 3.10 提问参考库

下面是一张扫描表，不是必答清单。只问与当前项目相关、且会影响需求、范围或验收的问题。

| 信息类别 | 需要了解 | 提问方向 |
| --- | --- | --- |
| 项目目标 | 核心问题和期望结果 | 这个软件最主要想解决什么问题？怎样算解决？ |
| 用户范围 | 用户类型、人数、角色 | 只有自己用，还是有其他人？角色之间有什么区别？ |
| 使用场景 | 环境、频率、操作流程 | 通常在什么情况下使用？一次用多久？ |
| 当前做法 | 现有方式及其问题 | 现在如何完成？最麻烦、最容易出错的环节是什么？ |
| 功能需求 | 需要完成的业务操作 | 用户需要通过软件完成哪些事情？ |
| 交互行为 | 输入、输出、操作反馈 | 操作后希望看到什么结果？失败时看到什么？ |
| 业务规则 | 权限、状态、操作限制 | 什么情况下允许或禁止？谁能做、谁不能做？ |
| 数据需求 | 来源、保存、管理、导出 | 哪些信息必须保存？保存多久？是否需要导入导出？ |
| AI 行为 | 自主范围、人工干预、质量 | AI 可以自主做到什么程度？哪些操作需要确认？ |
| 异常情况 | 失败、错误、恢复、重复操作 | 服务失败、数据异常、重复提交时怎么办？ |
| 非功能需求 | 性能、安全、可靠性等 | 对速度、安全、稳定性有什么要求？ |
| 平台环境 | 设备、系统、网络 | 只在什么设备上使用？是否需要多端？ |
| 外部依赖 | 外部服务、数据源、成本 | 是否必须接入某个外部服务？失败时能否继续？ |
| 优先级 | 核心功能与次要功能 | 第一版最不能缺少什么？ |
| 范围边界 | 版本规划与不做项 | 哪些可以明确推迟或不做？ |
| 验收标准 | 预期行为和成功条件 | 怎样证明这个功能符合预期？ |
| 约束条件 | 预算、时间、隐私、合规 | 有哪些成本、时间、数据或合规限制？ |

使用规则：

- 这张表用于提醒 AI 不要漏掉信息维度，不是要求逐项提问。
- 能通过现有材料确认的内容，不要问用户。
- 已经明确且不影响当前判断的内容，不重复问。
- 问题过多时，只保留最阻塞的 1–4 个，其余记录到问题清单。

## 3.11 停止条件

同时满足以下条件时，结束本阶段：

- 核心用户类型、使用场景和现有做法已经清楚。
- 核心业务流程的正常路径和主要异常路径已经分析。
- 核心功能已经拆分到可独立理解、可独立验证的程度。
- 核心业务规则、状态变化和重要异常有结论或明确标记。
- 非功能需求、数据要求和外部依赖有结论或明确标记。
- AI 行为（如适用）的自主范围、失败处理和人工接管已经明确。
- 剩余问题不会阻塞范围划分和验收标准制定。
- 用户确认 AI 对核心需求的理解与自己的意图一致。

## 完成标准

- 六维分析（用户场景、流程、功能、规则异常、非功能、数据依赖）都有结论或“不适用”说明。
- 每条核心需求都有明确的用户、触发条件、输入、系统行为、结果和失败处理。
- 术语表已经建立，模糊术语已澄清。
- 决策记录自包含，能脱离对话读懂。
- 文档状态与用户回答一致，没有把 AI 推测写成确认。

完成后直接进入 [04-structuring.md](./04-structuring.md)。
