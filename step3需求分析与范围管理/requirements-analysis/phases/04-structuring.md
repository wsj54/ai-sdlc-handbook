# 阶段 04：需求分类与结构化

## 目标

把前面讨论得到的零散信息，整理成规范、清晰、有层次、可引用的需求体系。

阶段 03 解决“信息是否足够”，本阶段解决“信息如何组织”。

## 1. 需求分类

至少分成六类，按需使用，不必为每个项目建满所有类别：

| 类别 | 判断标准 | 编号 |
| --- | --- | --- |
| 功能需求 | 软件必须提供的业务行为 | `FR-xxx` |
| 非功能需求 | 软件必须达到的质量要求 | `NFR-xxx` |
| 业务规则 | 软件必须遵守的业务逻辑、权限、状态和操作限制 | `BR-xxx` |
| 数据需求 | 需要记录、管理、处理的数据及其生命周期 | `DR-xxx` |
| 外部接口需求 | 与外部系统、服务或数据源之间的业务交互 | `IR-xxx` |
| 约束条件 | 开发、运行、成本、合规等方面的限制 | `CON-xxx` |

分类规则：

- 一条需求只归一个主类别；跨类别用关联字段连接，不重复描述同一项内容。
- 只属于某个功能的业务规则，可以挂在功能需求下；跨功能、跨模块的规则，独立为业务规则。
- 数据需求写“需要什么数据、谁使用、保存多久、能否导入导出”，不写表结构。
- 外部接口需求写业务目的、输入输出、失败要求和约束，不写协议、接口签名和调用方式。
- 约束条件写限制，不写解决方案。

## 2. 功能需求层次拆解

按下面的层次组织：

```text
功能模块
└── 子模块（可选）
    └── 功能需求
        └── 场景 / 行为
            └── 验收条件
```

拆分标准：

- 能独立理解：名称和描述脱离上下文仍然清楚。
- 能独立设计：后续可以单独设计界面和交互。
- 能独立验证：可以写出至少一条可观察的验收条件。
- 粒度一致：同一层级的需求大小相近，不把“整个模块”和“一个按钮”放在同一层。

不要按页面、数据库表或代码结构拆分。需求拆分依据是用户行为和业务能力，不是实现结构。

拆完后检查：

- 是否还有“管理”“处理”“支持”“优化”这类无法验证的动词？
- 是否有需求只是模块名称，没有具体行为？
- 是否有需求包含多个互不相关的操作，应该继续拆？
- 是否有需求小到无法单独验收，应该合并？

## 3. 需求编号

- 每项正式需求分配唯一编号。
- 模块使用 `M-xxx`，用户故事或用例使用 `UC-xxx`，验收条件使用 `AC-xxx`。
- 编号前缀表示类别，序号不重复使用；删除的需求保留编号并标为失效，不让后续编号回填。
- 原始需求编号 `REQ-xxx` 继续保留，用于追溯，不重新编号。
- 依赖使用 `DP-xxx`，不做项使用 `OOS-xxx`。
- 后续设计、开发任务和测试应能通过编号反查需求。

编号只是索引，不承载含义。引用编号时必须同时写出结论本身。

## 4. 状态管理

每条需求只保留一个状态：

| 状态 | 含义 |
| --- | --- |
| `confirmed` | 用户明确确认 |
| `pending` | 存在歧义或缺少信息 |
| `conflict` | 与其他需求或约束矛盾，尚未解决 |
| `assumption` | 为推进工作暂时采用，等待确认 |
| `deferred` | 当前阶段或当前版本不处理 |

规则：

- AI 提出的方案只能进入 `pending` 或 `assumption`，不能写成 `confirmed`。
- 用户只回“按推荐”时，把推荐内容本身写成结论。
- 一个需求同时存在冲突和歧义时，先记 `conflict`。
- 状态变化要在决策记录中留下依据。
- 状态是“信息可信度”，不是“开发进度”；不要用“开发中”“已完成”等状态。

## 5. 术语表

建立并维护术语表：

| 术语 | 定义 | 不包含 / 易混淆 | 来源 |
| --- | --- | --- | --- |
| GL-001 [术语] | [一句话精确定义] | [与哪些词区分] | [用户确认 / 现有材料] |

规则：

- 一个术语只对应一个概念，一个概念只用一个术语。
- 定义写边界，不只写同义词。
- 用户使用模糊词或多义词时，提出候选术语并请用户确认。
- 术语确认后立即写入，不攒到最后。
- 需求正文、验收条件和后续文档使用同一套术语。

## 6. 用户确认

整理完成后，请用户确认：

- AI 有没有理解错某个功能？
- 两个功能是否应该合并或拆分？
- 某些功能是否属于独立模块？
- 某条业务规则是否符合实际使用习惯？
- 术语是否准确、是否符合用户日常说法？
- 是否有用户提过、但整理后消失的内容？

用户确认的是“整理结果是否符合真实意图”，不是让用户学习需求工程术语。

## 完成标准

- 所有正式需求都已分类，类别判断有依据。
- 功能需求已拆到可独立理解、可独立设计、可独立验证的粒度。
- 每条需求有唯一编号、来源、状态和关联关系。
- 术语表已建立，核心术语无歧义。
- 没有把同一内容在多个类别下重复描述。
- 用户已确认整理结果与真实意图一致。

完成后直接进入 [05-scope-and-priority.md](./05-scope-and-priority.md)。
