# 需求分析与范围管理检查清单

在宣告「需求分析与范围管理」阶段完成前逐项检查。

判定规则：

- **通过**：有明确证据，能指向 `REQUIREMENTS.md` 或相关文件的具体章节或条目。
- **不适用**：本项目确实没有该项内容，并在文档中写明原因。
- **失败**：任一项既没有证据，也没有说明不适用。

出现失败项时，回到对应阶段修正，不宣告阶段完成。

## 1. 输入与上下文

- [ ] 已读取用户指定的需求文档，或已找到 `INITIAL_REQUIREMENTS.md`。
- [ ] 已读取 `DEVELOPMENT_APPROACH.md`，或已通过对话确认开发方式并标为 `assumption`。
- [ ] 输入清单完整，每份输入都有路径、日期、覆盖范围和局限。
- [ ] 多份输入冲突时已登记，没有静默选择其中一份。
- [ ] 项目现状（依赖、目录、测试、Git、配置）已读取，用于减少提问。
- [ ] 项目核心问题、目标、目标用户和开发模型都有来源。
- [ ] 本阶段分析深度与开发模型一致，没有对增量项目强行定义全部未来需求。
- [ ] 缺失输入已通过对话补齐最小信息，没有虚构前置文档。

## 2. 原始需求诊断

- [ ] 原始输入中的每条需求都已提取，能追溯到原话或来源。
- [ ] 一条原话包含多个需求时已拆分，重复表达保留了差异。
- [ ] 每条需求都有初步类型：明确功能、隐含功能、非功能、业务规则、约束、未确认想法。
- [ ] 背景、痛点、目标没有被直接当成功能需求。
- [ ] 用户提到的实现方式没有被写成功能需求。
- [ ] 重复、矛盾、模糊、缺失步骤、依赖和必要缺口都已检查。
- [ ] 每个问题都有涉及需求、说明、影响和建议处理方式。
- [ ] 阻塞后续分析的问题已提出，或明确标为 `assumption` / `deferred`。

## 3. 需求获取

- [ ] 用户类型、角色、使用目的、场景、环境、频率和现有做法已明确。
- [ ] 已询问用户“现在如何解决问题”，不只询问想要什么功能。
- [ ] 核心业务流程的正常路径已拆解到每一步的发起者、输入、系统行为、结果和下一步。
- [ ] 中断、撤销、重试、超时和失败路径已分析，或说明不适用。
- [ ] 核心功能已拆到可独立理解、可独立设计、可独立验证的粒度。
- [ ] 每个核心功能的前置条件、正常行为、边界、异常、状态变化和用户反馈已检查。
- [ ] 业务规则由用户确认，没有 AI 自行决定。
- [ ] 非功能需求按类别检查过，明显不适用的类别已说明原因。
- [ ] 数据来源、保存、导入导出、生命周期、敏感信息已明确。
- [ ] 外部依赖的业务目的、失败要求和成本约束已明确，未展开技术方案。
- [ ] 产品包含 AI 能力时，自主范围、人工确认、失败处理、人工接管和成本限额已明确。
- [ ] 模糊术语已澄清，术语表已建立并持续更新。

## 4. 分类与结构化

- [ ] 需求已按功能、非功能、业务规则、数据、外部接口、约束分类。
- [ ] 一条需求只归一个主类别，跨类别用关联字段连接，没有重复描述。
- [ ] 功能需求按模块、子模块、需求、场景、验收条件形成层次。
- [ ] 没有按页面、数据库表或代码结构拆分需求。
- [ ] 没有停留在“管理”“处理”“支持”“优化”这类无法验证的表述。
- [ ] 每条正式需求有唯一编号、来源、状态和关联关系。
- [ ] 原始 `REQ-xxx` 编号保留，正式需求能追溯到原始需求。
- [ ] 每条需求只有一个状态，且与正文一致。
- [ ] AI 的推荐或推测没有被写成 `confirmed`。
- [ ] 用户已确认整理结果与真实意图一致，没有丢失用户提过的内容。

## 5. 范围与优先级

- [ ] 核心业务闭环已用一句话描述，并能对应到具体需求。
- [ ] 每条需求都有 MoSCoW 优先级。
- [ ] 每条需求都有且只有一个版本归属。
- [ ] MVP、近期增量、未来扩展三层范围已写明。
- [ ] MVP 的需求详细到可以设计、开发和验收。
- [ ] 后续版本只写到目标、范围、依赖，没有过度细化。
- [ ] 明确不做项具体、有原因、有重新评估条件。
- [ ] 因版本延后的内容和明确不做项已区分。
- [ ] 需求依赖、关键路径和外部依赖已识别。
- [ ] 范围取舍有用户确认，不是 AI 单方面判断。
- [ ] 没有“没有归属”或“顺便加入”的需求。
- [ ] 新增需求已按来源、归属、影响、代价处理，没有静默扩大范围。

## 6. 细化与验收

- [ ] 每项 Must Have 需求通过七项检查：目标、用户操作、系统响应、业务规则、正常场景、异常边界、验收标准。
- [ ] 每项核心需求都有用户与前置条件、输入、正常行为、数据规则、边界、异常、结束行为。
- [ ] 每项核心需求至少有一条 `AC-xxx` 验收条件。
- [ ] 验收条件使用 Given-When-Then，`Then` 可观察、可重复验证。
- [ ] 正常、边界、异常场景都有覆盖，或说明不适用。
- [ ] 验收条件没有绑定具体实现技术。
- [ ] 非功能需求有衡量方式或验收方式。
- [ ] 暂不能定数值的指标已标为待验证指标，并写明验证阶段。
- [ ] 不确定的业务规则已交给用户确认，没有自行决定。
- [ ] 需求与验收条件、验证方式之间的映射已建立。

## 7. 审查与一致性

- [ ] 已切换产品经理、用户、测试工程师、架构师、安全审查者五个视角。
- [ ] 每个审查角色都实际检查并记录了结论或检查依据，不是只写“无问题”。
- [ ] 完整性、准确性、一致性、清晰性、可验证性、可行性、合理性、可追溯性八个维度都检查过。
- [ ] 审查从原始材料重新出发，没有只重复之前的结论。
- [ ] 需求之间的依赖和影响已分析，包括修改、删除、状态变化和权限变化。
- [ ] 没有循环依赖或无法同时满足的规则，或有明确处理方式。
- [ ] 需求膨胀、重复功能和无法验收的功能已识别并交用户处理。
- [ ] 所有阻塞问题已解决，或用户明确同意以 `assumption` / `deferred` 处理并记录风险。
- [ ] 审查后的文档与 `REQUIREMENT_REVIEW.md` 一致。
- [ ] 重大修改在决策记录中写明了原因。

## 8. 文档自包含与边界

- [ ] 全文搜索 `Q\d`：没有 `Q1=A`、`Q2=B` 这类无法自解释的引用。
- [ ] 每条决策记录都有完整问题、选项含义、用户选择和结论。
- [ ] 没有把“按推荐”“都同意”“其余照旧”当成结论。
- [ ] 文档信息、版本、日期、阶段状态已填写。
- [ ] 状态、结论和正文一致；改了结论，相关章节已同步。
- [ ] 术语在全文一致，没有混用同义词。
- [ ] 文档没有页面布局、交互细节或视觉设计。
- [ ] 文档没有技术栈、框架、数据库、API 签名或部署方式。
- [ ] 文档没有编码任务拆分、排期或人员安排。
- [ ] 用户追问上述内容时，已记录为 `deferred` 并说明移交阶段。
- [ ] 不适用章节都写明了原因。
- [ ] 文档中没有编造的业务名词、角色、字段或流程。
- [ ] 每个具体业务描述都能指向用户原话、用户回答或现有材料。

## 9. 交付与验收

- [ ] `REQUIREMENTS.md` 已按模板生成，并放在约定路径。
- [ ] 条件适用的 `PRODUCT_BACKLOG.md` 已生成，或说明不适用原因。
- [ ] 条件适用的 `REQUIREMENT_TRACEABILITY.md` 已生成，或说明并入 `REQUIREMENTS.md` 第 12 节。
- [ ] `REQUIREMENT_REVIEW.md` 已记录审查问题、严重程度、用户处理和结论。
- [ ] 已向用户提交：已确认需求摘要、MVP 和首版范围、不做项、核心验收标准、优先级、依赖、假设和风险。
- [ ] 已明确告诉用户：哪些内容仍需后续细化，哪些属于后续版本。
- [ ] 已说明下一步进入哪个阶段，以及本文件不替代产品设计和技术设计。
- [ ] 用户已明确确认需求基线。
- [ ] 如有修订，修订记录已追加，受影响章节已同步。
- [ ] 阶段完成后没有擅自开始界面设计、技术设计或编码。

## 退出判定

- 全部通过，或所有不适用项都有说明：阶段完成，可以交接。
- 任一项失败：回到对应阶段修正，不得宣告完成。
