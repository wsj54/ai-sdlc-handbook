# 需求分析与范围管理

把 `INITIAL_REQUIREMENTS.md` 中的原始想法，和 `DEVELOPMENT_APPROACH.md` 中的开发方式约定，转化成一份**可设计、可开发、可验证、范围明确**的正式需求基线。

这是一次**需求工程协作**，不是一次文档生成。AI 负责分析、追问、细化、检查并提出建议；用户负责提供真实业务知识、回答关键问题、做取舍和最终确认。

AI 至少承担四种角色：需求分析师、产品经理、需求访谈者、独立审查者。审查阶段再切换为产品经理、用户、测试工程师、架构师、安全审查者五个视角；不能一边提建议一边给自己打分。

## 用户在本阶段的角色

| 角色 | 职责 |
| --- | --- |
| 需求提供者 | 描述真实想法、实际场景和期望效果 |
| 业务决策者 | 确认功能行为、业务规则和取舍 |
| 产品负责人 | 决定功能优先级、MVP 和明确不做项 |
| 最终验收者 | 确认需求基线是否符合真实意图 |

用户不需要会写规范文档或使用需求工程术语。AI 负责把用户的业务知识转化成工程上清晰的需求。

## 本阶段回答什么

- 软件第一版要做什么、不做什么？
- 每项功能在什么条件下、由谁、输入什么、系统如何响应、产生什么结果？
- 有哪些业务规则、异常、边界和状态变化？
- 有哪些非功能要求、数据要求和外部依赖？
- 哪些属于 MVP、哪些属于后续版本、哪些明确不做？
- 需求之间有什么依赖、冲突和影响？
- 每项核心需求怎样才算验收通过？

## 本阶段不回答什么

| 内容 | 移交阶段 |
| --- | --- |
| 页面布局、交互细节、视觉设计、原型 | 产品设计阶段 |
| 技术栈、框架、数据库、API、部署方式 | 技术设计阶段 |
| 具体编码任务拆分、排期、人员安排 | 开发计划阶段 |
| 需求基线冻结后的变更处理 | 需求变更管理 |

这些内容即使被提到，也只记录为 `deferred`，写明移交阶段和原因，不在本阶段替后续阶段做决定。

## 三条设计原则

1. **AI 不是文档生成器，而是主动的需求分析者。** 主动发现缺口、提出问题、给出建议，但不替用户决定。
2. **不追求文档越完整越好，而是追求当前开发范围内的信息足够明确。** 增量、敏捷项目不提前细化全部未来需求。
3. **需求基线必须能成为产品设计、架构设计、任务拆分和测试的可靠依据。** 后续工作应能追溯到具体需求。

## 输入

按顺序查找并读取：

1. 用户明确指定的需求文档或路径；
2. `docs/01-原始需求/INITIAL_REQUIREMENTS.md`；
3. `docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md`；
4. 项目根目录下的 README、AGENTS、CLAUDE、说明、笔记类 Markdown；
5. 用户在对话中直接给出的描述。

同时读取项目现状，用于减少提问：

- 依赖清单（`package.json`、`pyproject.toml`、`requirements.txt`、`go.mod` 等）；
- 目录结构、已有源码、测试目录、CI 配置、部署配置；
- Git 历史（如果可用）。

每份输入都要记录：路径、日期或版本、它回答了哪些问题、与其他输入是否冲突。多份输入冲突时登记冲突，不静默选择其中一份。

找不到前置文档时不拒绝启动。用对话补齐最小信息：想解决什么问题、给谁用、第一版大概做什么、已知限制、打算怎么开发。缺失内容标 `assumption` 或 `deferred`，不虚构。

## 八步工作流

| 阶段 | 目标 | 主要动作 | 主要产物 | 何时暂停 |
| --- | --- | --- | --- | --- |
| 01 上下文与适配 | 建立分析基线，确定做到什么程度 | 读输入、查项目、识别开发模型、列缺口 | 分析基线、文档骨架 | 读完后进入 02 |
| 02 需求诊断 | 把原始材料当作待检验对象 | 逐条提取、分类、找重复/矛盾/模糊/缺口 | 原始需求清单、问题清单 | 需要用户回答阻塞问题时 |
| 03 需求获取 | 把核心需求问清楚 | 六维访谈、流程拆解、规则与异常、术语澄清 | 需求草稿、决策记录 | 每轮提问后等待回答 |
| 04 分类与结构化 | 把零散信息整理成需求体系 | 分类、层次拆解、编号、状态、术语表 | 结构化需求清单 | 需要用户确认整理结果时 |
| 05 范围与优先级 | 决定做什么、先做什么、不做什么 | 核心闭环、MoSCoW、MVP 分层、不做项 | MVP、版本范围、优先级、依赖 | 需要用户做取舍时 |
| 06 细化与验收 | 让需求具体到可设计、可验证 | 七项检查、Given-When-Then、非功能验收 | 详细需求、验收标准、验证映射 | 需要用户确认业务规则时 |
| 07 独立审查 | 换一个立场找问题 | 五角色切换、八维审查、依赖影响分析 | 审查报告、修订稿 | 用户处理审查意见时 |
| 08 基线与交接 | 形成正式交付 | 交付检查、生成文档、用户确认 | `REQUIREMENTS.md` 等正式文件 | 用户验收时暂停 |

## 访谈引擎

本技能的追问方式沿用 grilling 式访谈：把需求空间当成一棵**设计树**，按**轮次**推进，只问当前能够回答的问题。

### 事实自己查，决策问用户

- 能从文件、目录、依赖、Git、配置、现有文档中确认的**事实**，自己查，不问用户。
- 需要用户判断的**决策**（目标、用户范围、业务规则、优先级、取舍、验收口径）必须交给用户，不能替用户决定。
- 查不到又必须知道的事实，明确说“这一点无法从现有材料确认”，再问。

### 设计树与 frontier

把待确认内容组织成一棵树：每个决策分叉出依赖它的后续决策。

- **frontier（边界）**：所有前置条件已经敲定、现在就能问的问题。
- 一个问题如果依赖本轮另一个尚未回答的问题，它属于**下一轮**，不属于本轮。
- 用户回答后重新计算 frontier，再问下一轮。
- 当 frontier 为空，说明每个分支都已走过，没有留下被默默假设的东西。

### 轮次格式

每轮问 1–4 个问题；默认 2–3 个。只有属于同一场景、回答起来方便的问题才合并，不相关的问题不要硬凑。问完一轮就停，等待回答。

```text
❓ Q1｜<能脱离上下文独立理解的标题>
为什么问：<影响哪条需求、哪个范围决定或哪个验收口径>
可选答案：
A. <含义>
B. <含义>
C. <含义>
➡️ 推荐：<推荐项 + 理由>
影响：<选 A/B/C 分别会改变什么>

---

❓ Q2｜<标题>
...
```

规则：

- 每个问题只处理一个决策点。
- 选项写含义，不只有字母。
- 推荐是建议，不是替用户决定；最终决定权在用户。
- “影响”要具体，例如“选 A 会让首版增加一类用户角色和相应的数据隔离要求”，不要写“影响范围”。
- 不要问能通过读文件确认的事实。
- 用户只回“按推荐”时，把推荐内容本身写成结论；用户只回字母时，先复述该选项含义再写结论。

### 控制无效提问

提出每个问题前，先过四道筛子：

1. 是否影响核心功能或核心范围？
2. 是否影响本阶段的输出？
3. 是否影响后续设计或开发？
4. 是否存在无法撤销或高成本的风险？

四问都不影响时，允许采用合理假设（`assumption`）或推迟（`deferred`），不要为了完整而制造问题。

### 讨论结果立即落盘

每轮回答后立即更新文档，不攒到最后一次性写：

- 已确认需求；
- 需求状态；
- 相关业务规则和异常；
- 新增的待确认事项；
- 受影响的其他需求、依赖和范围。

不能只把结果留在聊天记录里。

## 全流程必须遵守的规则

### 信息状态

文档中的信息只使用五种状态：

| 状态键 | 展示名 | 含义 | 使用条件 |
| --- | --- | --- | --- |
| `confirmed` | 已确认 | 用户明确表达并确认 | 用户原话明确，或用户明确回答后 |
| `pending` | 待确认 | 存在歧义或缺少信息 | 有 2 种以上合理解释，或关键信息缺失 |
| `conflict` | 存在冲突 | 与其他需求或约束矛盾 | 冲突尚未解决 |
| `assumption` | 暂定假设 | 为推进工作暂时采用 | 用户暂不回答但要求继续 |
| `deferred` | 暂缓处理 | 当前阶段不需要确定 | 属于后续阶段或用户暂不决定 |

规则：

- AI 的推荐、推测、行业惯例只能进入 `assumption` 或 `pending`，不能写成 `confirmed`。
- 只有用户明确回答或确认，才能把 `pending`、`conflict`、`assumption` 转为 `confirmed`。
- 一个条目只保留一个状态；同时存在冲突和歧义时，先记 `conflict`。
- “明确不做”不是一种状态，而是一个已确认的范围决定，记录在“明确不做项”中。

### 编号与追溯

| 前缀 | 用途 |
| --- | --- |
| `REQ-xxx` | 第一阶段原始需求编号，沿用，不重新编号 |
| `M-xxx` | 功能模块 |
| `FR-xxx` | 功能需求 |
| `UC-xxx` | 用户故事 / 用例 |
| `NFR-xxx` | 非功能需求 |
| `BR-xxx` | 业务规则 |
| `DR-xxx` | 数据需求 |
| `IR-xxx` | 外部接口需求 |
| `CON-xxx` | 约束条件 |
| `AC-xxx` | 验收条件 |
| `DP-xxx` | 需求依赖 |
| `OOS-xxx` | 明确不做项 |
| `GL-xxx` | 术语 |
| `DEC-xxx` | 需求决策记录 |
| `Q-xxx` | 待确认问题 |
| `AS-xxx` | 暂定假设 |
| `DF-xxx` | 暂缓事项 |
| `RK-xxx` | 风险 |
| `RV-xxx` | 审查问题 |
| `BL-xxx` | 产品待办项 |
| `CH-xxx` | 修订记录 |

- 每条正式需求必须能追溯到 `REQ-xxx` 原话，或某一轮用户的明确回答。
- 编号只做索引，不承载含义；引用编号的地方要同时写出结论本身。
- 后续设计、任务拆分和测试应能通过编号反查需求。

### 记录自包含

文档要能被另一个对话、另一个人直接读懂：

- 每条记录脱离原对话仍然成立。
- 不写 `Q1=A`、`Q2=B` 这类引用；问题只存在于对话，字母的含义没有落盘。
- 决策记录写：完整问题、选项及含义、用户选择、结论、影响章节。
- 不把“按推荐”“照你说的”“其余都同意”当成结论，要写出被采纳的内容。
- 用户回答“都可以”“你决定”时，把推荐记为 `assumption`，并说明何时需要确认。

### 不编造需求

这是本技能最重要的约束：

- 不从通用模板、行业惯例、相似产品或 AI 的想象中推断用户没有表达的需求。
- 通用分类、典型场景、常见非功能项只能用来**提问**，不能直接写成需求。
- 用户没有提到、但实现核心流程明显不可缺少的内容，先作为问题提出；用户确认后才进入正式需求，未确认前标 `pending`。
- 不引入用户材料中没有的业务名词、角色、字段和流程；确需引入时先问。
- 示例、类比、参考产品只用于说明，不进入需求正文。
- 文档中的每个具体业务描述，都必须能指向用户原话、用户回答或项目现有材料。

### 需求不是实现

- 可以写：需要保存什么、需要通知谁、需要什么权限、失败时如何表现、需要调用哪类外部服务。
- 不写：用什么数据库、框架、协议、模型、部署方式、表结构、接口签名。
- 外部依赖只写业务必要性、输入输出、失败降级和约束，不写接入方案。
- 技术限制如果由用户明确提出，记为 `CON-xxx` 约束，不展开成技术设计。

### 范围控制

- 每条需求必须回答：属于 MVP、首版、后续版本，还是明确不做？
- 没有归属的需求不能进入需求基线。
- 范围扩大必须由用户确认；AI 不能自行加入“顺便做”的功能。
- 需求膨胀时优先做减法：能否用人工流程替代、能否延后、能否用更简单的行为满足。
- 范围决定要记录理由，不只记录结论。

### 开发模型适配

分析深度服从 `DEVELOPMENT_APPROACH.md`，不强行把所有模型做成同一份厚文档。详见 [phases/01-context-and-fit.md](./phases/01-context-and-fit.md)。

### 阶段边界

用户在本阶段追问界面、技术选型或任务拆分时：

1. 记录为 `deferred`；
2. 说明为什么现在不定；
3. 指出由哪个后续阶段处理；
4. 不因为用户追问就提前做设计。

只有用户明确要求切换阶段或调用其他技能时，才离开本阶段。

## 文档落盘与更新节奏

1. 阶段 01 结束时，创建 `REQUIREMENTS.md` 骨架，填写文档信息、输入来源、开发模型适配和分析范围。
2. 阶段 02–06 每轮回答后，立即更新相关章节、状态、决策记录和未决事项。
3. 阶段 07 审查后，更新受影响章节，并在 `REQUIREMENT_REVIEW.md` 记录问题与处理结果。
4. 阶段 08 补齐所有章节，运行 [CHECKLIST.md](./CHECKLIST.md)，处理失败项后再交付。

文档中的状态、结论和正文必须一致。改了结论，要同步改受影响的场景、规则、验收条件、依赖、范围和风险。

## 修订模式

用户读完后提出修改时，不重新生成整份文档：

1. 读取最新版 `REQUIREMENTS.md`。
2. 把每个修改点登记为 `CH-001`、`CH-002`……
3. 评估修改是否与目标、范围、业务规则、验收条件、开发模型一致；是否属于需求膨胀或越界到后续阶段。
4. 每轮挑 2–4 个最需要决定的修改点，说明影响和可选处理方式，由用户确认。
5. 只改受影响章节，同步状态、假设、依赖、风险和追溯关系。
6. 在文末追加修订记录，保留原描述，不覆盖历史。
7. 重新运行 [CHECKLIST.md](./CHECKLIST.md)，给用户一份变动摘要。

修订时同样遵守“不照单执行、不替用户否决、不静默改结论”。

## 完成条件

同时满足以下条件才能宣告本阶段完成：

- 软件的核心目标和用户范围已经明确。
- 核心使用场景和核心业务流程已经分析，正常与异常路径都有结论或标记。
- 原始需求均已识别、归类，没有无故遗漏。
- 核心功能已拆分成清晰、可理解、可独立验证的需求。
- 核心业务规则、状态变化和重要异常场景已经明确。
- MVP、首版范围、后续版本和明确不做项都已经写明。
- 需求优先级和重要依赖关系已经明确。
- 核心需求具有可验证的验收标准。
- 非功能需求、数据要求和项目约束已合理处理，不适用项有说明。
- 未知事项、假设和风险均已标记，并写明处理方式。
- 需求与原始需求、验收条件、后续设计/测试之间有追溯关系。
- 已完成独立审查，并解决所有阻塞性问题。
- [CHECKLIST.md](./CHECKLIST.md) 全部通过，或对“不适用”项有说明。
- 用户已经审查并明确确认需求基线。

任一条件不满足，继续对应阶段，不宣告完成。
