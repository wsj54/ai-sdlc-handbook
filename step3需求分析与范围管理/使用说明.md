# 需求分析与范围管理使用说明

这份说明回答一个问题：**原始需求整理完、开发模型也选好之后，第一版到底做什么、每项需求怎么算清楚、又怎么验收？**

它不会替你设计页面，也不会替你选技术栈。它做的是：把零散的初始需求收敛成一份范围明确、优先级合理、可以设计和开发、可以验证的正式需求基线。

一句话版本：

> 把 `INITIAL_REQUIREMENTS.md` 和 `DEVELOPMENT_APPROACH.md` 交给 `requirements-analysis` 技能，调用一次；它会先读项目、诊断需求，再分轮追问、划范围、定优先级、写验收标准、做独立审查，最后产出 `REQUIREMENTS.md`。

---

## 这个阶段做什么

- 明确软件第一版要做什么、不做什么。
- 分析目标用户、使用场景、核心业务流程和现有做法。
- 把核心功能拆成清晰、可理解、可独立验证的需求。
- 明确业务规则、状态变化、异常和边界情况。
- 分析非功能要求、数据要求和外部依赖。
- 确定 MVP、首版范围、后续版本和明确不做项。
- 排优先级、识别需求依赖和关键路径。
- 为核心需求制定可执行的验收标准。
- 做一次独立审查，检查遗漏、冲突、歧义、可验证性和需求膨胀。
- 产出正式需求基线，交给下一阶段。

## 这个阶段不做什么

- 不设计页面布局、交互细节、视觉稿或原型；
- 不选择技术栈、框架、数据库、API 或部署方式；
- 不拆分具体编码任务，也不排期；
- 不处理需求基线冻结后的变更流程。

这些内容即使被提到，也会被记录为“暂缓”，写明交给哪个后续阶段。

---

## 什么时候使用

适合在这些时候使用：

- 你已经有一份 `INITIAL_REQUIREMENTS.md`，但里面还是用户视角的想法，不能直接拿来开发；
- 你知道大概要做什么，但不确定第一版应该包含哪些、先做哪些；
- 你担心功能越加越多、第一版迟迟做不完；
- 你想把“自动”“智能”“方便”这类模糊要求变成具体行为；
- 你需要知道每项功能怎样才算做完、怎样验收；
- 你准备进入产品设计或技术设计，但需求还没有稳定下来。

如果你还没有原始需求文档，先用 `requirement-enrichment` 丰富想法，再用 `initial-requirements` 整理；如果你还没确定开发方式，先使用 `development-approach`。

## 使用前准备什么

不要求准备得很完整，但下面这些信息越清楚，提问轮次越少：

- 原始需求文档，最好是 `docs/01-原始需求/INITIAL_REQUIREMENTS.md`；
- 开发方式文档，最好是 `docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md`；
- 你目前实际怎么完成这件事，哪些环节最费时、最容易出错；
- 哪些业务规则是必须遵守的，哪些情况绝对不能发生；
- 数据从哪里来、要保存多久、是否需要导入导出、是否包含敏感信息；
- 是否依赖外部服务、账号、密钥或付费额度；
- 你希望第一版尽快体验到什么；
- 你明确不想做、暂时做不了或可以往后放的内容。

也可以提供比文字更有效的材料：

- 现在使用的表格、清单或文档；
- 现有软件的截图；
- 真实操作过程或参考软件；
- 典型输入和预期输出；
- 脱敏后的真实业务数据；
- 你认为不好用、不希望重复的体验。

不需要会写规范文档，也不需要懂需求工程术语。你负责提供真实业务知识，技能负责把它转成工程上清晰的需求。

---

## 只需要调用一次

在对话里说：

```text
请使用 requirements-analysis 技能，把我的原始需求整理成正式需求基线。
原始需求在 docs/01-原始需求/INITIAL_REQUIREMENTS.md，
开发方式在 docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md。
```

也可以直接把需求粘贴进对话：

```text
请使用 requirements-analysis 技能。
我的项目是……（描述你的需求）
```

调用一次后，技能会自动按顺序推进八个阶段，不需要你再手动调用：

1. **上下文与适配**：读输入、看项目现状、确认开发模型和分析深度。
2. **需求诊断**：逐条提取原始需求，找重复、矛盾、模糊和缺口。
3. **需求获取**：分轮访谈，明确用户、场景、流程、功能、规则、异常、数据和非功能要求。
4. **分类与结构化**：分类、拆解、编号、标记状态、建立术语表。
5. **范围与优先级**：找核心闭环，划 MVP、首版、后续版本和明确不做项。
6. **细化与验收**：把核心需求写到可设计、可验证，制定验收标准。
7. **独立审查**：切换多个审查视角，检查完整性、一致性和可行性。
8. **基线与交接**：生成正式文档，交给你确认，形成需求基线。

它只会在三种情况下停下来等你：

- 需要你回答一轮问题；
- 需要你在方案或范围之间做取舍；
- 文档写完，需要你验收或提出修改。

---

## 访谈阶段会发生什么

技能不会一次把所有问题问完，而是每轮问 1–4 个当前最阻塞的问题（通常是 2–3 个）。每个问题通常包含：

- **为什么问**：它会影响哪条需求、哪个范围决定或哪个验收口径；
- **可选答案**：A、B、C 分别代表什么；
- **推荐**：AI 的建议，不是替你决定；
- **影响**：选不同答案会改变什么。

你可以这样回答：

- “选 A。”
- “A 和 B 都要，区别是……”
- “我不确定，先按假设处理，但要在文档里标出来。”
- “这个现在不定，留到后面。”
- “你理解错了，我的意思是……”
- “按推荐。”

几条原则：

- 只有你明确确认的内容，才会被标成“已确认”。
- AI 的推荐、推测或行业惯例只能作为“待确认”或“暂定假设”，不能当成你的决定。
- 你改变主意时直接说，技能会检查新回答是否和之前的结论冲突。
- 回答选项时尽量把内容一起说清，例如“选 B：只在提交前提醒，不自动修改”，不要只回“选 B”。
- 如果 AI 问了你觉得它能从文档或项目里查到的事，直接告诉它去查。
- 不知道就说“还没想好”，不要为了推进随便选一个。

访谈不只问“你想要什么功能”，还会问：

- 你现在是怎么完成这件事的？
- 哪一步最容易失败、被打断或重复操作？
- 操作完成后数据变成什么状态？
- 发生错误时用户应该看到什么？
- 谁能做、谁不能做？
- 你说的某个词，具体指什么，不包含什么？

## 不同开发模型，文档深度不同

这个阶段不会机械要求所有项目都写同样厚的文档：

| 开发模型 | 本阶段重点 |
| --- | --- |
| 瀑布 | 在约定范围内尽量完整地分析，形成需求基线 |
| 敏捷 | 产品目标、MVP 和近期需求详细，远期需求允许粗略 |
| 增量 | 首个增量详细，后续增量写清目标、范围和依赖，进入迭代前再细化 |
| V 模型 | 每项需求同步规划验证方法和验收条件 |
| 螺旋 | 优先分析重大风险相关的需求和约束 |
| 原型 | 已确认需求与待验证的体验假设分开管理 |

所以，如果你采用增量或敏捷方式，看到“后续版本只写了目标和大方向”是正常的。**当前增量足够清楚，比把所有未来功能提前写完更重要。**

## 产出是什么

默认产出目录：

```text
docs/03-需求分析与范围/
```

可能包含：

| 文件 | 作用 |
| --- | --- |
| `REQUIREMENTS.md` | 必需。正式需求规范：目标、范围、功能、规则、非功能、数据、优先级、验收、依赖、约束、追溯 |
| `PRODUCT_BACKLOG.md` | 敏捷、增量项目使用。管理先做哪个、放在哪个迭代、依赖谁 |
| `REQUIREMENT_TRACEABILITY.md` | 大型项目使用。追溯原始需求、正式需求、验收条件和后续测试；小项目可并入 `REQUIREMENTS.md` |
| `REQUIREMENT_REVIEW.md` | 建议保留。审查问题、阻塞项、风险、假设、未决事项和处理结果 |

`REQUIREMENTS.md` 通常包含：

- 项目背景与目标；
- 目标用户与使用场景；
- MVP、首版、后续版本和明确不做项；
- 功能模块、功能需求、用例和业务规则；
- 非功能需求；
- 数据需求与外部接口需求；
- 需求优先级与版本规划；
- 验收标准；
- 需求依赖关系；
- 约束条件；
- 风险、假设与待确认事项；
- 需求追溯关系；
- 术语与定义；
- 需求决策记录；
- 修订记录。

## 文档里的五种状态怎么看

| 状态 | 对你意味着什么 |
| --- | --- |
| 已确认 | 你已经明确确认，可以作为下一阶段的依据 |
| 待确认 | 还有歧义或缺少信息，需要你回答 |
| 存在冲突 | 两条需求或约束互相矛盾，等你选择处理方式 |
| 暂定假设 | 你暂时没定，先按这个理解推进；以后可以改 |
| 暂缓处理 | 当前阶段或当前版本不需要定，已写明移交位置 |

看到“暂定假设”和“暂缓处理”不用担心，它们是被明确记录的不确定性，不是被偷偷当成确定需求。

## 怎么审核

文档写完后，技能会给你一份摘要，通常包括：

- 已确认需求摘要；
- MVP 和首版范围；
- 明确不做项；
- 核心验收标准；
- 需求优先级和版本规划；
- 关键依赖；
- 待确认事项、暂定假设、暂缓事项和风险；
- 需要下一阶段重点关注的内容；
- 检查清单结果。

重点检查：

- AI 有没有理解错你的意思？
- 有没有漏掉你明确提过的需求？
- 第一版范围是否符合你的预期？
- 明确不做项是否写清楚了？
- 业务规则是否符合你的实际使用习惯？
- 验收标准是不是能实际判断，而不是“正确”“正常”这类空话？
- 哪些是暂定假设？你能接受吗？
- 哪些是暂缓事项？是否确实可以留到后面？

确认没有问题后，明确回复：

```text
可以确认需求基线。
```

在你确认之前，这个阶段不会被标记为完成，后续阶段也不应该直接开始。

## 怎么修改

如果文档有问题，不用自己手改，也不用让 AI 重新生成整份文档。直接指出具体章节或需求编号：

```text
请修改 REQUIREMENTS.md：
1. FR-003 的规则不对，提交后应该允许在限定时间内撤回。
2. 第 4.4 节的某条业务规则和我实际做法不一致。
3. OOS-002 不应该列为不做项，它只是延后到下一版本。
4. NFR-001 的验收方式太模糊，需要写清楚怎么判断。
```

技能会：

1. 登记每个修改点为 `CH-001`、`CH-002`……；
2. 评估修改是否与目标、范围、业务规则、验收条件和开发模型一致；
3. 判断是否属于需求膨胀、重复功能或越界到界面/技术设计；
4. 每轮挑 2–4 个最需要决定的修改点，说明影响和可选处理方式；
5. 按你确认的结果修改，只改受影响章节；
6. 同步状态、依赖、风险和追溯关系；
7. 追加修订记录，保留原内容；
8. 重新运行检查清单，给你一份变动摘要。

它不会因为“你说了”就直接改；明显不合理的地方，它会先指出并给替代方案。它也不会替你否决，最终改不改由你决定。

---

## 需求基线之后还能改吗

能。第三阶段完成，并不代表需求以后不能变化。但后续变化要先判断类型，不能想到一个新功能就直接改代码：

| 类型 | 处理方式 |
| --- | --- |
| 原有需求理解不正确 | 修正原需求，并检查受影响的验收条件和设计 |
| 原有功能没有按需求实现 | 作为缺陷处理，不改需求定义 |
| 新增功能 | 进入产品待办列表，评估优先级和版本归属 |
| 业务规则变化 | 评估对需求、数据、验收和后续设计的影响 |
| 优先级变化 | 调整版本规划和开发顺序 |
| 重大方向变化 | 重新评估整体需求、范围和开发流程 |

需求变更管理不属于本技能的执行范围；本阶段只负责建立基线并说明边界。

## 常见误区

- **把需求分析当成“让 AI 生成一份 PRD”。** 没有访谈和取舍，生成的只是通用模板，不是你的需求。
- **一上来就让 AI 写页面和技术方案。** 页面、技术栈、数据库和接口属于后续阶段；过早决定会掩盖真正的需求问题。
- **把 AI 的推荐当成自己的决定。** 推荐只是建议；你不确认，它应该保持“待确认”或“暂定假设”。
- **追求文档越完整越好。** 当前开发范围足够清楚，比把未来所有功能提前写死更重要。
- **跳过访谈，直接要最终文档。** 缺少真实场景、业务规则和异常信息时，文档只能靠猜。
- **只回“Q1 选 A”“按推荐”。** 问题和字母只存在于对话里；回答时把选项内容和推荐内容说清楚。
- **把所有“以后可能有用”的功能都放进第一版。** 范围膨胀是第一版做不完的常见原因。
- **不写明确不做项。** 不写清楚不做什么，后续开发很容易擅自扩大范围。
- **验收标准写成“正确”“正常”“友好”。** 这些无法判断；应写成可观察、可重复验证的结果。
- **把模板、行业惯例或类似产品当成需求。** 它们只能帮助提问，不能直接写成你的需求。
- **让 AI 编造性能数字。** 暂不能定的指标应标为待验证，而不是随便填一个数值。
- **需求文档写完就再也不看。** 需求、范围或业务规则变化时，应回到文档修订，而不是只在聊天里临时改。
- **把需求分析和需求变更管理混在一起。** 基线建立和后续变更判断是两件事。

## 和其他阶段的关系

```text
想法 / 原始描述
      |
      v
requirement-enrichment（需求丰富，可选）
      |
      v
initial-requirements（原始需求整理）
      |
      v
development-approach（选开发模型 + 定开发流程）
      |
      v
requirements-analysis（本阶段：需求分析与范围管理）
      |
      v
产品设计 / 技术设计 / 任务拆分 / 迭代开发 / 测试与验收
```

本阶段的输出 `REQUIREMENTS.md` 是后续工作的共同依据：

- 产品设计从确认的需求和验收标准出发；
- 技术设计能追溯到具体需求编号；
- 任务拆分依据优先级、版本归属和依赖关系；
- 测试依据验收标准判断功能是否完成；
- 出现新想法时，先判断它对需求、范围、设计和测试的影响。
