# 产品设计与交互原型使用说明

这份说明回答一个问题：**需求基线确认之后，软件到底长什么样、页面之间怎么走、每个页面怎么交互？**

它不会替你写代码、选技术栈，也不会直接产出 HTML 原型。它做的是：把已确认的需求转成一份结构化的产品设计文档，这份文档能直接交给下一步的 HTML 交互原型去实现。

一句话版本：

> 把 `REQUIREMENTS.md`（和 `FEASIBILITY_REVIEW.md`）交给 `product-design` 技能，调用一次；它会先读需求、再分轮追问，产出 `PRODUCT_DESIGN.md`，作为后续交互原型开发的蓝图。

***

## 这个阶段做什么

- 明确产品整体怎么组织：有哪些页面、如何导航。
- 梳理用户完成关键任务的流程和异常分支。
- 列出首版全部页面，标注角色权限和详细程度。
- 把核心页面的元素、交互、状态、跳转写到能直接驱动原型。
- 抽取跨页面通用的交互模式和反馈规则。
- 明确设计原则、设计约束和视觉方向（只给方向，不锁死）。
- 建立术语表，保证全流程用词一致。
- 写清移交原型阶段的说明。

## 这个阶段不做什么

- 不产出 HTML / 视觉原型，不写具体配色、字号、间距；
- 不选择技术栈、框架、组件库、数据库或 API；
- 不写代码；
- 不重新做需求分析。

这些内容即使被提到，也会被记录为“暂缓”，写明交给哪个后续阶段。

***

## 什么时候使用

适合在这些时候使用：

- 你已经有一份确认过的 `REQUIREMENTS.md`，准备开始设计页面和交互；
- 你大概知道要做哪些功能，但不确定页面怎么组织、先做哪些页面；
- 你准备让 AI 帮你做 HTML 交互原型，需要先有一份设计蓝图；
- 你担心直接做原型会漏页面、漏交互、来回返工。

如果你还没有需求基线，先完成第三阶段（`requirements-analysis`）；如果还没做可行性分析，先完成第四阶段（`feasibility-review`）。

***

## 使用前准备什么

不要求准备得很完整，但下面这些材料越清楚，提问轮次越少：

- 需求基线：`docs/03-需求分析与范围/REQUIREMENTS.md`（核心，必需）；
- 可行性结论：`docs/04-初步可行性分析/FEASIBILITY_REVIEW.md`（提供设计约束和风险）；
- 原始需求：`docs/01-原始需求/INITIAL_REQUIREMENTS.md`（提供背景和场景）；
- 开发方式：`docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md`（决定设计深度）。

如果部分文档缺失，技能也能基于你口述推进，但会显著增加提问轮次，并记录输入缺口。

***

## 只需要调用一次

在对话里说：

```text
请使用 product-design 技能，基于我的需求基线产出产品设计文档。
需求基线在 docs/03-需求分析与范围/REQUIREMENTS.md，
可行性结论在 docs/04-初步可行性分析/FEASIBILITY_REVIEW.md。
```

调用一次后，技能会自动按顺序推进七个阶段，不需要你再手动调用：

1. **上下文与输入**：读需求、识别开发模型、列设计约束。
2. **信息架构**：确定页面层级与导航、站点地图。
3. **用户流程**：梳理核心闭环流程和异常分支。
4. **页面清单**：枚举全部页面，标注角色权限和详细程度。
5. **页面详细设计**：核心页面的元素、交互、状态、跳转四要素。
6. **交互规范**：抽取通用交互模式、反馈、错误处理。
7. **审查与交接**：独立审查，写清移交原型阶段的说明。

它只会在三种情况下停下来等你：

- 需要你回答一轮问题；
- 需要你在设计方案之间做取舍；
- 文档写完，需要你验收或提出修改。

***

## 访谈阶段会发生什么

技能不会一次把所有问题问完，而是每轮问 1–4 个当前最阻塞的问题（通常是 2–3 个）。每个问题通常包含：

- **为什么问**：它会影响哪个页面、流程、交互或约束；
- **可选答案**：A、B、C 分别代表什么；
- **推荐**：AI 的建议，不是替你决定；
- **影响**：选不同答案会改变什么。

你可以这样回答：

- “选 A。”
- “A 和 B 都要，区别是……”
- “我不确定，先按假设处理，但要在文档里标出来。”
- “这个现在不定，留给原型阶段。”
- “你理解错了，我的意思是……”
- “按推荐。”

几条原则：

- 只有你明确确认的内容，才会被标成“已确认”。
- AI 的设计建议、行业惯例只能作为“待确认”或“暂定假设”，不能当成你的决定。
- 回答选项时尽量把内容一起说清，例如“选 B：删除前弹窗确认，不直接删”，不要只回“选 B”。
- 如果 AI 问了你觉得它能从文档里查到的事，直接告诉它去查。
- 不知道就说“还没想好”，不要为了推进随便选一个。

访谈不只问“页面长什么样”，还会问：

- 这个任务用户通常怎么完成，最在意什么？
- 页面信息这么多，哪些必须一眼看到，哪些可以折叠？
- 这个操作如果失败，用户应该看到什么、能怎么办？
- 这个功能要不要独立成一个页面，还是并入现有页面？
- 首版先做哪些页面，哪些留到后续？

## 不同开发模型，设计深度不同

这个阶段不会机械要求所有项目都写同样厚的文档：

| 开发模型    | 本阶段重点             |
| ------- | ----------------- |
| 瀑布      | 在约定范围内尽量完整地设计全部页面 |
| 敏捷 / 增量 | 核心闭环页面详细设计，远期页面从简 |
| 原型      | 重点设计需要验证体验的假设页面   |

所以，如果你采用敏捷或增量方式，看到“后续版本页面只写了目的和清单”是正常的。**核心页面足够清楚，比把所有页面提前写死更重要。**

***

## 产出是什么

默认产出目录：

```text
docs/05-产品设计/
```

核心产物：

| 文件                  | 作用                                                   |
| ------------------- | ---------------------------------------------------- |
| `PRODUCT_DESIGN.md` | 必需。设计原则与约束、信息架构、用户流程、页面清单、页面详细设计、交互规范、术语表、待确认事项、移交说明 |

`PRODUCT_DESIGN.md` 是原型阶段的直接输入，通常包含：

- 设计原则与约束（含视觉方向约定）；
- 信息架构（导航结构 + 站点地图）；
- 用户流程（核心闭环 + 异常分支）；
- 页面清单（全部页面 + 角色权限 + 详细程度）；
- 页面详细设计（核心页面的元素 / 交互 / 状态 / 跳转四要素）；
- 交互规范（通用模式、反馈、错误处理）；
- 术语表；
- 待确认事项与决策记录；
- 移交原型阶段的说明。

***

## 文档里的五种状态怎么看

| 状态   | 对你意味着什么                   |
| ---- | ------------------------- |
| 已确认  | 你已经明确确认，可以作为原型开发的依据       |
| 待确认  | 还有歧义或缺少信息，需要你回答           |
| 存在冲突 | 两个设计或约束互相矛盾，等你选择处理方式      |
| 暂定假设 | 你暂时没定，先按这个理解推进；以后可以改      |
| 暂缓处理 | 当前阶段不需要定，留给原型 / 技术 / 后续版本 |

看到“暂定假设”和“暂缓处理”不用担心，它们是被明确记录的不确定性，不是被偷偷当成确定设计。

***

## 怎么审核

文档写完后，技能会给你一份摘要，通常包括：

- 设计摘要（信息架构、核心流程、页面清单、核心页面四要素概览）；
- 待确认问题、暂定假设、暂缓事项清单；
- 审查问题与处理结果；
- 移交原型阶段的关键说明；
- 检查清单结果。

重点检查：

- AI 有没有理解错你的意思？
- 有没有漏掉你明确提过的页面或功能？
- 核心页面能不能直接交给原型实现（元素、交互、状态、跳转是否齐全）？
- 页面组织是否符合你的使用习惯？
- 视觉方向有没有被锁死（应该只是方向，不该出现具体色值字号）？
- 哪些是暂定假设？你能接受吗？
- 哪些是暂缓事项？是否确实可以留到原型阶段？

确认没有问题后，明确回复：

```text
可以进入原型开发阶段。
```

在你确认之前，这个阶段不会被标记为完成，原型阶段也不应该直接开始。

***

## 怎么修改

如果文档有问题，不用自己手改，也不用让 AI 重新生成整份文档。直接指出具体章节或编号：

```text
请修改 PRODUCT_DESIGN.md：
1. PG-003 首页信息优先级不对，应该把“今日待办”放在最上面。
2. 第 5.3 节某条交互和我期望不一致，点击后应该是跳转而不是弹窗。
3. 某个页面漏了空状态，需要补充。
```

技能会：

1. 登记每个修改点为 `CH-001`、`CH-002`……；
2. 评估修改是否与需求、设计原则、交互规范一致，是否越界到原型 / 技术阶段；
3. 每轮挑 2–4 个最需要决定的修改点，说明影响和可选处理方式；
4. 按你确认的结果修改，只改受影响章节；
5. 同步状态、假设、追溯关系；
6. 追加修订记录，保留原内容；
7. 重新运行检查清单，给你一份变动摘要。

它不会因为“你说了”就直接改；明显不合理的地方，它会先指出并给替代方案。它也不会替你否决，最终改不改由你决定。

## 常见误区

- **把产品设计当成“让 AI 画页面”。** 没有访谈和取舍，生成的是通用模板，不是你的产品。
- **跳过设计文档，直接做 HTML 原型。** 原型阶段容易漏页面、漏交互、来回返工。
- **在设计文档里锁死视觉。** 配色、字号、间距是原型阶段的事，设计文档只给方向。
- **把 AI 的推荐当成自己的决定。** 推荐只是建议；你不确认，它应该保持“待确认”或“暂定假设”。
- **追求所有页面都写满四要素。** 次要页面从简即可；核心页面写满才是关键。
- **只回“Q1 选 A”“按推荐”。** 问题和字母只存在于对话里；回答时把选项内容和推荐内容说清楚。
- **把“以后可能有用”的页面都设计进首版。** 范围膨胀会让设计和原型都做不完。
- **不写异常和空状态。** 正常流程跑通了，但失败、空数据时用户会不知所措。
- **凭空加页面和功能。** 每个页面、交互都该能追溯到需求；AI 新提的建议要你确认才进文档。

## 和其他阶段的关系

```text
requirements-analysis（第三阶段：需求基线）
      |
      v
feasibility-review（第四阶段：可行性分析）
      |
      v
product-design（本阶段：产品设计文档）─── 产出 PRODUCT_DESIGN.md
      |
      v
交互原型开发（HTML 原型，按 PRODUCT_DESIGN.md 实现）
      |
      v
技术验证 / 架构设计 / 任务拆分 / 编码 / 测试
```

本阶段的输出 `PRODUCT_DESIGN.md` 是后续交互原型开发的共同依据：

- 交互原型按页面清单和四要素直接实现，不用重新访谈你；
- 视觉方向在原型阶段逐步细化；
- 出现新想法时，先判断它对设计、原型和需求的影响。

## 最快上手版本

```text
1. 准备好 REQUIREMENTS.md（和 FEASIBILITY_REVIEW.md）。
2. 对 AI 说：“请使用 product-design 技能，产出产品设计文档。”
3. 按轮回答 1–4 个问题；不确定就说“先按假设”或“留给原型阶段”，回答选项时把内容说清。
4. 等它生成 docs/05-产品设计/PRODUCT_DESIGN.md。
5. 重点审核：页面有没有漏、核心页面四要素是否齐全、视觉有没有被锁死、异常和空态有没有覆盖。
6. 没问题就说“可以进入原型开发阶段”；有问题就指出章节或编号，让它修订。
```

## 原型制作工具提示

产品设计文档确认后，进入原型开发阶段时，推荐使用 [mattpocock/skills](https://github.com/mattpocock/skills) 仓库中的 `prototype` 技能来制作交互原型。

它专为“验证设计”的交互原型设计，正好衔接本阶段的产物：

```text
请使用 prototype 技能，基于 docs/05-产品设计/PRODUCT_DESIGN.md 制作交互原型。
```

`prototype` 技能会读取 `PRODUCT_DESIGN.md` 中的页面清单和页面详细设计（元素 / 交互 / 状态 / 跳转四要素），生成可点击的 HTML 原型，帮你验证设计是否合理，而不需要写正式代码。
