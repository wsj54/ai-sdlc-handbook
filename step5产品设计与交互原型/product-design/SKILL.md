# 产品设计

把 `REQUIREMENTS.md` 中已确认的需求，和 `FEASIBILITY_REVIEW.md` 中的设计约束与风险，转化一份**能直接驱动交互原型开发**的产品设计文档。

这是一次**设计协作**，不是一次文档生成。AI 负责设计、追问、细化、检查并提出建议；用户负责提供真实业务知识、确认设计取舍和最终验收。

本阶段只解决「**软件长什么样、页面之间怎么走、每个页面怎么交互**」，不解决「用什么技术实现、视觉上最终好不好看」。视觉只给方向性约定，具体配色、字号、间距留给交互原型阶段迭代。

产出：`PRODUCT_DESIGN.md`（单文档）。文件结构见 [TEMPLATE.md](./TEMPLATE.md)；宣告完成前必须通过 [CHECKLIST.md](./CHECKLIST.md)。

## 用户在本阶段的角色

| 角色 | 职责 |
| --- | --- |
| 业务知识提供者 | 说明真实使用场景、现有做法、偏好和禁忌 |
| 设计决策者 | 确认页面结构、信息优先级、交互取舍 |
| 最终验收者 | 确认设计文档是否符合真实意图、能否交给原型阶段 |

用户不需要会画线框图或写交互规范。AI 负责把业务知识转化成结构化的设计描述。

## 本阶段回答什么

- 产品整体怎么组织：有哪些页面、页面之间如何导航？
- 用户如何完成关键任务：核心流程和异常分支？
- 每个页面放什么、元素之间如何配合？
- 每个元素如何交互：点击 / 输入 / 切换之后发生什么、跳到哪里？
- 每个页面 / 元素有哪些状态：空、加载、错误、禁用、完成？
- 有哪些跨页面的通用交互模式和反馈规则？
- 有哪些设计原则和约束必须遵守？

## 本阶段不回答什么

| 内容 | 移交阶段 |
| --- | --- |
| HTML / 视觉原型、具体配色、字体、间距 | 交互原型阶段（本阶段同一环节的下一步） |
| 技术栈、框架、组件库、数据库、API | 技术设计 / 架构设计阶段 |
| 具体编码实现 | 编码阶段 |

这些内容即使被提到，也只记录为 `deferred`，写明移交位置，不在本阶段替后续阶段做决定。

## 三条设计原则

1. **设计文档是原型的蓝图，不是原型本身。** 用结构化文字描述页面和交互，让原型阶段能照着实现，不必重新访谈用户。
2. **核心页面详细、次要页面从简。** 核心闭环的页面写到「元素 + 交互 + 状态 + 跳转」四要素齐全；次要 / 简单页面只列清单和目的。
3. **每一项设计都能追溯到需求。** 页面、交互、状态都源于 `REQUIREMENTS.md` 的需求或用户本轮确认；不凭空发明页面和功能。

2. `docs/03-需求分析与范围/REQUIREMENTS.md`（核心事实来源）；

## 访谈引擎

本技能的追问方式沿用 grilling 式访谈：把设计空间当成一棵**设计树**，按**轮次**推进，只问当前能够回答的问题。

### 事实自己查，决策问用户

- 能从需求文档、可行性报告、现有材料中确认的**事实**，自己查，不问用户。
- 需要用户判断的**设计决策**（页面怎么组织、信息优先级、交互取舍、范围裁剪）必须交给用户，不能替用户决定。
- 查不到又必须知道的事实，明确说“这一点无法从现有材料确认”，再问。

### 设计树与 frontier

把待确认内容组织成一棵树：每个决策分叉出依赖它的后续决策。

- **frontier（边界）**：所有前置条件已经敲定、现在就能问的问题。
- 一个问题如果依赖本轮另一个尚未回答的问题，它属于**下一轮**，不属于本轮。
- 用户回答后重新计算 frontier，再问下一轮。
- 当 frontier 为空，说明每个分支都已走过，没有留下被默默假设的东西。

### 轮次格式

每轮问 1–4 个问题；默认 2–3 个。只有属于同一场景、回答起来方便的问题才合并，不相关的问题不要硬凑。问完一轮就停，等待回答。

```text
❓ Q1｜<能脱离上下文独立理解的标题>
为什么问：<影响哪个页面、流程、交互或约束>
可选答案：
A. <含义>
B. <含义>
C. <含义>
➡️ 推荐：<推荐项 + 理由>
影响：<选 A/B/C 分别会改变什么>
```

规则：

- 每个问题只处理一个决策点。
- 选项写含义，不只有字母。
- 推荐是建议，不是替用户决定；最终决定权在用户。
- “影响”要具体，例如“选 A 会把首页信息密度提高，但首次使用门槛上升”，不要写“影响体验”。
- 不要问能通过读文件确认的事实。
- 用户只回“按推荐”时，把推荐内容本身写成结论；用户只回字母时，先复述该选项含义再写结论。

### 控制无效提问

提出每个问题前，先过四道筛子：

1. 是否影响核心页面或核心流程？
2. 是否影响本阶段的输出？
3. 是否影响后续原型开发？
4. 是否存在无法撤销或高成本的风险？

四问都不影响时，允许采用合理假设（`assumption`）或推迟（`deferred`），不要为了完整而制造问题。

### 讨论结果立即落盘

每轮回答后立即更新 `PRODUCT_DESIGN.md`，不攒到最后一次性写：新增 / 修改的页面、流程、交互、状态、设计约束、待确认事项。不能只把结果留在聊天记录里。

## 全流程必须遵守的规则

### 信息状态

文档中的信息只使用五种状态：

| 状态键 | 展示名 | 含义 | 使用条件 |
| --- | --- | --- | --- |
| `confirmed` | 已确认 | 用户明确表达并确认 | 用户原话明确，或用户明确回答后 |
| `pending` | 待确认 | 存在歧义或缺少信息 | 有 2 种以上合理解释，或关键信息缺失 |
| `conflict` | 存在冲突 | 与其他设计或需求约束矛盾 | 冲突尚未解决 |
| `assumption` | 暂定假设 | 为推进工作暂时采用 | 用户暂不回答但要求继续 |
| `deferred` | 暂缓处理 | 当前阶段不需要确定 | 属于原型 / 技术 / 后续版本 |

规则：

- AI 的设计建议、行业惯例、推测只能进入 `assumption` 或 `pending`，不能写成 `confirmed`。
- 只有用户明确回答或确认，才能把 `pending`、`conflict`、`assumption` 转为 `confirmed`。
- 一个条目只保留一个状态；同时存在冲突和歧义时，先记 `conflict`。
- “明确不做”不是一种状态，而是一个已确认的范围决定，记录在范围说明中。

### 编号与追溯

| 前缀 | 用途 |
| --- | --- |
| `REQ-xxx` / `FR-xxx` / `BR-xxx` / `AC-xxx` / `NFR-xxx` | 沿用前序需求编号，用于追溯，不重新编号 |
| `IA-xxx` | 信息架构节点（导航 / 层级） |
| `FLOW-xxx` | 用户流程 |
| `PG-xxx` | 页面 |
| `EL-xxx` | 页面元素 |
| `INT-xxx` | 交互行为 |
| `ST-xxx` | 页面 / 元素状态 |
| `LINK-xxx` | 跳转关系 |
| `PR-xxx` | 设计原则 |
| `DC-xxx` | 设计约束 |
| `GL-xxx` | 术语 |
| `DEC-xxx` | 设计决策记录 |
| `Q-xxx` | 待确认问题 |
| `AS-xxx` | 暂定假设 |
| `DF-xxx` | 暂缓事项 |
| `RV-xxx` | 审查问题 |
| `CH-xxx` | 修订记录 |

- 每个页面、每条交互、每个状态必须能追溯到 `FR-xxx` / `BR-xxx` 需求，或某一轮用户的明确回答。
- 编号只做索引，不承载含义；引用编号的地方要同时写出结论本身。
- 后续原型阶段应能通过编号反查设计依据。

### 记录自包含

文档要能被另一个对话、另一个人直接读懂：

- 每条记录脱离原对话仍然成立。
- 不写 `Q1=A`、`Q2=B` 这类引用；问题只存在于对话，字母的含义没有落盘。
- 决策记录写：完整问题、选项及含义、用户选择、结论、影响章节。
- 不把“按推荐”“照你说的”“其余都同意”当成结论，要写出被采纳的内容。
- 用户回答“都可以”“你决定”时，把推荐记为 `assumption`，并说明何时需要确认。

### 不编造设计

这是本技能最重要的约束：

- 不从通用模板、行业惯例、相似产品的界面中推断用户没有要求的功能或页面。
- 通用交互模式（如搜索框、下拉菜单）只能用来**提问**，不能直接写进设计。
- 用户没有提到、但实现核心流程明显不可缺少的页面或交互，先作为问题提出；用户确认后才进入设计，未确认前标 `pending`。
- 不引入用户材料中没有的页面、角色、字段和流程；确需引入时先问。
- 示例、类比、参考产品只用于说明，不进入设计正文。

### 设计不是实现

- 可以写：页面上有什么元素、元素之间如何配合、点击后发生什么、跳转到哪里、空 / 错误状态显示什么。
- 不写：用什么前端框架、组件库、数据库、接口签名、具体的 CSS 值或色号。
- 视觉只写方向性约定（如“主色倾向简洁中性、强调色用于关键操作”），不写具体色值、字号、间距像素。

### 页面详细设计的四要素

核心页面的详细设计必须齐备四要素，才能被原型阶段直接实现：

1. **元素（EL）**：页面上有什么，各自的作用。
2. **交互（INT）**：对每个元素，用户做什么、系统如何响应。
3. **状态（ST）**：页面 / 元素在空、加载、错误、禁用、完成等情况下如何呈现。
4. **跳转（LINK）**：每个可点击动作之后去哪个页面或触发什么变化。

四要素缺失任一项，该页面不能标 `confirmed`。次要页面允许只写元素和目的，其余标 `deferred` 或从简说明。

### 范围控制

- 页面和交互必须落在 `REQUIREMENTS.md` 已确认的范围内，或用户本轮明确新增。
- 范围扩大必须由用户确认；AI 不能自行加入“顺便做”的页面。
- 设计膨胀时优先做减法：能否合并页面、能否用更简单的交互满足需求。
- 范围决定要记录理由，不只记录结论。

### 阶段边界

用户在本阶段追问 HTML 原型、视觉、技术选型或编码时：

1. 记录为 `deferred`；
2. 说明为什么现在不定；
3. 指出由哪个后续阶段处理；
4. 不因为用户追问就提前做原型或技术设计。

只有用户明确要求切换阶段或调用其他技能时，才离开本阶段。

## 文档落盘与更新节奏

1. 阶段 01 结束时，创建 `PRODUCT_DESIGN.md` 骨架，填写文档信息、输入来源、设计原则与约束。
2. 阶段 02–06 每轮回答后，立即更新相关章节、状态、决策记录和待确认事项。
3. 阶段 07 审查后，更新受影响章节，并记录审查问题与处理结果。
4. 补齐所有章节，运行 [CHECKLIST.md](./CHECKLIST.md)，处理失败项后再交付。

文档中的状态、结论和正文必须一致。改了结论，要同步改受影响的流程、页面、交互、约束和移交说明。

## 修订模式

用户读完后提出修改时，不重新生成整份文档：

1. 读取最新版 `PRODUCT_DESIGN.md`。
2. 把每个修改点登记为 `CH-001`、`CH-002`……
3. 评估修改是否与需求、设计原则、交互规范一致；是否属于设计膨胀或越界到原型 / 技术阶段。
4. 每轮挑 2–4 个最需要决定的修改点，说明影响和可选处理方式，由用户确认。
5. 只改受影响章节，同步状态、假设、依赖、风险和追溯关系。
6. 在文末追加修订记录，保留原描述，不覆盖历史。
7. 重新运行 [CHECKLIST.md](./CHECKLIST.md)，给用户一份变动摘要。

修订时同样遵守“不照单执行、不替用户否决、不静默改结论”。

## 完成条件

同时满足以下条件才能宣告本阶段完成：

- 产品整体信息架构已经明确，页面层级与导航清晰。
- 核心用户流程和异常分支已经梳理，正常与异常路径都有结论或标记。
- 全部页面已列入页面清单，角色权限和详细程度标记齐全。
