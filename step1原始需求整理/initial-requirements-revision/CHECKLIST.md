# 需求文档修订检查清单

在宣告一次修订完成前逐项检查。

判定规则：

- **通过**：有明确证据，能指向 `INITIAL_REQUIREMENTS.md` 的具体章节或修订记录。
- **不适用**：本次修订确实不涉及，并已说明原因。
- **失败**：既没有证据，也没有说明不适用。

出现失败项时，回到 [SKILL.md](./SKILL.md) 的对应步骤修正，不宣告修订完成。

## 1. 修改前检查

- [ ] 已读取最新版 `INITIAL_REQUIREMENTS.md`，不是凭记忆修改。
- [ ] 每个修改点都有编号（`CH-xxx`）、位置、原内容和期望结果。
- [ ] 缺失的“改哪里”“改成什么”已通过提问补齐，没有用猜测填空。
- [ ] 修改点涉及的需求、场景、冲突和依赖已定位。

## 2. 合理性评估检查

- [ ] 每条修改点都评估了目标一致、内部一致、来源可追溯、完整性、阶段边界、必要性和影响范围。
- [ ] 每个评估结论都有具体依据，引用了需求编号或章节，不是主观判断。
- [ ] 越界到功能规则、MVP、优先级、验收标准或技术选型的要求，已标为 `deferred`。
- [ ] 与其他已确认需求矛盾的修改点，没有被直接执行。

## 3. 讨论与确认检查

- [ ] 建议调整和建议不采纳的修改点，都给出了理由和替代方案。
- [ ] 涉及两条需求取舍的，由用户明确裁决，AI 没有自行选择。
- [ ] 用户坚持的修改，已记录“已提示影响，用户坚持”。
- [ ] 未采纳的修改点保留了用户的原始要求，没有直接删除。
- [ ] 每个修改点都有用户明确选择，或明确暂缓。

## 4. 执行检查

- [ ] 新增需求编号顺延且不重复。
- [ ] 修改过的需求保留了原描述，可在修订记录中查到。
- [ ] 删除需求经过用户明确确认，且已检查引用它的场景、依赖和冲突。
- [ ] 状态变更都有用户回答依据，没有把 AI 推测写成已确认。
- [ ] 新引入的冲突标为 `conflict` 并登记第 06 节，没有静默解决。
- [ ] 只改了达成一致的内容，没有顺带改写无关章节。
- [ ] 修改后的表述自包含，没有新增 `Q1=A`、`Q2=B` 这类引用。
- [ ] 没有把“按推荐”“照你说的”“其余都同意”保留为结论。
- [ ] 旧文档中无法自解释的 Q 代号已还原；无法还原的标 `pending` 并已请用户补充。

## 5. 一致性联动检查

- [ ] 第 02 节对应关系与第 04 节需求清单一致。
- [ ] 第 03 节场景关联的需求编号仍然有效。
- [ ] 第 05 节澄清记录与对应需求的状态、描述一致。
- [ ] 第 06 节冲突记录与涉及需求的状态一致。
- [ ] 第 07 节依赖关系没有指向已删除或不存在的需求。
- [ ] 第 08 节约束与修改后的需求不矛盾。
- [ ] 第 09 节未决事项、假设、风险已更新。
- [ ] 第 10 节的已明确内容、不确定性和完成状态反映最新结果。
- [ ] 需求编号连续，全文没有悬空引用。
- [ ] 全文搜索 `Q\d`：只出现在 2.1 原话与 5.1 还原表，其他位置均已改写为结论实质。

## 6. 修订记录检查

- [ ] 文档信息中的版本号已递增。
- [ ] 修订记录写明了版本、日期、修改点编号、结论和影响章节。
- [ ] 未采纳和暂缓的修改点也在修订记录中留痕。
- [ ] 修订记录没有覆盖历史版本的内容。

## 7. 交付检查

- [ ] 变动摘要说明了改了什么、为什么改。
- [ ] 变动摘要说明了哪些没改、为什么没改。
- [ ] 新引入的待确认项、冲突或风险已告知用户。
- [ ] 用户已确认修改结果。

## 退出判定

- 全部通过，或所有不适用项都有说明：本次修订完成。
- 任一项失败：回到工作流程修正，不得宣告完成。
