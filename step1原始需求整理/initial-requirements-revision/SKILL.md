# 需求文档修订

用户读完 `INITIAL_REQUIREMENTS.md`，指出一个或多个不符合要求的地方。本技能负责评估这些修改点是否合理、是否与其他内容冲突，通过与用户讨论达成一致，再执行修改。

核心原则：**不照单执行，也不替用户否决。** 用户提的是修改诉求，不是最终方案；AI 给的是评估和建议，不是决定权。

修改的对象是已有文档，不是重新做一遍需求整理。

## 与 initial-requirements 的分工

| | initial-requirements | 本技能 |
| --- | --- | --- |
| 时机 | 首次整理原始需求 | 文档已存在，用户发现不符 |
| 输入 | 零散描述、笔记、聊天记录 | 具体修改点 |
| 主要动作 | 分类、澄清、检测冲突 | 评估修改合理性、讨论、执行修改 |
| 产物 | `INITIAL_REQUIREMENTS.md` v0.1 | 同一文件的新版本 + 修订记录 |

本技能只处理用户提出的修改点及其牵连内容，不重新访谈全部需求。

## 输入

必须先读现有 `INITIAL_REQUIREMENTS.md`。找不到时，请用户确认路径，或提示先用 `initial-requirements` 生成文档。

用户的修改点可以是：

- 一条：`REQ-003 写错了，我不是要自动执行，只要提醒`
- 多条：编号列表，每条一句
- 按章节：`第 05 节 CL-002 的结论不对`
- 没有编号：描述现象，由 AI 定位到具体条目

修改点先登记为 `CH-001`、`CH-002`……。每条记录位置、原内容、期望结果、用户理由。缺少“改哪里”或“改成什么”时先问清，不用猜测补齐。

## 工作流程

### 1. 读取并建立基线

读完整份文档，记录：当前版本、状态分布（已确认/待确认/冲突/假设/暂缓）、与修改点相关的需求、场景、冲突和依赖。

完成标准：能说出每个修改点落在哪一节、涉及哪些需求编号。

### 2. 登记修改点

建立修改单：

| 编号 | 位置 | 原内容 | 期望改为 | 用户理由 | 状态 |
| --- | --- | --- | --- | --- | --- |
| CH-001 | [04 / REQ-003] | [原文摘要] | [用户想要的结果] | [用户说明] | 待评估 / 讨论中 / 已采纳 / 已调整采纳 / 未采纳 / 暂缓 |

完成标准：每条都有位置、原内容和期望结果；缺失信息已通过提问补齐。

### 3. 逐条合理性评估

按「合理性评估维度」检查每条修改点，给出结论：建议采纳、建议调整、建议不采纳、需用户裁决。结论必须引用具体条目作为依据，不能只给感觉。

完成标准：每条修改点都有评估结论和依据；涉及其他章节的影响已列出。

### 4. 分轮讨论

每轮选 2–4 个最需要用户决定的修改点，按下述格式提问：

```text
Q1 - CH-001：<标题>
评估：<建议采纳 / 建议调整 / 建议不采纳 / 需用户裁决>
依据：<引用具体需求编号、约束、场景>
影响：<会牵连哪些条目>
可选方案：
A. 按你的原要求修改，同时把 REQ-00x 标为冲突
B. 改成 ……，与 REQ-00x 保持一致
C. 暂缓，记入第 09 节
推荐：<选项 + 理由>
```

讨论规则：

- 用户坚持与已确认需求冲突的修改时，不能静默执行；必须让用户选择：改哪一条、两条都改、标为冲突、或暂缓。
- 用户坚持但依据不足时，可以执行，但要在修订记录写明“已提示影响，用户坚持”。
- 被判定不合理的修改，记录“未采纳”和原因，保留用户的原始要求，不删除。
- 用户改变主意时，重新评估，并检查是否与之前的回答矛盾。
- 用户说“就按我说的改”时，仍要先给出影响提示；用户确认后再执行。

完成标准：本轮修改点都有用户明确选择，或明确暂缓。

### 5. 执行修改

只改达成一致的部分。执行规则：

| 修改类型 | 处理方式 |
| --- | --- |
| 新增需求 | 编号顺延（如 `REQ-012`），来源写“用户修订（CH-xxx）” |
| 修改需求 | 新描述生效；原描述写入修订记录，不覆盖历史 |
| 删除需求 | 必须用户明确确认；删除后检查引用它的场景、依赖和冲突 |
| 状态变更 | 依据用户明确回答；`pending` → `confirmed` 需有回答，`conflict` 未解决不得转 `confirmed` |
| 措辞修正 | 错别字、格式、编号排序可直接改，但登记修订记录 |
| 冲突新增 | 标 `conflict`，登记第 06 节，不静默选择 |

记录规则：

- 修改后的表述必须自包含；代号只做索引，引用处写出结论实质。
- 不新增 `Q1=A`、`Q2=B` 这类引用；引用澄清时写“用户澄清：<结论>”。
- 不把“按推荐”“照你说的”保留为结论；写出被采纳的内容。
- 旧文档中存在无法自解释的 Q 代号时，先在 05.1 节还原成完整问题与结论；无法还原的标 `pending`，请用户补充。
- 修改用户原话以外的内容时，保持第 2.1 节原话不变。

完成标准：修改单状态与文档内容一致；每条修改都能对应到具体章节，且脱离原对话可读懂。

### 6. 一致性联动

一处修改往往牵连多处。按联动表逐项检查并更新：

| 改动位置 | 必须检查 |
| --- | --- |
| 04 需求清单 | 02 对应关系、03 场景关联、07 依赖、09 未决事项 |
| 05 澄清结论 | 对应需求的状态和描述 |
| 06 冲突处理 | 涉及需求的状态、09 风险 |
| 02 原始描述 | 是否仍能追溯到来源；新增内容是否有来源 |
| 新增或删除需求 | 编号连续性、全部引用点 |
| 全文 Q 代号 | 只允许出现在 2.1 原话与 5.1 还原表；其他位置的引用改为结论实质 |
| 任何修改 | 文档版本、修订记录、10.2 不确定性、10.4 完成状态 |

完成标准：没有悬空引用；编号连续；全文没有无法自解释的 Q 代号；所有关联章节与修改后的正文一致。

### 7. 复核与交付

运行 [CHECKLIST.md](./CHECKLIST.md)，然后向用户提交变动摘要：

- 改了哪些条目，为什么改。
- 哪些修改点未采纳或暂缓，原因是什么。
- 本次修改新引入的待确认项、冲突或风险。
- 下一步建议。

用户确认后，修订结束。用户不确认时，回到第 4 步继续讨论。

完成标准：用户确认修改结果，CHECKLIST 没有未处理的失败项。

## 合理性评估维度

| 维度 | 检查内容 | 不合理信号 |
| --- | --- | --- |
| 目标一致 | 修改后是否仍服务于第 01 节的问题、目标和场景 | 改完与产品目标脱节 |
| 内部一致 | 与已确认需求、约束、依赖是否矛盾 | 需要同时改另一条却没提 |
| 来源可追溯 | 是否改变用户原意，是否有依据 | 把 AI 建议当用户要求；无来源 |
| 完整性 | 修改后是否缺少角色、条件、边界 | 只改一半，留下悬空引用 |
| 阶段边界 | 是否越界到功能规则、MVP、优先级、验收标准、技术选型 | 要求写“系统具体怎么实现” |
| 必要性 | 是纠正错误，还是偏好变化 | 只换措辞却改变含义 |
| 可独立理解 | 改后的表述能否脱离原对话读懂 | 引入 `Q1=A`，或把“按推荐”当结论 |
| 影响范围 | 是否牵连场景、依赖、冲突、未决事项 | 改一条，其他章节全部失配 |

评估结论的含义：

| 结论 | 含义 | 后续动作 |
| --- | --- | --- |
| 建议采纳 | 合理，且与现状一致 | 用户确认后执行 |
| 建议调整 | 方向合理，但表述、范围或条件需要改 | 给出替代方案供选择 |
| 建议不采纳 | 与目标、已确认需求或阶段边界冲突 | 说明理由，记录未采纳 |
| 需用户裁决 | 涉及两条需求的取舍，AI 无权决定 | 给出选项，由用户选择 |

## 边界

| 本技能做 | 本技能不做 |
| --- | --- |
| 评估修改点合理性 | 需求分析、功能规则定义 |
| 讨论取舍并执行修改 | 替用户决定冲突怎么处理 |
| 同步受影响的章节 | 调整 MVP、优先级、验收标准 |
| 记录修订历史 | 技术选型、架构或实现方案 |

用户提出越界修改时，记录为 `deferred`，写在修订记录里，说明留给后续阶段。

## 交付物

- 更新后的 `INITIAL_REQUIREMENTS.md`。
- 文档末尾的修订记录：版本、日期、修改点、结论、影响章节。
- 对话中的变动摘要。

## 退出条件

同时满足才结束：

- 每个修改点都有结论：已采纳、已调整采纳、未采纳或暂缓，并写明原因。
- 修改已落到文档，联动章节已同步。
- 没有未处理的新冲突；新引入的待确认项已登记。
- CHECKLIST 通过，或对“不适用”项有说明。
- 用户确认修改结果。
