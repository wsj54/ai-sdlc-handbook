# 原始需求整理检查清单

在宣告「原始需求整理」阶段完成前逐项检查。

判定规则：

- **通过**：有明确证据，能指向 `INITIAL_REQUIREMENTS.md` 的具体章节或条目。
- **不适用**：本项目确实没有该项内容，并在文档中写明原因。
- **失败**：任一项既没有证据，也没有说明不适用。

出现失败项时，回到 [SKILL.md](./SKILL.md) 的对应步骤修正，不宣告阶段完成。

## 1. 需求完整性检查

- [ ] 用户明确提出的每条需求，都在第 04 节有对应条目。
- [ ] 每条需求都能追溯到第 02 节的来源原话或某轮用户回答。
- [ ] 合并重复表达时，保留了有价值的细节差异。
- [ ] 没有擅自删除需求；改写过的表达没有改变原意，或已标为 `pending`。
- [ ] 用户提出的“不要”“限制”“排除”也作为约束记录在第 08 节。
- [ ] 后续轮次新增的想法已经补录，没有只留在对话里。

## 2. 逻辑一致性检查

- [ ] 同一功能的不同描述之间，没有未处理的矛盾。
- [ ] 不同功能之间，没有未处理的规则冲突。
- [ ] 用户目标与具体功能之间的冲突已登记。
- [ ] 用户约束导致某需求无法实现时，已指出并处理。
- [ ] 前后轮次回答不一致时，已请用户确认以哪条为准。
- [ ] 每个冲突都有用户确认的处理方式，或明确 `deferred` 并记入第 09 节风险。
- [ ] 没有把仍存在冲突的需求标为 `confirmed`。

## 3. 歧义检查

- [ ] 程度词、范围词、动作词、角色和结果标准都已澄清，或标为 `pending`。
- [ ] 每个歧义点对应一个明确问题，没有把多个问题揉成一个。
- [ ] 没有替用户选择解释；每个 `pending` 项都有可选解释和推荐。
- [ ] 第 05.2 节写入了完整问题、用户选择与结论。
- [ ] 用户回答后仍然模糊的内容，已拆成新的待确认问题。

## 4. 信息自包含检查

- [ ] 全文搜索 `Q\d`：只出现在第 2.1 节原话和第 05.1 节还原表中，其他地方没有 `Q1=A`、`Q2=B` 这类引用。
- [ ] 每条需求的“来源”都写出原话主题与澄清结论，不是只有 `S-00x`、`CL-00x` 代号。
- [ ] 没有把“按推荐”“照你说的”“其余都同意”当成结论。
- [ ] 第 05.2 节每行都有完整问题、字母对应的含义、用户选择和结论。
- [ ] 第 05.1 节存在时，每个字母回答都已还原；无法还原的标 `pending` 并已请用户补充。
- [ ] 第 9.1 节只保留仍未解决的问题，已确认的不再留在本节。
- [ ] 把文档单独交给另一个对话，也能读懂每条需求与结论，不需要回看原对话。

## 5. 信息状态检查

- [ ] 只使用 `confirmed`、`pending`、`conflict`、`assumption`、`deferred` 五种状态。
- [ ] 没有把 AI 的建议或推测写成用户确认。
- [ ] 无法确定的信息标为 `pending` 或 `assumption`，没有用推测填补空白。
- [ ] 每个 `assumption` 写明了假设内容、采用原因和影响。
- [ ] 每个 `deferred` 写明了暂缓原因和移交阶段。
- [ ] 每条需求只有一个状态，且与正文描述一致。
- [ ] 状态变化有回答依据，能在第 05 节或第 06 节找到留痕。
- [ ] 同时存在冲突与歧义时，优先记录为 `conflict`。

## 6. 阶段交付检查

- [ ] `INITIAL_REQUIREMENTS.md` 已按 [TEMPLATE.md](./TEMPLATE.md) 的 10 节生成。
- [ ] 文档信息、状态说明、日期已填写。
- [ ] 第 09 节完整记录待确认问题、暂定假设、暂缓事项和潜在风险。
- [ ] 第 10 节写明已明确的认知、剩余不确定性和下一阶段关注点。
- [ ] 文档没有进入功能规则、MVP、优先级、验收标准或技术选型。
- [ ] 没有为了满足模板而编造内容；不适用项已说明原因。
- [ ] 文档足以支撑下一阶段开展需求分析与范围管理。
- [ ] 用户已明确确认“可以进入下一阶段”。

## 退出判定

- 全部通过，或所有不适用项都有说明：阶段完成，可以交接。
- 任一项失败：回到工作流程修正，不得宣告完成。
