# 原始需求整理

把用户零散、模糊、可能相互矛盾的想法，整理成一份经过初步澄清、结构化、没有未处理认知冲突的原始需求文档，交给下一阶段「需求分析与范围管理」。

这是一次**整理**，不是一次需求分析。本阶段回答：

- 用户想解决什么问题？
- 用户提出了哪些想法？
- 描述里有没有歧义？
- 不同想法之间是否冲突？
- 用户有哪些约束？
- 哪些事情还没有确定？

本阶段不回答：产品具体怎么满足这些问题、哪些功能进入产品、功能规则怎么定义、如何排优先级、MVP 是什么、用什么技术。

产出：`INITIAL_REQUIREMENTS.md`。文件结构见 [TEMPLATE.md](./TEMPLATE.md)；宣告完成前必须通过 [CHECKLIST.md](./CHECKLIST.md)。

## 输入

接收用户用自然语言描述的初始想法、功能描述、使用场景、目标、限制条件，也接收聊天记录、零散笔记和已有文档。

用户没有提供输入时，先请其用自然语言说明四件事：想解决什么问题、想做出什么、给谁用、已经有哪些想法。用对话获取，不用模板逼问。

读到新材料时逐句保留来源。用户的原话是后续所有归纳的依据。

## 工作流程

### 1. 建立基线

读完所有输入，在项目工作目录创建或更新 `docs/01-原始需求/INITIAL_REQUIREMENTS.md`；用户指定了路径就以用户为准。

先记录文档信息：项目名称（可暂定）、日期、输入来源。

完成标准：用户明确说过的每条需求，都能在文档里找到出处。

### 2. 首轮整理

按「需求分类与归纳规则」完成：

- 拆分、归类、合并重复表达。
- 给需求编号：`REQ-001`、`REQ-002`……
- 标注来源原话。
- 识别模糊点、冲突、依赖、约束和未决事项。
- 先写出文档 v0，所有判断都落在五种信息状态里。

完成标准：文档 v0 已落盘；每条需求都有编号、来源和状态；每个疑点、冲突都有独立条目。

### 3. 提问轮次

从「当前必须明确」的问题中选 2–4 个，按阻塞程度排序：会阻塞后续所有判断的先问。

每个问题都要说明为什么问、有哪些可选解释、推荐哪一种。推荐是建议，不是替用户决定。

用下面的格式，问完一轮就停，等待回答：

```text
问题 1｜<能独立理解的标题>
为什么问：<它影响哪个需求、冲突或约束>
可选解释：
A. <解释 A 的具体含义>
B. <解释 B 的具体含义>
C. <解释 C 的具体含义>
推荐：<推荐项 + 理由>
```

问题编号只在本次对话里指路，不能成为文档里的唯一信息。收到回答后，按“完整问题 + 用户选择的含义 + 结论”写进第 05 节。

完成标准：本轮问题都得到回答，或用户明确表示暂不回答、暂缓处理；回答已转成自包含的决策记录。

### 4. 更新文档

每轮回答后立即更新文档，按下表处理：

| 用户反应 | 处理方式 | 状态 |
| --- | --- | --- |
| 明确确认某一种解释 | 写入回答，更新需求描述 | `confirmed` |
| 回答仍模糊，或产生新歧义 | 保留问题，必要时拆出新问题 | `pending` |
| 冲突被确认并选定处理方式 | 记录处理方式与影响 | `confirmed` |
| 不回答但要求继续推进 | 写明假设内容、采用原因和影响 | `assumption` |
| 当前阶段不需要确定 | 写明暂缓原因和移交阶段 | `deferred` |

每轮回答先写成一条决策记录，再改需求：完整问题、被选中的解释及其含义、结论、影响的需求。结论写实质，例如“断网时已生成试卷仍可作答”，而不是“Q5=B”。

更新时保留用户原话，不要用归纳结果覆盖原始表述。同时检查新回答是否引入新的歧义、冲突、依赖或约束。

完成标准：文档状态与本轮回答一致；新增决策记录自包含；新增疑点、冲突、依赖都已登记。

### 5. 循环检查

有新引入的问题就回到第 3 步。没有新问题，就检查是否还存在「当前阶段必须明确」的阻塞项。

完成标准：没有未处理的阻塞性歧义或冲突。

### 6. 阶段验收

逐项运行 [CHECKLIST.md](./CHECKLIST.md)，然后向用户提交四样东西：

- 已确认的需求摘要。
- 待确认、冲突、暂定假设、暂缓处理的清单。
- 需要下一阶段重点关注的事项。
- 一个明确问题：是否可以进入下一阶段。

用户明确确认之前，不宣告阶段完成，不进入需求分析。

完成标准：用户明确确认，且 CHECKLIST 没有未处理的失败项。

## 需求分类与归纳规则

按需使用下列分类，不必为每个项目建满所有分类：

- 用户与角色
- 目标与价值
- 使用场景与流程
- 功能需求
- 数据与内容
- 交互与体验
- 权限与安全
- 通知与提醒
- 性能、可用性、离线等非功能约束
- 集成与外部依赖
- 范围与边界

归纳时遵守：

- 先逐句提取，再归类。用户没说的内容不补进去。
- 合并重复表达时保留细节差异；有差异就并列，不合并成一条。
- 一条描述包含多个需求时拆分，每条都保留同一句来源。
- 可以把原话润色通顺，但含义变化必须标为待确认。
- 用户说的“想要”和“不要”都算需求或约束。

## 模糊需求识别与澄清规则

优先检查这些模糊信号：

| 信号 | 例子 |
| --- | --- |
| 程度词 | 自动、智能、尽量、快速、方便、好用、及时 |
| 对象不清 | 任务、项目、用户、提醒、同步 |
| 范围不清 | 所有、全部、随时、长期 |
| 动作不清 | 管理、安排、优化、处理、跟进 |
| 条件不清 | 根据情况、必要时、优先级高的 |
| 角色不清 | 谁可以看、谁可以改、谁可以删 |
| 结果不清 | 做到什么程度算成功 |

处理规则：

- 不替用户选择一种解释。
- 列出 2–3 种合理解释，说明彼此差异。
- 给出推荐解释和理由，但状态保持 `pending`，直到用户确认。
- 一次只澄清一个歧义点，不把多个问题揉成一个。

示例：用户说“我希望 AI 能自动帮我安排任务”。

不要直接理解成“AI 自动排程”。先拆出可选解释：

- 只给出时间建议，由用户确认。
- 直接修改任务的计划时间。
- 根据优先级、截止日期和空闲时间自动排程。
- 是否允许调整用户已经安排好的任务。

然后逐项确认。

## 冲突检测规则

检查五类冲突：

1. 同一功能的不同描述互相矛盾。
2. 不同功能之间存在规则冲突。
3. 用户目标与具体功能冲突。
4. 用户提出的约束使某项需求无法实现。
5. 前后描述不一致，包括前后轮次回答之间的不一致。

处理规则：

- 指出冲突涉及的需求编号和原话。
- 说明冲突原因和影响。
- 给出可选处理方式及各自后果，附推荐。
- 由用户选择。AI 不自行裁决，不静默改需求。
- 用户暂不处理时，状态保持 `conflict` 或改为 `deferred`，并写入第 09 节风险。
- 冲突未解决前，相关需求不能标为 `confirmed`。

示例：用户同时提出“任务必须由用户手动确认才能修改”和“AI 可以根据情况自动调整所有任务的时间”。

应指出冲突，并问：AI 自动调整时间是否可以绕过用户确认？还是只能生成建议、等待批准后执行？不要替用户选其中一条。

## 关联与依赖识别规则

记录明显的关系：

- A 依赖 B：没有 B 就无法实现 A。
- A 与 B 共享同一数据或对象。
- A 是 B 的前置条件。
- A 与 B 可能互斥。

只记录关系、前置条件和影响。不设计系统架构、不排优先级、不定义实现方案。

## 信息状态管理规则

所有信息只使用五种状态：

| 状态键 | 展示名 | 含义 | 使用条件 |
| --- | --- | --- | --- |
| `confirmed` | 已确认 | 用户明确表达并确认 | 用户原话明确，或用户明确回答后 |
| `pending` | 待确认 | 存在歧义，需要用户回答 | 有 2 种以上合理解释 |
| `conflict` | 存在冲突 | 与其他需求或约束矛盾 | 冲突尚未解决 |
| `assumption` | 暂定假设 | 为推进讨论暂时采用 | 用户暂不回答但要求继续 |
| `deferred` | 暂缓处理 | 当前阶段不需要确定 | 属于后续阶段或暂不决定 |

状态转换规则：

- 只有用户明确回答或确认，才能把 `pending`、`conflict`、`assumption` 转为 `confirmed`。
- AI 的推测只能进入 `assumption`，不能进入 `confirmed`。
- 一个需求只保留一个状态；同时存在冲突和歧义时，先记 `conflict`。
- 每轮更新后检查：有没有把建议写成用户确认？有没有用推测填补空白？
- 状态变化要在第 05 节或第 06 节留下回答依据。

## 记录规则（自包含）

文档要能被另一个对话、另一个人直接读懂：每条记录脱离原对话仍然成立。

- 代号只做索引，不做含义载体。`S-001`、`CL-001` 可以出现，但引用处必须同时写出结论本身。
- 不写 `Q1=A`、`Q2=B`、`S-003（Q4=C）` 这类引用：问题只存在于对话，字母选项的含义没有落盘。
- 不把“按推荐”“照你说的”“其余都同意”当成结论；必须写出被采纳的内容。
- 每条需求的“来源”写两段：来自哪句原话（主题）+ 用户澄清的结论。
- 提问时每个问题带能独立理解的标题；选项写含义，不只有字母。
- 第 2.1 节的原始片段原样保留，不修改；其中无法理解的字母回答，在第 05.1 节补“问答还原”。
- 无法还原的字母回答标 `pending`，请用户补充问题与答案，不用猜测补齐。
- 交付前全文搜索 `Q\d`：只允许出现在第 2.1 节原话和第 05.1 节还原表中。

示例：

- 不合格：`S-003（Q2=B）`
- 合格：`用户澄清：作答期 AI 只解释题意、可指出题面问题；不评价答案对错，不给答案与思路`

## 用户沟通与提问规则

- 每轮 2–4 个问题，按阻塞程度排序。
- 每个问题说明为什么问，并给出可选项和推荐答案；选项要写含义。
- 用户只回“选 B”“Q1 选 A”时，先把该选项的含义复述成结论，再写入文档。
- 用户说“按推荐”“都同意”时，把推荐内容本身写进结论，不能只记“按推荐”。
- 用户说“不知道”“还没想好”时，记为 `assumption` 或 `deferred`，不逼答。
- 用户的新回答与之前矛盾时，指出前后差异，请其确认以哪条为准。
- 用户提出新想法时，先归入文档，再检查是否引入新冲突。
- 用户要求直接给结论时，可以给推荐，但必须标明这是建议，状态不变。
- 只问当前阶段必须明确的问题，不追求把所有问题问完。
- 不为了文档完整而制造内容；没有相关内容就写“不适用”并说明原因。
- 归纳、重组和优化表达是允许的；改变需求含义必须先让用户确认。

## 边界

| 本阶段做 | 本阶段不做，留给下一阶段 |
| --- | --- |
| 用户想解决什么问题 | 产品具体如何满足这些问题 |
| 用户提出了哪些想法 | 哪些功能应该进入产品 |
| 描述中有没有歧义 | 功能规则如何定义 |
| 不同想法之间是否冲突 | 如何解决优先级和范围冲突 |
| 用户有哪些约束 | 如何把约束转化为具体需求 |
| 哪些事情还没有确定 | 如何确定 MVP、验收标准和优先级 |

用户在本阶段追问下一阶段内容时，记录为 `deferred`，说明为什么现在不定。只有用户明确要求切换阶段或调用其他技能时，才离开本阶段。

## 交付物

- `INITIAL_REQUIREMENTS.md`：按 [TEMPLATE.md](./TEMPLATE.md) 生成。
- 文档同时包含已确认、待确认、冲突、暂定假设、暂缓处理五类信息。
- 不额外生成问题清单；未决事项统一放在第 09 节。
- 文档不出现无法自解释的 `Q1`、`Q2` 引用；代号只做索引。
- 文档生成后如需修改，交给 `initial-requirements-revision` 处理，不手改正文。

## 阶段退出条件

同时满足以下条件才能宣告阶段完成：

- 用户明确提出的需求都已收录，且可追溯到来源。
- 阻塞性歧义已澄清，或用户明确同意以 `assumption`、`deferred` 处理。
- 冲突已解决，或用户明确同意暂缓并记录风险。
- 所有需求状态、来源、关联关系与正文一致。
- CHECKLIST 全部通过，或对“不适用”项有说明。
- 用户明确确认“可以进入下一阶段”。

任一条件不满足，继续第 3–5 步，不宣告完成。
