# CHECKLIST.md — 第六阶段完成检查清单

> 使用规则：宣告本阶段完成前逐项检查。不适用项必须写明原因，不允许静默跳过。

## 一、通用检查（三种模式都必须）

- [ ] 前置文档已读取并在文档基本信息中登记；缺失输入已说明，未凭空补全。
- [ ] 执行模式（A / B / C）已判定，判定理由已记录，**已由用户确认**（DEC-xxx）。
- [ ] 模式顺序正确：**先完成筛查并形成候选 TV 清单，再给出引用证据的推荐模式，最后用户确认**；未在筛查前向用户抛出 A/B/C 选择问题，推荐理由引用了具体 TV 项。
- [ ] 候选 TV 清单经过六维度技术风险筛查，筛查有依据。
- [ ] 影响验证范围或成功标准的信息缺口已收集，或记为 `pending`；AI 未把自设指标当成用户确认的验收标准。
- [ ] TV 清单条目字段完整，来源可追溯（RISK-xxx 或"第六阶段新识别"），每条有处理方式。
- [ ] 用户已确认 TV 清单无遗漏、分类与优先级合理。

## 二、模式 A（跳过）专项

- [ ] 极简版 `TECHNICAL_VALIDATION.md` 已落盘到 `docs/06-技术验证/`。
- [ ] 决策理由结合项目实际填写，注明已完成的筛查依据，不是套话。
- [ ] 已知技术风险与后续注意事项已写明，决策日期已填。
- [ ] 用户已确认跳过决策，可进入第七阶段。

## 三、模式 B / C 专项

### 调研

- [ ] 需要调研的 TV 项均有调研结论；来源均为官方或可靠资料（RES-xxx，含链接与查阅日期），无编造。
- [ ] 调研结论与实测结论已区分；文档支持未直接写成"已验证"。
- [ ] 存在选择空间的 TV 项有方案对比与初步推荐（标注 `assumption`）；无选择空间的写明"从简"原因。

### 验证方案

- [ ] 每个待验证 TV 项的方案八要素齐全（目标 / 假设 / 方法 / 环境 / 输入 / 成功标准 / 失败标准 / 预期产物）。
- [ ] 成功标准可判定、与需求验收标准对齐、经用户确认；失败标准已写。
- [ ] PoC 范围最小化，未越界成 MVP 或产品开发。

### 执行

- [ ] 每个待验证 TV 项已真实执行，或已产出用户执行指引并说明等待中。
- [ ] 所有 `A 实测` 证据有真实运行记录或用户回传结果；**没有把推测、模拟结果或代码审阅结果伪装成真实测试**。
- [ ] 证据文件已存入 `docs/06-技术验证/validation/TV-xxx-xxx/` 并在文档中引用（EV-xxx）。
- [ ] 失败与异常已如实记录，无美化。

### 结论与交接

- [ ] 每条 TV 项有四档结论之一，并附证据等级；**标记"通过"的结论均有 A 级或 B 级证据**。
- [ ] "不通过 / 有条件通过"的项有深入分析和处理方式，处理方式已经用户确认。
- [ ] 七个关键问题（推荐方案、理由、替代方案、局限、需求调整、架构影响、遗留风险）均有答案。
- [ ] 第 8 章架构约束（DC-xxx）完整：技术版本、依赖条件、运行环境、性能边界、成本上限等已明确，可被第七阶段直接执行。
- [ ] 验证结果要求的需求 / 产品设计调整已列为建议并标注待修订文档，未擅自修改前序文档。
- [ ] 遗留风险与待办已记录，明确影响和处理方式。
- [ ] 交接检查清单（phases/06 第 7 节七项）全部通过。
- [ ] 文档自包含：脱离本对话可被第七阶段直接读懂；编号引用处写出了结论本身。
- [ ] 用户已明确确认"可以进入第七阶段"（或有条件进入及其条件）。
