# 阶段 04：制定技术验证方案

本阶段目标：对调研后仍存在较大不确定性的 TV 项，设计实际验证实验。**先明确验证目标和成功标准，再开始编写 PoC 代码**——否则容易出现代码运行成功了，却不知道是否真的证明技术方案可行。

## 1. 统一验证方案结构

每个待验证 TV 项按以下结构制定方案：

| 项目 | 说明 |
| --- | --- |
| 验证目标 | 具体想确认什么？ |
| 验证假设 | 当前认为技术方案应该能够实现什么？ |
| 验证方法 | 通过什么代码、接口调用或实验验证？ |
| 验证环境 | 使用什么语言、版本、环境和依赖？ |
| 测试输入 | 使用什么数据或场景？ |
| 成功标准 | 达到什么条件才算通过？ |
| 失败标准 | 出现什么情况说明方案不合适？ |
| 预期产物 | 测试代码、运行结果、日志或性能数据等 |

示例（占位，非真实项目）：

> 验证目标：确认 AI 模型能否通过工具调用正确创建任务。
> 验证假设：模型能够从自然语言中识别任务标题、截止日期和优先级，并正确调用创建任务工具。
> 验证方法：使用模型 API 编写一个最小化 Function Calling 测试程序。
> 测试输入：准备 20 条不同表达方式的任务创建请求（正式数量和准确率阈值按实际要求确定）。
> 成功标准：字段提取达到约定准确率，工具调用参数符合预期，错误输入能被正确处理。
> 验证产物：测试代码、输入样本、模型输出、测试结果。

## 2. 成功标准必须可判定

- 成功标准要与 `REQUIREMENTS.md` 的非功能需求和验收标准对齐（如需求要求 3 秒响应，验证就要测端到端响应时间）。
- 用户描述的模糊期望（如"要快""要准"）由 AI 转换为可测试指标，但**转换结果必须经用户确认**；AI 自设的指标只能标 `assumption`，不能当成用户确认的验收标准。
- 成功标准和失败标准都要写，失败标准明确"什么情况说明方案不合适"，避免实验后无判断依据。

## 3. 选择验证方式

根据问题性质选择，成本从低到高：

| 方式 | 成本 | 适合验证 |
| --- | --- | --- |
| 文档和资料验证 | 低 | 功能是否支持、接口是否存在、SDK 是否兼容、平台是否允许部署 |
| 小型代码实验 | 中低 | API 能否调用、库能否正常工作、数据结构是否满足要求、模型是否支持结构化输出 |
| PoC 概念验证 | 中 | 多个技术组合后能否完成关键业务流程、关键模块能否协作 |
| 性能、稳定性和边界测试 | 按需 | 性能要求、可靠性要求、安全约束和复杂运行环境 |

调研已能覆盖的问题不再实验；一个 PoC 可同时覆盖多个关联 TV 项时合并设计。

## 4. PoC 设计原则

- **PoC 不是 MVP，更不是简化版完整产品。** 只验证关键技术链路，例如：用户输入 → 模型 API → 识别任务信息 → 调用创建任务工具 → 返回结构化参数 → 验证参数正确。不需要登录系统、任务管理页面、数据库管理界面。
- PoC 尽量独立、最小化，与正式产品代码区分开。
- PoC 代码存入 `docs/06-技术验证/validation/TV-xxx-xxx/`（README + 测试代码 + 输入样本 + 结果文件）。
- 实验代码以后有复用价值的，在架构设计阶段决定是否保留，本阶段不作为产品代码。

## 5. 用户确认验证方案

向用户展示每个 TV 项的验证方案（重点：验证目标、成功标准、需要的配合），确认：

- 成功标准符合用户的实际期望（特别是 AI 转换的量化指标）。
- 测试输入的代表性是否足够（需要真实样本时用户确认或提供）。
- 用户需要配合的事项（账号、环境、回传结果）已明确。

用户确认后，验证方案写入 `TECHNICAL_VALIDATION.md` 第 6 章各 TV 小节的"验证目标 / 验证假设 / 验证方法 / 验证环境 / 测试输入与场景 / 成功标准"，进入 phases/05 执行。

## 完成标准

- 每个待验证 TV 项的方案八要素齐全。
- 成功标准可判定，且经用户确认（AI 转换的指标已区分 `confirmed` 与 `assumption`）。
- 验证方式选择合理，无过度验证。
- PoC 范围最小化，不越界成产品开发。
- 用户需要的配合事项已明确告知。
