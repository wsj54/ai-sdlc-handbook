# 阶段 03：技术调研与方案分析

本阶段目标：对需要进一步确认的 TV 项开展技术调研，弄清"有哪些可行方案、各方案什么条件、有什么坑"，为下一步验证方案（或直接结论）提供依据。

模式 B 时本阶段与 phases/04 合并执行：调研后仍不确定的问题直接给出小型验证安排，不必逐项展开多方案分析。

## 1. 调研内容（四类，按 TV 项实际需要取用）

**A. 技术方案调研**
- 是否有成熟技术或框架可以实现？
- 各技术方案的优缺点是什么？
- 是否有官方推荐的实现方式？
- 是否存在已废弃或不再推荐的技术？
- 是否存在更简单的替代方案？

**B. 技术兼容性调研**
- 技术之间是否兼容？
- 相关 SDK 是否支持目标语言和版本？
- 是否支持目标操作系统？
- 是否存在依赖冲突？
- 是否有特殊部署要求？

**C. 外部服务调研**
- API 是否具有所需能力？
- 是否存在调用次数或速率限制？
- 是否有使用费用？
- 是否有数据传输限制？
- 是否支持所需的认证方式和接口协议？

**D. 实现难度和风险调研**
- 是否有成熟的解决方案？
- 是否存在已知技术缺陷？
- 是否需要用户自行维护复杂组件？
- 是否有较低成本的替代实现？

## 2. 来源规则

1. **优先参考官方文档、官方仓库、官方技术规范和可靠技术资料**，不依赖二手博客作为唯一依据。
2. 每个来源登记为 `RES-xxx`：来源名称、链接、查阅日期、它支撑的结论。
3. 使用检索工具查证时，区分"官方说法"与"社区经验"；无法确认可靠性的信息标注来源性质。
4. 查不到的如实写"未找到可靠资料"，标 `pending`，不编造。

## 3. 调研结论与实测结论必须区分

这是本阶段的诚信红线：

- 官方文档写明支持某项功能 → 只能证明该功能**在文档描述的条件下**受支持（`B 文档` 级证据）。
- 不能直接证明它在当前项目环境中一定运行正常——那需要 phases/05 的实测（`A 实测` 级证据）。
- 写入文档时明确标注证据等级；调研结论不得直接写成"已验证"。

## 4. 产出：可选方案与对比

只有**确实存在选择空间**的 TV 项才做多方案比较（TEMPLATE 第 5 章允许"从简"）：

- 列出候选方案 `OPT-xxx`（技术名称 + 一句话定位）。
- 对比维度按需选取：能力匹配度、成熟度、兼容性、成本、部署复杂度、维护负担、与用户技术偏好的契合度。
- 给出初步推荐 + 理由，标注为 AI 建议（`assumption`），最终取舍在验证结果出来后由用户确认。
- 有明确结论（如"该库官方文档明确支持目标环境，无需进一步验证"）的 TV 项，可直接进入初步结论，标 `B 文档` 级证据。

## 5. 落盘

写入 `TECHNICAL_VALIDATION.md` 第 5 章"技术调研与方案分析"：技术问题说明、可选技术方案、技术对比、官方资料与参考来源（RES 清单）。

## 完成标准

- 每条进入调研的 TV 项都有调研结论，并区分了证据等级。
- 来源均有链接和查阅日期，无编造资料。
- 存在选择空间的 TV 项有方案对比和初步推荐（标 `assumption`）。
- 调研后仍不确定的问题已明确列出，转入 phases/04 制定验证方案。
- 直接可下结论的问题已标记，待 phases/06 汇总。
