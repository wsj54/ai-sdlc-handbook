# 阶段 01：上下文、风险筛查与模式判定

本阶段目标：建立验证基线，判断项目需要哪种深度的技术验证（模式 A / B / C），并向用户收集 AI 无法获知的实际信息。**这是整个 skill 的分流点。**

## 1. 读取输入文档

按 [SKILL.md「输入」](../SKILL.md) 的优先级顺序查找并读取前置文档，提取七类信息：

1. 项目的核心功能和 MVP 范围。
2. 关键业务流程和产品交互。
3. 功能实现可能涉及的技术能力。
4. 已有的技术约束和资源限制。
5. 第四阶段已发现的技术风险（FEASIBILITY_REVIEW.md 的风险清单与"移交第六阶段的技术问题清单"）。
6. 尚未确定的技术选型和实现假设。
7. 非功能要求及其验收条件（准确率、响应时间、稳定性、成本等）。

每份输入记录：路径、版本、它回答了什么。多份输入冲突时，以第三阶段确认的需求基线为准，冲突登记到待确认事项。

前置文档全部缺失时不拒绝启动：询问用户是否已完成前序阶段；用户坚持继续时仅基于口述推进，并在文档"文档基本信息"中记录输入缺口。不凭空补全前序结论。

## 2. 技术风险筛查

结合需求与产品设计，从六个维度筛查技术风险：

| 判断维度 | 需要考虑的问题 |
| --- | --- |
| 技术成熟度 | 是否使用成熟、稳定、已有大量实践的技术？ |
| 技术熟悉度 | 用户或 AI 是否有足够经验使用该技术？ |
| 技术不确定性 | 是否存在尚未确定的技术实现问题？ |
| 影响程度 | 如果技术方案失败，会不会影响核心功能或推翻整体设计？ |
| 外部依赖 | 是否依赖第三方 API、模型、平台、硬件或特殊运行环境？ |
| 非功能要求 | 是否存在特殊的性能、安全、可靠性、成本要求？ |

筛查产物：一份**候选 TV 问题清单**（内部工作产物，先不写入正式文档），每条含：初步编号、关联需求、技术问题、初步风险判断。这是待评估清单，不代表全部都要验证。

判断时始终盯住核心问题：**是否存在"高影响、尚未验证"的技术不确定因素？** 即该问题不验证是否可能推翻核心功能实现方式或整体架构。

## 3. 向用户收集信息

根据筛查结果识别信息缺口，按 [SKILL.md「向用户收集信息」](../SKILL.md) 的六个问题域和提问格式，逐轮收集：

- 只问对当前技术验证有实质影响的问题（会改变验证范围、成功标准或模式判定的才问）。
- 事实自己查：某库是否支持异步、某 API 是否有某能力，AI 查文档或写测试代码确认，不推回给用户。
- 用户不知道的记 `pending`，允许标记"待调研"。
- 用户回答后立即更新文档草稿，再判断下一轮问什么；没有实质缺口就停止提问，不追求问满。

**顺序硬规则：提问轮次只用于收集信息缺口。禁止在筛查完成前把"选哪种模式"抛给用户——用户没有被给过评估依据，无法回答，这会迫使用户替 AI 做本应由 AI 完成的评估。**

## 4. 模式判定（分流点）

**触发前提（必须全部满足才能进入本节）：**

1. 前置文档已读取，七类信息已提取。
2. 六维度技术风险筛查已完成，候选 TV 清单已形成。
3. 影响模式判定的信息缺口已收集（如预算、模型要求），或已记为 `pending`。

满足前提后，按 [SKILL.md「三种执行模式」](../SKILL.md) 判定模式：

1. **AI 先完成评估**：对照六维度筛查结果和候选 TV 清单，逐一判断是否存在"高影响、尚未验证"的技术不确定因素。
2. **AI 给出模式推荐 + 推荐理由**，理由必须引用具体证据（候选 TV 清单中影响最大的 TV 项、需求中的非功能要求、外部依赖情况），不能只说"项目比较简单"。
3. **向用户呈现评估结论并请求确认**。模式确认问题的固定格式：

```text
📋 技术风险筛查结论（先给评估，再请确认）
筛查结果：<六维度筛查摘要——发现了哪些技术不确定因素，哪些已有成熟方案>
候选 TV 清单：<N 项，其中高影响 x 项：TV-xxx …>
➡️ 推荐模式：<A / B / C>
推荐理由：<引用具体 TV 项和筛查证据>
影响：<选不同模式分别意味着什么验证深度和用户配合成本>
（用户确认后登记为 DEC-xxx；用户有异议时按用户意见调整并记录）
```

4. **由用户确认**模式选择。模式决定用户后续配合成本（是否提供账号、数据、回传测试结果），必须用户拍板。但拍板的前提是 AI 已给出完整评估——**不允许让用户在没有评估依据的情况下冷选择 A/B/C**。

### 模式 A（跳过）的退出路径

判定为模式 A 时，本阶段收尾即生成极简版 `TECHNICAL_VALIDATION.md`（见 [TEMPLATE.md](../TEMPLATE.md) 跳过模式模板），内容包括：

- 执行模式：跳过
- 决策理由：项目使用成熟技术栈，核心功能均有成熟实现方案，暂无高影响、未验证的技术不确定因素（结合项目实际填写，引用候选清单证明已筛查）
- 已知技术风险：无需要专项验证的风险（或列出已识别但不值得专项验证的低风险项及理由）
- 后续注意事项：架构设计阶段继续确认技术版本及依赖兼容性
- 决策日期

生成后直接进入退出检查，不执行 phases/02–06。

### 模式 B / C 的推进路径

创建 `TECHNICAL_VALIDATION.md` 骨架（第 1–3 章可先行填写），进入 [phases/02-issue-selection.md](./02-issue-selection.md)。

## 落盘要求

- 模式 A：`docs/06-技术验证/TECHNICAL_VALIDATION.md`（极简版）落盘。
- 模式 B / C：文档骨架落盘，含文档基本信息（验证模式字段）、验证概述、技术环境与约束（运行环境、开发环境、外部依赖、资源成本约束）。

## 完成标准

- 前置文档已读取，七类信息已提取，输入缺口已记录。
- 候选 TV 清单已建立，六维度筛查有结论。
- 影响验证范围或成功标准的信息缺口已向用户收集，或记为 `pending`。
- 执行模式已判定并由用户确认，登记为决策记录。
- 模式 A：极简文档已落盘；模式 B / C：文档骨架已落盘。
