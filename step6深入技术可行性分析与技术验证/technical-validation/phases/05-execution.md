# 阶段 05：执行技术验证与 PoC

本阶段目标：按 phases/04 确认的方案真实执行验证，获得 `A 实测` 级证据。**本阶段的核心诚信规则：不允许把推测、模拟结果或代码审阅结果伪装成已经完成的真实测试。**

## 1. AI 与用户的分工

| 角色 | 职责 |
| --- | --- |
| AI | 编写验证代码、运行本环境可执行的测试、整理结果、分析问题 |
| 用户 | 提供账号 / API Key、测试数据、运行环境，执行 AI 无法直接运行的测试并回传真实结果 |

## 2. AI 可直接执行的验证

本环境可以真实运行代码时：

1. 按 phases/04 的方案编写测试代码或 PoC，存入 `docs/06-技术验证/validation/TV-xxx-xxx/`。
2. **真实运行**，保留原始输出（日志、响应、结果文件），登记为 `EV-xxx`。
3. 对照成功标准逐条核对，记录每条的实测值。
4. 与预期不符时如实记录，不做美化；进入 phases/06 分析原因。

注意：AI 无法获取真实外部条件时（如没有 API Key、无法访问付费服务、缺少目标硬件），不得用"模拟响应""假数据推导"替代实测——那属于 `C 推测`，走下方第 3 节的用户执行协议。

## 3. 用户执行协议（AI 无法直接执行的测试）

对必须由用户执行的验证项：

1. **产出用户执行指引**，包含：
   - 最小操作步骤（一条条列出，可照着做）。
   - 需要采集的数据及格式（如：接口返回的原始 JSON、运行耗时截图、控制台报错全文）。
   - 需要覆盖的输入场景（对应测试输入清单）。
   - 注意事项（如不要手动挑选"看起来成功"的结果）。
2. **暂停等待用户回传**，期间不虚构结果、不推进依赖该项的结论。
3. 用户回传后核对：
   - 结果完整覆盖指引要求 → 登记 `EV-xxx`（来源标注"用户实测"）。
   - 结果不完整 → 指出缺什么，请用户补充；不能凭已有部分直接下"通过"结论。
4. 结果未回传前，该 TV 项状态只能是 `尚未验证`。

## 4. 验证方式对应的执行要点

| 方式 | 执行要点 |
| --- | --- |
| 文档和资料验证 | 在 phases/03 完成，此处只核对文档结论是否已登记（`B 文档`） |
| 小型代码实验 | 单文件最小验证；跑通即登记证据，失败也登记失败证据 |
| PoC 概念验证 | 按 phases/04 设计的关键链路实现；组合了多个技术时，逐环节记录输出，便于失败时定位是哪个环节的问题 |
| 性能、稳定性和边界测试 | 在可控环境中测：响应时间、并发、资源消耗、异常恢复、边界输入；记录测试条件（机器、网络、数据量），因为脱离条件的性能数字没有意义 |

## 5. 异常与失败的处理

- 测试失败不是坏结果：失败证据同样是有效证据，照实登记。
- 环境问题（依赖装不上、版本冲突）导致的失败，先区分是"技术方案不行"还是"环境没配对"，修复环境后重试；修复过程记入执行过程。
- 外部服务偶发失败时，区分偶发与稳定失败，必要时按失败标准约定的重试规则重测。

## 6. 落盘

每完成一个 TV 项，写入 `TECHNICAL_VALIDATION.md` 第 6 章对应小节：

- 执行过程：做了什么、跑了什么、遇到什么问题。
- 实际结果：对照成功标准的逐条实测值，附 `EV-xxx` 证据引用。
- 证据文件：`docs/06-技术验证/validation/TV-xxx-xxx/` 下的 README、测试代码、结果文件。

**此处只记录事实，不下结论**——结论分析统一在 phases/06 进行。

## 完成标准

- 每个待验证 TV 项都已执行，或已产出用户执行指引并说明等待中。
- 所有登记为 `A 实测` 的证据都有真实运行记录或用户回传结果支撑。
- 证据文件已存入 validation/ 目录，可独立查阅。
- 失败和异常均已如实记录，无美化。
