# 深入技术可行性分析与技术验证

在需求基线、可行性结论和产品设计已经确认的基础上，回答：**关键技术方案到底能不能实现？能否满足要求？**

本阶段不是把所有技术都研究一遍，而是找出那些可能导致技术方案失败的"**高影响、尚未验证**"的不确定因素，用最小的成本获得足够的证据，让第七阶段的架构设计能够在明确的技术边界内进行。

产出：`TECHNICAL_VALIDATION.md`（唯一核心文档）+ 验证证据目录 `validation/`。文件结构见 [TEMPLATE.md](./TEMPLATE.md)；宣告完成前必须通过 [CHECKLIST.md](./CHECKLIST.md)。

## 与前后阶段的边界（最高优先级约束）

第四、第六、第七阶段都涉及"技术"，但回答的问题不同：

| | 第四阶段（已完成） | 第六阶段（本阶段） | 第七阶段（后续） |
| --- | --- | --- | --- |
| 核心问题 | 项目整体能不能做？ | 关键技术方案能不能实现需求？ | 最终应该如何构建整个系统？ |
| 典型判断 | 资源、预算、平台准入、明显风险 | 某项关键技术能否满足要求、某外部服务是否符合条件、是否需要 PoC | 技术栈确定、模块划分、数据库、接口、系统架构 |
| 产出 | 可行性结论、风险清单、移交验证的问题清单 | 调研结果、PoC 结果、技术结论、架构约束 | ARCHITECTURE.md |

由此推出四条硬约束：

1. **不提前完成系统架构设计。** 本阶段只提供经过验证的技术依据、可行性结论和架构约束。完整的技术栈确定、模块划分、数据库设计、接口设计属于第七阶段。
2. **不提前开发完整产品。** PoC 不是 MVP，更不是简化版产品。PoC 只验证关键技术链路，不需要登录系统、管理页面和完整交互。
3. **验证深度由项目决定，不由流程决定。** 简单项目不做无意义的技术研究；复杂项目不能为赶进度省略关键验证。
4. **所有结论区分证据等级。** 查阅文档不等于实际验证，代码能运行不等于满足业务要求，模拟测试不等于真实环境测试（见"证据分级"）。

## 三种执行模式

phases/01 完成技术风险筛查后判定模式，AI 给出推荐和理由，**由用户确认**。

**判定顺序硬规则：模式推荐只能产生于评估之后，不能先于评估。** AI 必须先读取前置文档、完成六维度风险筛查、形成候选 TV 清单，再给出带证据引用的推荐模式，最后才向用户请求确认。禁止在筛查前或与筛查同时把"A / B / C 选哪种"作为问题抛给用户；用户只做确认或调整，不做冷选择。

| 模式 | 适用 | 典型情况 | 处理方式 |
| --- | --- | --- | --- |
| A：跳过 | 技术方案成熟、无明显技术未知因素 | 普通 CRUD、熟悉的框架做常见功能、无复杂集成、无特殊性能安全要求 | 生成极简决策记录文档，直接进入第七阶段 |
| B：轻量验证 | 整体方案成熟，存在一两个需确认的技术问题 | 接入不熟悉的第三方 API、确认某库是否支持目标环境、验证模型能否稳定返回指定格式 | 查官方文档 + 小型测试代码，不搭建完整 PoC |
| C：完整验证 | 核心功能依赖尚未验证的技术能力 | AI Agent / 多 Agent、RAG 检索质量、本地模型部署、实时通信、高并发、多系统深度集成 | 制定验证方案，必要时独立 PoC，完成测试对比分析 |

判断模式时盯住一个核心问题：**是否存在"高影响、尚未验证"的技术不确定因素？** 即：如果这个问题不验证，是否可能推翻核心功能实现方式或整体架构？

## 输入

按顺序查找并读取：

| 优先级 | 文档 | 用途 |

| 必需 | `docs/04-初步可行性分析/FEASIBILITY_REVIEW.md` | 最直接的风险线索：移交第六阶段的技术问题清单 |
| 必需 | `docs/05-产品设计/PRODUCT_DESIGN.md` | 理解技术要服务的真实使用场景，避免只验证单独技术 |
| 必需 | `docs/02-开发模型与流程/DEVELOPMENT_APPROACH.md` | 开发方式与质量门禁，决定验证方式和深度 |
| 辅助 | `docs/01-原始需求/INITIAL_REQUIREMENTS.md` | 追溯早期约束 |
| 辅助 | `docs/03-需求分析与范围/PRODUCT_BACKLOG.md` | 确定验证优先级 |
| 辅助 | 第三方 API 官方文档、现有源代码、数据样本、部署环境说明、原型文件 | 有时才用，不强制收集 |

规则：

- REQUIREMENTS.md 最重要（定成功标准），FEASIBILITY_REVIEW.md 是风险起点，PRODUCT_DESIGN.md 防止脱离产品体验验证技术。例如需求要求"AI 在 3 秒内完成任务提取"，验证就不能只测能否提取成功，还要测端到端响应时间。
- 缺失处理与第四、第五阶段一致：先读已有文档，判断缺失是否真的影响验证；不为了凑文档清单要求用户准备全部资料。关键文档缺失时说明影响，用户确认后继续；缺口记入文档信息，不凭空补全。
- 注意：**不需要用户提前具备完整技术方案。** 用户负责提供 AI 无法获知的实际业务背景、资源条件、使用约束和验收要求；技术调研和验证由 AI 完成。

## 向用户收集信息

沿用 grilling 式访谈：事实自己查（文档、官方资料、测试代码），决策问用户。六个问题域按需取用，不问满：

**A. 关键需求与优先级** —— 哪些是 MVP 必须实现的？哪些可以暂时用简单方案？哪些不能砍？哪些可以调整交互方式降低实现难度？（例如：AI 自主修改任务是 MVP 核心能力，还是 MVP 只给建议由用户确认后执行？）

**B. 运行环境与资源** —— 目标平台、操作系统、部署方式、网络环境（能否访问海外服务）、硬件资源、预算限制、使用规模。个人项目不为了形式问无意义的问题。

**C. 第三方服务与外部依赖** —— 已确定的服务商、API 文档、是否有 Key/测试账号、免费额度与限制、数据与地域限制、是否允许更换服务商。AI 应用还需确认：模型服务商、能否用海外/付费模型、是否要求模型可替换或支持本地部署、成本上限。未确定服务商的，记为待调研比较事项。

**D. 数据与测试样本** —— 验证依赖真实数据特征时才有意义：有代表性的文件/图片/知识库/任务输入样本、数据字段与规模、预期执行结果与异常场景。涉及隐私优先用脱敏或合成数据。

**E. 质量与验收标准** —— 准确率、响应时间、稳定性（允许偶尔失败？可重试？）、并发量、成本上限、可用性、安全要求。用户可以用模糊期望描述，AI 负责转换成可测试指标，但**AI 自设的指标只能标 `assumption`，不能当成用户确认的验收标准**。

**F. 技术偏好与取舍** —— 是否优先开源、是否减少第三方依赖、是否降低部署复杂度、能否接受付费服务和厂商锁定、重开发速度还是长期可维护性、是否愿意为降难度调整功能。这些决定方案选择的边界，不是让用户选技术栈。

### 提问格式

每轮 1–4 个问题（默认 2–3），只问对当前技术验证有实质影响的问题；用户不知道的记"未知"（`pending`），不逼答；AI 能自己解决的问题不推回给用户。

```text
❓ Q1｜<能脱离上下文独立理解的标题>
为什么问：<影响哪项技术验证的范围或成功标准>
可选答案：
A. <含义>
B. <含义>
➡️ 推荐：<推荐项 + 理由>
影响：<不同选择分别改变什么>
```

用户只回"按推荐"时，把推荐内容本身写成结论。

## 全流程硬规则

### 证据分级（核心诚信机制）

每个 TV 项的结论必须附加证据等级：

| 等级 | 含义 | 示例 |
| --- | --- | --- |
| `A 实测` | 本环境真实运行的结果，或用户回传的真实执行结果 | 测试代码真实跑通、PoC 输出日志、用户提供的 API 实测响应 |
| `B 文档` | 官方文档、技术规范、可靠资料的调研结论 | 官方文档写明支持，附来源链接和查阅日期 |
| `C 推测` | AI 基于经验或类比的分析判断 | "该库通常支持异步调用" |

硬规则：

1. **标记"通过"必须有 A 级或 B 级证据。** 只有 C 级证据的，只能标"尚未验证"或"有条件通过"。
2. **调研结论和实测结论必须区分。** 官方文档写明支持某功能，只能证明该功能在文档描述的条件下受支持，不能证明它在当前项目环境中运行正常。
3. **不允许把推测、模拟结果或代码审阅结果伪装成已经完成的真实测试。** AI 无法真实执行某项测试时，必须产出用户执行指引并等待真实结果。

### 四种结论状态

| 结论 | 含义 | 后续处理 |
| --- | --- | --- |
| 通过 | 已有足够证据证明方案满足当前要求 | 可以作为架构设计依据 |
| 有条件通过 | 基本可行，但需满足某些条件 | 条件写入架构设计约束 |
| 不通过 | 无法满足要求或风险不可接受 | 寻找替代方案、调整需求或缩小范围 |
| 尚未验证 | 缺少必要环境、数据或实验结果 | 保留风险，不得标记为已验证 |

### AI 与用户分工

- AI 负责：编写验证代码、运行可执行的测试、查阅官方资料、整理结果、分析问题。
- 用户负责：提供 AI 无法直接访问的账号、测试数据、运行环境与真实执行结果。
- AI 能自己完成的调研和实验，不反复向用户提问。

### 信息状态

沿用五状态体系：`confirmed`（用户明确确认）/ `pending`（待确认）/ `conflict`（存在冲突）/ `assumption`（暂定假设）/ `deferred`（暂缓处理）。

- AI 的调研结论进 `B 文档` 证据 + 文档结论本身；AI 的推测只能进 `C 推测` 或 `assumption`。
- 只有用户明确回答或确认，才能转为 `confirmed`。
- 一个条目只保留一个状态。

### 编号与追溯

| 前缀 | 用途 |
| --- | --- |
| `TV-xxx` | 技术问题 / 验证项（核心主线编号） |
| `RISK-xxx` | 引用第四阶段风险编号，不重新编号 |
| `OPT-xxx` | 候选技术方案 |
| `RES-xxx` | 调研来源（附链接 + 查阅日期） |
| `EV-xxx` | 验证证据（测试代码、日志、结果文件） |
| `DC-xxx` | 架构约束（交接给第七阶段） |
| `Q-xxx` / `AS-xxx` / `DF-xxx` / `DEC-xxx` / `CH-xxx` | 待确认 / 暂定假设 / 暂缓 / 决策记录 / 修订记录 |

- 编号只做索引，引用处必须写出结论本身，脱离本对话仍能读懂。
- 每个 TV 项必须能追溯到关联需求（`FR-xxx` / `NFR-xxx`）、第四阶段风险（`RISK-xxx`）或本轮用户确认。

### 阶段边界

用户在本阶段追问技术栈最终确定、模块划分、数据库设计、接口设计时：

1. 记录为 `deferred`；
2. 说明为什么现在不定；
3. 指出由第七阶段处理；
4. 不因为用户追问就提前做架构设计。

只有用户明确要求切换阶段或调用其他技能时，才离开本阶段。

## 文档落盘与更新节奏

1. phases/01 结束时创建 `TECHNICAL_VALIDATION.md` 骨架（模式 A 为极简版），落到项目工作目录 `docs/06-技术验证/TECHNICAL_VALIDATION.md`；用户指定了路径就以用户为准。
2. 每轮回答后立即更新相关章节、状态、决策记录，不攒到最后一次性写。
3. 验证证据存入 `docs/06-技术验证/validation/TV-xxx-xxx/`（README + 测试代码 + 结果文件），保持阶段产物自包含。
4. 结论变化时同步受影响的调研分析、架构约束和交接说明。

## 修订模式

用户读完后提出修改时，不重新生成整份文档：

1. 读取最新版 `TECHNICAL_VALIDATION.md`，把修改点登记为 `CH-001`、`CH-002`……
2. 评估修改是否与证据、结论状态、架构约束一致；结论变更是否需要补充验证。
3. 每轮挑 2–4 个最需要决定的修改点说明影响，由用户确认。
4. 只改受影响章节，同步证据等级、结论状态与第 8 章架构约束。
5. 文末追加修订记录，重新运行 [CHECKLIST.md](./CHECKLIST.md)，给用户变动摘要。

修订时同样遵守"不照单执行、不替用户否决、不静默改结论"。

## 完成条件

同时满足以下条件才能宣告本阶段完成：

- 已识别可能影响架构的关键技术问题（TV 清单）。
- 高影响问题已验证，或有明确的替代方案和风险处理方式。
- 所有标记"通过"的结论都有 A/B 级证据支撑，没有把推测写成已验证。
- 关键技术建议有调研或实验依据，来源可追溯。
- 技术版本、依赖条件、运行环境等重要约束已写入第 8 章架构约束。
- 尚未解决的问题已记录，明确了影响和处理方式。
- 验证结果若改变了需求或产品设计，相关文档已更新或标记待修订。
- 交接检查清单（见 phases/06）全部通过。
- [CHECKLIST.md](./CHECKLIST.md) 全部通过，或对"不适用"项有说明。
- 用户明确确认"可以进入第七阶段"（或有条件进入及其条件）。

任一条件不满足，继续对应阶段，不宣告完成。
